<h2 id="главное">🏠 Главное</h2>

🚚 Выпуск пакетов группы [`packages/`](../packages/README.md) — четыре шага, каждый своей
командой. Здесь живёт знание о НАШЕЙ поставке: что пакеты держатся одной версией, что
приложения и стенды в выпуске не участвуют, в каком порядке идут шаги. Механика (объявление
команды, конверт ответа, коды возврата, проба поставки) — в движке, здесь только сценарий.

🔁 **Скрипты одинаковы в любом репозитории.** Те же файлы уезжают синком в рабочий репозиторий
и работают там же; различаются только [переменные](#переменные), а не код. Девопс берёт отсюда
готовую команду; нужно что-то сверх — строит у себя на том же движке, не правя эти скрипты.

<h2 id="команды">🚀 Команды</h2>

```bash
pnpm --filter @web-core/release release <команда> [--json]
```

| Команда | Что делает | Что меняет |
|---|---|---|
| `plan` | что выпустится и какой версией | ничего, это вопрос |
| `version` | применяет план: версии, CHANGELOG, журнал интентов | файлы в дереве |
| `publish` | публикует группу в реестр и отчитывается, что уехало | реестр |
| `verify` | ставит опубликованное в чистый проект ВНЕ репозитория и собирает | ничего, кроме временной папки |

Коды возврата одинаковы у всех: `0` — сделано или делать нечего, `1` — отказ, `2` — команду
позвали неверно. `--json` отдаёт тот же ответ одним конвертом:

```bash
pnpm --filter @web-core/release release plan --json
# {"outcome":"done","summary":"выпуск 0.3.1: 19 пакетов","data":{"version":"0.3.1","packages":[…]}}
# {"outcome":"nothing","summary":"интентов нет — выпускать нечего"}
```

`verify` умеет проверять не всю группу разом:

```bash
pnpm --filter @web-core/release release verify --only @web-core/io
pnpm --filter @web-core/release release verify --no-types      # без проверки типов, быстрее
```

<h2 id="переменные">🎚️ Переменные</h2>

Ровно то, что различается между репозиториями. Всё остальное — код, и он один и тот же.

| Переменная | Что задаёт | По умолчанию |
|---|---|---|
| `NPM_CONFIG_REGISTRY` (или `--registry`) | куда публикуем и откуда ставим при приёмке | реестр из `.npmrc` окружения |
| токен реестра | право на запись | `.npmrc` окружения (у нас — `REGISTRY_TOKEN` из `.env`, см. [`PUBLISHING.md`](../PUBLISHING.md)) |

<h2 id="устройство">🧩 Устройство</h2>

| Файл | Что держит |
|---|---|
| `src/index.ts` | объявление четырёх команд и запуск программы |
| `src/plan.ts` | чтение плана выпуска и его разбор |
| `src/apply.ts` | применение плана плюс сверка, что интентов не осталось |
| `src/publish.ts` | публикация и чтение сводки `pnpm-publish-summary.json` |
| `src/verify.ts` | приёмка: проба поставки по каждому публикуемому пакету |
| `src/workspace.ts` | какие пакеты воркспейса вообще публикуются |
| `src/run.ts` | запуск внешней команды с захватом вывода |

<h2 id="цена">⚖️ Цена сценария</h2>

⚠️ **План разбирается из ЧЕЛОВЕЧЕСКОГО вывода `pnpm version -r --dry-run`.** Флаг `--json` у
этой команды объявлен в справке, но на план не действует: вывод остаётся текстовым в любом
порядке флагов (проверено на pnpm 11.17.0, 2026-09-23). Поэтому `src/plan.ts` разбирает строки
регуляркой, и это хрупко по построению — формат сменится молча.

Что сделано, чтобы поломка была громкой: если план собрался, но не разобрался ни в одну строку,
команда отвечает отказом «формат вывода pnpm изменился», а не пустым успехом. Когда `--json`
заработает, разбор снимается одной правкой.

<h2 id="нет">🚪 Чего здесь нет</h2>

- **Тегов, релизов и мержа** — они на стороне рабочего репозитория (решение user 2026-09-23).
  `pnpm version` в рекурсивном режиме их и не делает.
- **Коммита версий** — что делать с изменённым деревом после `version`, решает тот, кто запустил
  сценарий.
- **Знания о конкретном реестре** — адрес приходит переменной, а не записан в коде.
