# 🧭 Флоу выпуска — что делает девопс

Базовый порядок, которым выпускаются пакеты `@web-core/*`. Команды — в
[`README.md`](./README.md), причины решений — там же. Здесь только последовательность и то, обо
что реально спотыкаются.

Всё ниже прогонялось целиком 2026-09-23 на выпуске `0.4.0` — числа и отказы в примерах
настоящие, не придуманные.

## 📦 Откуда берутся эти скрипты

Папка `packages/.release/` приезжает синком вместе с пакетами — код сценария одинаков в обоих
репозиториях, различаются только переменные ниже. Чтобы она заработала в рабочем репозитории,
там нужно одно: объявить её членом воркспейса (`pnpm-workspace.yaml`) и исключить из выпуска, —
она приватная и в реестр не едет:

```yaml
packages:
  - packages/*
  - packages/.release   # скрытые папки `packages/*` не берёт

versioning:
  ignore:
    - './packages/.release'
```

Зависимость у неё одна — `@web-core/cli`, он едет тем же синком.

## 🔑 Что нужно до первого запуска

|                 |                                                                    |
| --------------- | ------------------------------------------------------------------ |
| Адрес реестра   | `NPM_CONFIG_REGISTRY` (или `--registry` у команды)                 |
| Токен на запись | строка в **пользовательском** `~/.npmrc`, а не в файле репозитория |

> [!IMPORTANT]
> **Токен нельзя класть в `.npmrc` репозитория даже через переменную.** pnpm 11 не разворачивает
> переменные в учётных данных из project-level файла и отказывает предупреждением: файл
> коммитится, и секрет утёк бы в чужой реестр. Рабочие места: `~/.npmrc` или шаг пайплайна,
> который его пишет.

## 🚦 Порядок

```bash
pnpm --filter @web-core/release release plan --json      # 1. что выпустится
pnpm build                                               # 2. собрать dist
pnpm --filter @web-core/release release version --json   # 3. поднять версии
pnpm --filter @web-core/release release publish --json   # 4. опубликовать
pnpm --filter @web-core/release release verify --json    # 5. принять поставку
```

Каждый шаг отвечает одним конвертом: `outcome` — `done` / `nothing` / `failed`, плюс `summary`
для человека. Коды возврата: `0` — сделано или делать нечего, `1` — отказ, `2` — команду позвали
неверно.

### 1. `plan` — что выпустится

Ничего не меняет. Пусто — значит интентов нет, и выпускать нечего:

```json
{"outcome":"nothing","summary":"интентов нет — выпускать нечего"}
{"outcome":"done","summary":"выпуск 0.4.0: 17 пакетов","data":{"version":"0.4.0","packages":[…]}}
```

Интенты записывает разработчик, не девопс: `pnpm change --bump minor --summary "…" <пакеты>`.
Нет интентов — пайплайн честно заканчивается на этом шаге, а не падает.

### 2. `pnpm build` — обязательный шаг, его легко забыть

Публикуется содержимое `dist`, и никакой `prepublishOnly` его не собирает. Пропустили сборку —
в реестр уедет прошлая, а то и отсутствующая.

Известная особенность: `apps/reference` может падать (`MISSING_EXPORT`) — это приватное
приложение-гейт, в реестр оно не едет и выпуск не блокирует. Пакеты при этом собираются все.

### 3. `version` — поднять версии

Требует **чистого рабочего дерева** — иначе `ERR_PNPM_UNCLEAN_WORKING_TREE`, и сценарий ответит
`failed`, ничего не тронув. В пайплайне после checkout дерево чистое; руками — закоммитьте своё
до выпуска.

Шаг меняет `package.json` всех пакетов группы и пишет CHANGELOG. **Коммита и тега не делает** —
что делать с изменённым деревом, решает тот, кто запустил.

### 4. `publish` — отправить в реестр

Идемпотентен: повторный запуск, когда всё уже в реестре, отвечает `nothing`, а не падает.
Пайплайн можно перезапускать.

### 5. `verify` — принять поставку

Ставит опубликованные пакеты в чистый проект **вне репозитория**, импортирует каждый подпуть из
`exports` и проверяет типы. Это единственный шаг, отвечающий на вопрос «а у потребителя оно
вообще работает»: внутри монорепо пакеты соединены симлинками, и ошибки поставки там невидимы.

```bash
release verify --only @web-core/io    # один пакет
release verify --no-types             # без проверки типов, быстрее
```

Что он ловит — не теория. На выпуске `0.4.0` шаг прошёл по 19 пакетам и нашёл **один настоящий
дефект поставки**: `@web-core/mcp` не импортируется голым `node` — его `dist` ссылается на
директорию (`dist/register-tool`), а ESM так не умеет. Внутри репозитория это невидимо: там
работает бандлер.

⚠️ **Остальные отказы того прогона дефектами НЕ были** — это ограничения самой пробы, и их чинит
владелец `@web-core/cli` (пункты заведены):

| Отказ | Почему это не поломка пакета |
|---|---|
| `Cannot find package 'postcss'` / `'xstate'` / `'solid-js'` | опциональный peer (`peerDependenciesMeta.optional`): подпуть честно требует, чтобы потребитель поставил зависимость сам. Проба их не ставит |
| `Client-only API called on the server side` | браузерный пакет (`ui`, `router`, `chat`) — голый `node import` падает по природе, проверять надо бандлером |
| `ERR_UNKNOWN_FILE_EXTENSION` / `ERR_IMPORT_ATTRIBUTE_MISSING` | подпуть отдаёт файл, а не модуль (`./base.css`, `./tsconfig`) — импортировать его как ESM нельзя |
| `ERR_UNSUPPORTED_DIR_IMPORT` в чужом пакете | сломана зависимость вендора, не наш код |

Вывод для девопса: пока эти пункты не закрыты, **`verify` читают глазами, а не принимают за
светофор**. Отчёт несёт шаги и путь к временному проекту — всё воспроизводится руками.

## 🧯 Если что-то пошло не так

| Симптом                                            | Что значит                                                         |
| -------------------------------------------------- | ------------------------------------------------------------------ |
| `nothing` на `plan`                                | интентов нет — это не ошибка, пайплайн просто заканчивается        |
| `failed` на `version`, «Working tree is not clean» | в дереве незакоммиченные правки                                    |
| `failed` на `publish`                              | нет прав (токен) или реестр недоступен — повторить безопасно       |
| `failed` на `verify`                               | поставка сломана у потребителя; смотреть `details.failures` и шаги |
| `failed`, «формат вывода pnpm изменился»           | обновился pnpm и сменил вид плана — чинится в `src/plan.ts`        |
