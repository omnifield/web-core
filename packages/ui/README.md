<h2 id="структура">📁 Структура</h2>

Скелет одинаков для каждого компонента кита и заведён шаблоном (генератором), а не решением
разработчика на месте: папка или файл, которого нет в этом списке, — то, чего ни один инструмент
кита не увидит (обход `entity/passport.ts` для входа в кит, барели, сборка README). Разработчик
заполняет содержимое размеченных файлов, а не придумывает структуру заново на каждый компонент.

```

├─ index.ts                🚪 барель наружу — что видит остальной кит
├─ entity/                 📜 контракт (рантайм)
│  ├─ anatomy.ts             части и адреса
│  ├─ passport.ts            части + состояния + настройки + ось варианта
│  ├─ io.ts                  вход/выход — необязателен, не у каждого компонента есть форма
│  └─ index.ts                барель entity
├─ components/              🧱 настоящие Solid-компоненты, по одному на часть
│  └─ index.ts                барель + `defineKitComponent`
├─ playground/              🛝 редакторские метаданные + доказательство скина
│  ├─ index.ts                `defineEditorInfo`
│  ├─ parts.ts                человеческие описания частей/состояний
│  ├─ recipe.ts               доказательный рецепт — никогда не в продакшене
│  ├─ settings.ts             необязателен — только если есть настройки
│  └─ assemblies(.ts|/)      готовые деревья схемы; файл или папка — по размеру
├─ test/ (или *.test.tsx)   🧪 доказательства: рецепт одевается, сборки рисуются
└─ README.md                📖 этот документ — сгенерированное + сохранённые зоны
```

**Обязательное** — `index.ts`, весь `entity/` кроме `io.ts`, весь `components/`,
`playground/index.ts`+`parts.ts`+`recipe.ts`, хотя бы одна сборка, `README.md`. **Необязательное** —
`entity/io.ts` (нет формы — нет файла, не пустой файл), `playground/settings.ts` (нет настроек —
нет файла). **Форма, а не наличие** — `assemblies`/тесты живут файлом ИЛИ папкой в зависимости от
того, сколько их: один файл, пока одной сборки хватает, папка — как только их больше одной.

**Количество внутри узла — не часть скелета, часть сложности компонента.** Сколько файлов
реально лежит в `components/` — решает не шаблон, а то, сколько у компонента частей и сколько
логики у каждой: `button` — один `kit.tsx` на единственную часть (`root`), `tree-view` — россыпь
файлов (`root.tsx` + `item/index.tsx`+`control.tsx`+`content.tsx`+`indicator.tsx`) на пять частей
с настоящей веткой внутри. Та же логика у сборок (`accordion` держит `base` и `action-list`,
`tree-view` пока только `base`) и у самого `recipe.ts` — не то, что файлов становится больше, а
то, что один файл шире: больше состояний, больше частей, больше правил внутри. Скелет фиксирует
ГДЕ что лежит, а не СКОЛЬКО его там — это решает сложность конкретного компонента, не шаблон.

**Скелет не запрещает — он делает предсказуемым.** Нельзя завести файл вне этого списка не
потому, что кит жадный, а потому, что весь остальной кит (барели, обход входа, генератор README,
редактор) уже умеет читать ровно эти места и ничего больше. Заполненный по этому скелету компонент
получает ВСЁ взаимодействие с китом бесплатно — попадает в барель, в паспорт, в редактор, в
`RenderTree`, в проверки. Если для задачи кажется, что нужен непредусмотренный файл — это почти
всегда значит, что возможности движка изучены не до конца: живой компонент — обычный Solid-код
(см. `RenderTree`'s `slots` для чужого контента в узле схемы, обычные модули `shared/` для общей
логики между частями) — редко нужен новый КЛАСС файла, почти всегда достаточно уже
предусмотренного места для него.

<h2 id="shared">🧷 Shared</h2>

Общий код кита вне папки конкретного компонента — то, что нужно больше чем одному компоненту,
заводится один раз, а не копией на каждый, у кого похожая нужда. Полное описание — в
[`src/shared/README.md`](./src/shared/README.md).

<h2 id="entity">🗃️ Entity</h2>

`entity/` — контракт компонента, тот, по которому он физически работает в приложении: анатомия,
паспорт и (если у компонента есть форма) IO. Это водораздел с `playground/` (см. ниже) в другую
сторону — здесь код и данные, которые едут в бандл приложения, а не проза для редактора.

<h3 id="anatomy">🧩 Anatomy</h3>

Анатомия — это перечень частей компонента и адрес каждой из них в разметке
(`data-scope="<компонент>"`/`data-part="<часть>"`). Она нужна, чтобы скин и редактор могли
обратиться к конкретному куску компонента по имени, а не гадать по классам и вложенности.

**Анатомия не выдумывается заново — берётся у Zag.js.** `entity/anatomy.ts` почти всегда строится
на `createAnatomy` из `@zag-js/<компонент>/anatomy` — том же перечне частей, каким пользуется сам
Zag внутри своей логики. Свой список частей рано или поздно разойдётся с тем, что реально шлёт
Zag на следующем релизе, поэтому кит берёт готовое, а не переписывает. Наружу из кита это не
видно: пользователь компонента получает СВОИ обёртки кита (`TreeRoot`, `TreeItem` и так далее у
дерева, аналогично у любого другого компонента), а не имя внутренней библиотеки.

`.build()` на анатомии даёт на каждую часть готовый адрес: `attrs` — атрибуты для JSX-узла, и
`selector` — CSS-селектор для скина. Считается один раз при загрузке модуля, не на каждый рендер.

**У анатомии есть свой построитель — `.omit(...)` и `.extendWith(...)`.** Первый убирает часть,
которую кит не собирается адресовать по отдельности, второй добавляет часть, которую придумал сам
кит (в Zag её нет вовсе). Оба метода — часть ТОГО ЖЕ построителя, что собрал исходный список
частей, поэтому добавленная часть получает настоящий адрес: скин и редактор видят её как обычную
часть, без особых случаев внутри движка.

**Готовую анатомию у надстройки (`@ark-ui/*/anatomy`) не берут — только у Zag.** Надстройка
собирает свой список поверх заговского и дописывает туда части, не проверяя, было ли уже такое
имя; взяв её объект целиком, кит вместе с полезными частями получает и повторы (см. `FAQ.md`).
Нужные части добавляются своим `.extendWith(...)`. Если машины у Zag нет вовсе — анатомия
объявляется через `createAnatomy` из `@web-core/skin/model`, как у `button`, `diagram` и `field`.

**Одинаковый смысл в разных компонентах должен называться одинаково.** Если у одного компонента
поставщик называет свою часть одним словом, а у другого — другим, хотя по смыслу это одно и то
же (например, «кликабельная строка с индикатором» или «место, куда потребитель кладёт своё
содержимое»), кит выравнивает имена сам — сокращает и добавляет части так, чтобы одна и та же
роль везде адресовалась одним и тем же словом. Причина не в красоте: анатомия — это шаблон, по
которому рано или поздно будут писаться сборки автоматически, и если у каждого компонента для
одной и той же идеи будет своё имя, ни генератор, ни человек не смогут писать сборку, не заглядывая
каждый раз в исходники конкретного компонента. Устоявшиеся общие имена складываются в свой
словарь (`shared/data/anatomy.ts`), и следующий компонент с той же формой подставляет готовое имя,
а не изобретает своё.

**У части «место, куда потребитель кладёт своё содержимое» (`content` и подобные) не должно быть
своих визуальных стилей.** Ни падинга, ни цвета, ни размера шрифта — какими они будут, решает то,
что реально легло внутрь, а не сама часть-контейнер. Причина не только вкусовая: `content` у
раскрывающихся частей (аккордеон, дерево и другие с keyframe-анимацией высоты через `--height`,
`packages/skin/src/motion/scenarios.ts`) — узел, чей размер меняет анимация каждый кадр. Найдено
живьём на аккордеоне: паддинг на этом узле превращал плавное закрытие в дёрганое (после какого-то
момента браузер переставал успевать перерисовывать кадры и просто прыгал к финальному состоянию).
Без своего падинга/цвета на `content` анимация идёт кадр в кадр без единого пропуска. На этой части
остаётся только МЕХАНИКА контейнера — `overflow: hidden`, `box-sizing: border-box`, сама анимация,
— а не оформление.

**Анатомия фиксирует АДРЕС части, а не то, каким кодом эта часть в итоге нарисована.** Один и тот
же адрес схемы может внутри рисоваться по-разному в зависимости от данных, которые компонент
получил, — это решает обычный код внутри функции компонента (`if`/`<Show>` по пропсам), а не
что-то особое в движке сборки: движок берёт компоненты и схему и рисует, а что происходит ВНУТРИ
функции компонента — его не касается.

**У корневой части нет своих `attrs` в коде кита.** Адрес корня уже приходит от самого Zag, кит
его не переставляет — `{...anatomyParts.root.attrs}` не пишется вручную ни в одном компоненте
кита, это была бы работа впустую поверх того, что уже есть.

<h3 id="passport">📜 Passport</h3>

Паспорт (`entity/passport.ts`, `definePassport(...)`) — то, что компонент заявляет о себе
данными: какие у него части, что каждая часть умеет менять на себе, какой вариант вида она несёт
и какие настройки вообще существуют. По паспорту скин проверяет, что рецепт ничего не забыл, а
редактор — что можно положить внутрь конкретной части.

**Части паспорта — это анатомия плюс список состояний на каждую.** Само перечисление частей
паспорт не придумывает — берёт готовым из анатомии (см. выше) — и на каждую часть добавляет,
какие состояния у неё бывают. Состояние — это пара «имя» + «метка»: метка — реальный CSS-селектор,
по которому скин действительно сможет её поймать, не изобретённый класс. Меток два вида:
атрибутная (`{ kind: "attribute", name: "data-selected" }`, ставит сам компонент/движок) и
псевдоклассовая (`{ kind: "pseudo", name: ":hover" }`, это работа браузера, а не компонента —
компонент никогда не пишет `:hover` на себя вручную). Паспорт может пометить один атрибут разными
значениями для разных состояний — например, «раскрыто» и «закрыто» у одной и той же части часто
делят один атрибут (`data-state`) с разными значениями (`"open"`/`"closed"`), а не заводят каждое
как отдельный флаг.

**Переменные (`variables`) — это CSS custom properties, которые часть реально несёт.** У каждой
переменной есть `setBy` — кто отвечает за то, что в неё положено конкретное значение (например,
`"kit"`, если значение считает сам код компонента, а не рецепт). Без этого поля скин не смог бы
отличить «переменная, которую можно смело подставить в рецепт» от «переменная, которую ещё
предстоит кому-то заполнить».

**Ось варианта (`variantAxis`) — это открытое имя, а не список кита.** Кит не хранит перечень
вариантов вида («outline», «primary» и подобное) — вариант это просто атрибут (`data-variant`),
имя которому даёт человек в редакторе, собирая скин. Паспорт объявляет только сам факт, что у
компонента есть такая ось и какой атрибут она занимает, — имена вариантов кит не знает и не
ограничивает.

**Настройки (`settings`) — типизированы против настоящих пропов компонента, не против
воображаемого списка.** `defineSettings<Props>()({...})` берёт тип из реального компонента, так
что настройка, которой в компоненте не существует, — это ошибка типов, а не то, что можно
случайно объявить в паспорте и забыть подключить. Если у компонента нет ни одной настройки,
паспорт так прямо и говорит — пустым объектом, а не отсутствием файла.

**Паспорт едет в бандл приложения — в отличие от `playground/`.** Он часть рантайм-контракта: сам
компонент по нему физически работает, поэтому паспорт живёт в `entity/`, не в `playground/` —
редакторская проза (человеческие описания, что каждая часть означает) читается только
инструментами редактора и в собранное приложение никогда не попадает.

<h3 id="io">🔌 IO</h3>

IO (`entity/io.ts`) — контракт данных компонента: во что реально резолвятся `bind`/`repeat` пути
сборки на входе, и что компонент отдаёт наружу на выходе. Это не про вид — одна и та же форма
входа одинаково дружит с любым рецептом, а вид отдельно решает скин.

**Схема пишется не голым zod, а инструментом кита.** `import { z } from "@web-core/io"`
вместо прямого импорта `zod` — если схемную библиотеку под капотом когда-нибудь придётся сменить,
переписать нужно будет в одном месте (внутри `packages/io`), а не в `entity/io.ts` каждого
компонента по отдельности.

**`input`/`output` — две разные, не одна общая схема.** `input` — форма данных, которые компонент
готов принять (то, что реально читают `bind`/`repeat` в сборке). `output` — форма того, что
компонент отдаёт наружу при взаимодействии (например, ключи выбранного).
`Data` (`z.infer<typeof input>`) — обычный TypeScript-тип, снятый с этой же схемы, а не описанный второй раз руками, — им
типизируются пути `bind`/`repeat` в сборке.

**Не у каждого компонента есть форма — и это нормально.** Компонент без собственных данных
(например, если ему нечего принимать, кроме того, что уже несёт сама часть) просто не заводит
`entity/io.ts` — файл необязателен, в отличие от остального `entity/`.

**Одно и то же поле в разных компонентах должно быть одним и тем же полем, а не только
похожим.** Раньше разные компоненты называли, например, подпись элемента одинаково просто по
привычке, каждый раз набирая `label: z.string()` заново, — ничего не мешало одному компоненту
однажды назвать это же поле иначе. Теперь такие поля — общий словарь (`shared/data/fields.ts`), а
не отдельная строка в каждом `io.ts`: готовый кусок формы подставляется через spread
(`{ ...fields.labeled }`) вместо того, чтобы каждый компонент набирал его заново. Так название и
тип поля физически один на весь кит, а не только по договорённости.

<h2 id="компоненты">🧱 Компоненты</h2>

`components/` — настоящие Solid-реализации: код, который рисует разметку. Кит компонента — это
КАРТА (`index.ts`, `defineKitComponent`), не один компонент на папку: каждая часть паспорта
рисуется своим сабкомпонентом — отдельной функцией с человеческим именем (`AccordionControl`, не
`control`), своими пропами и своим адресом (`data-scope`/`data-part`) в разметке.

<h3 id="свой-словарь-пропсов">🎭 Свой словарь пропсов, не чужой</h3>

Потребитель берёт компонент кита, а не библиотеку под ним, и не должен знать, что там вообще
что-то есть. Это касается не только имени компонента (см. заметку про анатомию выше — снаружи
`TreeRoot`/`TreeItem`, не имя внутренней библиотеки), но и формы его пропсов: кит объявляет СВОЙ
тип, а внутри функции-обёртки сам решает, в каком виде отдать данные поставщику — Ark, Kobalte,
Zag или вообще никому, если компонент свой с нуля. Прямое присваивание чужого типа пропсов как
своего — протёкшая абстракция: это значит, что кит не придумал контракт, а взял чужой и переклеил
на него своё имя, вместе со всей номенклатурой поставщика, включая его собственные приёмы
композиции.

Способ подмены разметки — тоже часть словаря кита, а не поставщика: один публичный способ сказать
«нарисуй этот компонент другим тегом или другой разметкой», один и тот же по имени и поведению для
любого компонента кита, независимо от того, что у него внутри.

<h3 id="extras">🧩 Extras — не строительный кубик</h3>

Не любая часть становится отдельным сабкомпонентом, который можно собрать снаружи. Наружу
(`components/index.ts` → барель пакета → карта кита) идут только те куски, которые нужны для
СТРОИТЕЛЬСТВА — то, что потребитель или движок сборки кладут сами, выбирая между вариантами.
Часть, которая не выбор компоновки — всегда идёт вместе с другой и сама по себе не существует, —
не заводит собственного публичного компонента: её кладёт внутрь себя тот сабкомпонент, которому
она принадлежит. Кит держит для такой части имя — `extras`.

- **Root несёт свой Provider сам.** Провайдер — не отдельный кубик рядом с корнем, а его
  собственный внутренний контекст; собирает себя корень целиком, потребитель не собирает
  «root + provider» вручную.
- **Технические узлы остаются внутри владельца.** Часть, которая существует не ради компоновки, а
  ради технической нужды (фокус, форма, доступность), не адресуется в анатомии и не входит в
  карту кита — её кладёт сам компонент-владелец, потребителю собирать её отдельно не нужно.

Общее правило: всё, что провайдер компонента отдаёт как техническую деталь реализации, кит не
передаёт потребителю в голом виде — наружу идёт только то, что реально можно скомпоновать
по-разному.

<h3 id="скин-компонент-просит-сам">🎨 Скин — компонент просит сам</h3>

Почти каждый `root.tsx` первой строкой в теле функции, до `useSlot`/`useAddress`, зовёт
`useKitLife(passport, props)` (`shared/utils/skin-life.ts`). Утилита делает три дела одним
вызовом: пишет трейс жизни примитива (метка `ui.${passport.component}` берётся из самого паспорта,
не набирается второй раз руками в каждом файле), зовёт `useComponentSkin(passport, props)` из
`@web-core/skin/solid` — та реактивно допечатывает CSS только тех `variant`/`settings`, которые
компонент реально получил в пропсах сейчас, а не весь рецепт формы целиком, — и зовёт
`useComponentValidation(passport, props)` из `@web-core/form/solid`, ВОЗВРАЩАЯ её результат
(`Accessor<ComponentValidation | undefined>` — `{invalid?, errorText?, hidden?, disabled?}`).
Без `<SkinProvider>`/`<ValidationProvider>` в дереве (голый кит, тест без провайдера) — тихий
no-op по обоим: кит обязан жить без presets и без формы вовсе, это его базовое обещание.

```tsx
import { passport } from "../entity/passport.js";
import { useKitLife } from "../../shared/utils/skin-life.js";

export const Button = slotAware(function Button<T extends ValidComponent = "button">(
  props: ButtonProps<T>,
) {
  useKitLife(passport, props);
  // ...
});
```

Возврат — `Accessor<ComponentValidation | undefined>` — большинство компонентов зовут `useKitLife`
выражением-стейтментом и не читают его: TS не заставляет использовать возврат, ничьё поведение не
меняется. Компонент, которому есть что показать (`invalid`/`errorText` — `Field`, разбор ниже),
забирает акцессор:

```tsx
const validation = useKitLife(passport, props);
return <ArkRoot {...dropAddress(props)} invalid={validation()?.invalid} errorText={validation()?.errorText} />;
```

**`useKitLife` не заменяет адресацию — только просит CSS.** Утилита читает `variant`/`settings` из
пропсов, но чтобы напечатанное правило хоть что-то нашло в разметке, каждая часть ещё обязана
физически нести `data-scope`/`data-part` — их ставит только `anatomyParts.<часть>.attrs`, ни Zag,
ни Ark сами их не проставляют (проверено по `toast.connect.mjs` — там нет ни одного `data-scope`).
На это нашли и починили живой пример: `toast` звал `useKitLife` последним из всей 33 компонентов
(см. `FAQ.md`) именно потому, что до этого у него не было адресации ни на одной из пяти частей —
`useKitLife` без неё напечатал бы CSS, которому попросту не за что было бы зацепиться в DOM.

Устройство самого `useComponentSkin` (кеш по компоненту, single-flight на сеть, гонка с чужим
`wear()`) — забота `packages/skin`, разбор там (`packages/skin/README.md`/`FAQ.md`). Здесь несём
только паспорт и пропсы — чужая ответственность внутрь не копируется.

<h2 id="playground">🛝 Playground</h2>

`playground/` — всё, что видит редактор скина и агент, читающий каталог, но никогда не видит
собранное приложение. Это водораздел с `entity/`: `entity/` — контракт, по которому компонент
физически работает, `playground/` — человеческие описания ЭТОГО ЖЕ контракта, для того, кто
собирает вид руками, а не пишет код. Пакет собирается с `sideEffects: false`, поэтому продакшен,
который не импортирует `playground/`, не платит ни единым словом из того, что здесь написано.

<h3 id="playground-parts">🔩 Parts</h3>

`playground/parts.ts` — то же самое перечисление частей, что и в паспорте, но с человеческим
описанием на русском вместо только машинного контракта: что часть значит (`means`), что значит
каждое её состояние и каждая переменная, и что можно положить внутрь неё (`accepts`).

**`accepts` — правило вложенности, и у него три разных состояния, не два.** Не объявлено —
ничего не запрещает: молчание не значит запрет. Пустой список — не пускает НИЧЕГО: место в этой
части уже занято самим компонентом, добавлять туда через схему нечего. Непустой список —
допустимо ровно то, что перечислено, и ничего сверх. Спутать пустой список с «не объявлено» —
частая ошибка: это два прямо противоположных правила, а не один и тот же способ написать
«ничего особенного».

**Правило работает в обе стороны.** Вперёд его читает редактор — чтобы не дать собрать дерево, в
котором внутрь части попадёт что-то незаявленное. Назад его читает механика скина — чтобы для
части вывести, у каких предков она вообще имеет право оказаться, не храня этот список отдельно.

**Часть допускает не только другие части, но и содержимое, и по роду.** `accepts` может называть
конкретную часть по имени (`{ kind: "component", name: "control" }`), любой компонент без разбора
имени (`{ kind: "component" }`), или содержимое определённого рода
(`{ kind: "content", genus: "text" }`, `"icon"`) — род сюда приходит от самого компонента (`genus`, объявляется в
`playground/index.ts`), это две стороны одного и того же правила: часть говорит, какой род
пускает, компонент — какого он рода.

<h3 id="recipe">🎨 Recipe</h3>

`playground/recipe.ts` — ДОКАЗАТЕЛЬСТВО, а не поставка. Он лежит в папке компонента, но никогда
не экспортируется из `index.ts`/`passport.ts`/`components/index.ts` — читает его только тест
самого компонента, чтобы доказать: паспорт МОЖЕТ быть одет целиком настоящим механизмом скина.
Кит по умолчанию не несёт ни одного стиля — это не приблизительный вид «для затравки», а именно
доказательство того, что раздетый паспорт в принципе одевается.

**Настоящий вид живёт отдельно, не здесь.** То, что реально видит пользователь приложения, —
запись в службе скина (палитра + рецепты форм, надетые в наряд), не файл в этой папке. Компонент
без такой записи рисуется вообще без единого правила скина — и это законное состояние, не
«сломанная подсветка».

**Проверять рецепт нужно через реальную сборку скина, а не голой проверкой.** Пустой скин без
палитры (`{name, recipes}` без `variables`) заваливает вообще всё — каждая ссылка вида
`var(--space-2)` читается как «неизвестное значение», потому что сверять её физически не с чем.
Правильный путь — собрать реальный `assemble(outfit, { palettes: [палитра], forms: [form] })` и
уже РЕЗУЛЬТАТ проверять — тем же путём, каким проверяет живой редактор скина, а не сокращённым
для теста. Палитра для теста обязана закрывать ВЕСЬ словарь целиком, а не только то, что нужно
конкретному рецепту, — иначе тест заваливается на ролях, которые к делу не относятся.

**Каждое состояние, объявленное в паспорте, обязано быть адресовано хоть одним правилом.**
Проверка (`skinGaps`) не прощает молчания: состояние можно оформить незаметно (пустым/нейтральным
правилом), но не пропустить вовсе — иначе однажды окажется, что состояние в паспорте объявлено,
а в разметке никак не выглядит иначе, и никто не заметит этого, пока кто-то не наткнётся вживую.

**Переменная части — не всегда СВОЯ, и наследование браузера здесь не в счёт.** Часть может
объявить в паспорте CSS-переменную (например, глубину вложенности), а физически в разметке эту
переменную видит и её ДОЧЕРНЯЯ часть — просто потому, что лежит внутри в DOM. Обычный CSS отдал
бы значение по наследованию сам, но проверка скина не берёт это на веру: голая ссылка на
переменную в части, которая её не объявляла, — это ошибка проверки, даже если в браузере всё
отработало бы правильно. Правильный адрес — `ancestors` в записи части: явно назвать часть-предка,
её состояние (если нужно) и что взять из её переменной. Так генерируется настоящий составной
селектор («у этого предка — вот это значение для потомка»), а не тихая надежда на то, что браузер
досчитает сам.

**Безусловный `display` в базовых пропсах бьётся с нативным `[hidden]` — и всегда проигрывает
автор, не браузер.** Часть, которую кит прячет НАТИВНЫМ атрибутом `hidden` (а не своим состоянием
вроде `data-selected`) — это обычный способ показывать что-то «только пока раскрыто» или «только
пока выделено» — не должна получать `display` в БАЗОВЫХ пропсах рецепта. Причина в специфичности
CSS: правило браузера `[hidden] { display: none }` бьётся одним атрибутом, а собственный селектор
кита (`[data-scope="…"][data-part="…"]`) — уже двумя, то есть конкретнее, и обычный
`display: flex` в базовых пропсах побеждает браузер безоговорочно. Атрибут переключается честно, а
содержимое всё равно остаётся видимым — потому что в этом конкретном споре сильнее оказался автор
рецепта, а не браузер. Это не разовая опечатка: один и тот же класс бага находили дважды, на двух
разных компонентах, одним и тем же способом. Правило простое: `display` для такой части — только
внутри состояния, при котором она ПОКАЗАНА, никогда — в базовые пропсы без условия.

**Вид части решает, какие набивку, высоту и шрифт она носит — не компонент.** Шкала
(`packages/style`, `SPACE_ROLES`) говорит, сколько стоит роль, но не говорит, какая часть какую
роль носит; без этого одинаковые по смыслу части у разных компонентов одеваются по-разному, и
соседние контролы начинают читаться как из разных китов. Видов четыре, и вид выводится из самих
свойств части, а не из её имени — имена у компонентов свои, а вид общий:

| вид | как узнаётся | что носит |
| --- | --- | --- |
| контрол `md` | ступень высоты `control-height-md`, своей вертикальной набивки нет | `paddingInline: space-4`, `fontSize: font-size-md` |
| контрол `sm` | то же со ступенью `control-height-sm` | `paddingInline: space-3`, `fontSize: font-size-sm` |
| строка списка | кликабельна (`cursor: pointer`) и несёт свою вертикальную набивку | `paddingInline: space-2`, `paddingBlock: space-1`; шрифт свой |
| панель | контейнер вокруг содержимого | со своими пунктами — `space-1`; свободное содержимое — `space-4`; карточка — `space-6` |

Высота, набивка и шрифт контрола едут ВТРОЁМ: взял ступень — взял все три значения. Смесь
(`sm`-высота с `md`-шрифтом) и была тем, из-за чего кит выглядел разнобойно. Нулевая набивка
(`paddingBlock: "0"`) значит «набивку даёт родитель» — такая часть не меряется ни одним из видов
(кнопка сортировки внутри ячейки таблицы). Держит это `test/space-roles.test.ts`, прогоном по всем
рецептам кита; разбор, почему строка списка не считается контролом, — в [`FAQ.md`](./FAQ.md).

**`root` не носит внешних отступов на самом себе.** `margin`/`padding` снаружи компонента ставит
тот, кто его расставляет рядом с другими (родительский контейнер, сетка), а не сам компонент —
иначе у каждого компонента в раскладке свой, слегка отличающийся зазор, и картина расползается от
соседа к соседу. Это касается только ВНЕШНЕГО отступа: внутренние отступы у частей ВНУТРИ `root`
(строка, поле, ячейка) — обычная часть анатомии компонента и никак не переезжают.

<h3 id="settings">🎚️ Settings</h3>

`playground/settings.ts` — человеческое описание настроек компонента для редактора: что значит
каждая настройка (`means`) и, если у неё несколько вариантов, что значит каждый вариант. Файл
необязателен — заводится только у компонента, у которого настройки вообще есть.

**Имя настройки — не своё слово, а слово из общего закрытого перечня.** Кит держит один список
имён настроек на весь кит (`orientation`, `multiple` и подобные) — так же, как для групп
компонентов в каталоге (см. ниже про сам каталог): если каждый компонент называет одну и ту же
идею по-своему, ни человек, ни генератор не смогут понять новый компонент, не читая его с нуля.
Настройка компонента обязана и называться именем из этого перечня, И реально существовать пропом
у самого компонента — одного из двух условий недостаточно.

**У настройки — вид значения, значение по умолчанию, и, возможно, зависимость от другой
настройки.** Значение бывает простым переключателем (да/нет) или выбором из нескольких вариантов
— тогда у каждого варианта тоже есть своё `means`. Настройка может быть объявлена «неважной» при
конкретном значении другой настройки — например, одна настройка становится бессмысленной, если
другая уже выключает то, на что первая влияет; редактор использует это, чтобы не показывать
человеку выбор, который в данный момент ничего не изменит.

**Файл написан БЕЗ явной типовой аннотации — и это осознанно, а не недосмотр.** Если объявить тип
руками, ключи объекта расширяются до `string`, и опечатка в имени настройки перестаёт быть личной
ошибкой этого файла — превращается в невнятную ошибку совсем в другом месте («отсутствуют
свойства orientation, multiple»), где реально ничего не отсутствует. Без аннотации TypeScript
сверяет буквально те же самые ключи, что здесь написаны, с тем, что просит паспорт, — переименуй
настройку здесь, и ошибка укажет ровно на эту строку, а не на что-то по соседству.

<h3 id="assemblies">🏗️ Assemblies</h3>

`playground/assemblies/` — готовые деревья схемы (`PassportAssembly`): доказательство, что
паспорт реально собирается в рабочую композицию через движок (`RenderTree`), а не только теоретически
проходит проверку по отдельности. Один файл — одна сборка, барель `index.ts` собирает их в общий
список.

**У составного компонента обязана быть минимум одна БАЗОВАЯ сборка, и её слот под содержимое
потребителя остаётся пустым.** Автор компонента не знает заранее, что именно туда положат — его
дело показать анатомию и вложенность (какая часть во что вкладывается, как работает повтор), а не
насытить слот содержимым за потребителя. Живой пример в ките — у аккордеона `base.ts` держит
контент-слот каждого раздела пустым (`children: []`), а рядом отдельным файлом лежит
`action-list.ts` — тот же аккордеон, но с настоящим списком выбора внутри содержимого. Появится
третья сборка с чем-то ещё внутри слота — базовая при этом не меняется никогда, обе живут рядом,
одна не переписывает другую.

**Сборка может ссылаться на ЧУЖОЙ компонент кита прямо внутри себя** (как `action-list.ts`
ссылается на список выбора) — составные сборки не обязаны ограничиваться частями одного
паспорта.

**Сборка — это не только компоновка частей: дефолтный проп корня тоже бывает сборкой, если он
решает ФОРМУ.** Обычно соседние сборки отличаются деревом — какая часть в какой лежит. Но у
компонента, который растит структуру сам (по данным, как `table` и `diagram`), дерево у всех
сборок одинаковое — один узел корня с `bind`, — и вся разница в одном объявленном пропе. Это
законная сборка, а не «настройка, положенная не туда»: сборка отвечает на вопрос «чем эта вещь
является», и если проп меняет, КАКИМИ частями и по какой математике компонент себя рисует, он и
есть ответ на этот вопрос.

🔍 Живой пример — `diagram`: `shape` (`line`/`area`/`bar`/`point`) решает, какой частью рисуется
серия и какую шкалу берёт корень под неё; четыре сборки отличаются ровно этим пропом, деревья у
них совпадают до последнего узла. Потребитель при этом выбирает вид графика тем же способом, что
и любую другую сборку — по имени, и те же самые данные показываются любым из четырёх видов.

Граница проходит по тому, что проп меняет. Меняет ВИД (цвет, толщина, отступ, прозрачность) —
это рецепт и его варианты, сборке там делать нечего. Меняет то, ЧЕМ вещь нарисована (другие
части, другая математика, другой вид шкалы) — сборка, даже если разница в одном слове.

> [!IMPORTANT]
> На уровне приложения (в `products/*`, в реальном использующем коде) деревья для `RenderTree`
> НЕ ПИШУТСЯ вручную литералом. Живой код всегда обращается к уже готовой, названной сборке
> компонента через `instanceOf(component, rootProps, assemblyName, data)` — и уже РЕЗУЛЬТАТ этого
> вызова передаёт в `<RenderTree tree={...} registry={...} data={...} />`. Сборки — это
> собственность компонента кита, доказанная его же тестами; приложение выбирает готовую сборку по
> имени и отдаёт ей свои данные, а не сочиняет новое дерево схемы на лету. Если ни одна из готовых
> сборок компонента не подходит — это повод завести новую именованную сборку РЯДОМ с существующими
> в самом компоненте (см. правило выше), а не собрать разовое дерево прямо в коде приложения.
