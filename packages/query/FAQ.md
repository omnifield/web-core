# ❓ FAQ

Короткие ответы на конкретные вопросы, которые уже возникали по этому пакету. Не общая
документация (она в [`README.md`](./README.md)) и не план (он в [`ROADMAP.yaml`](./ROADMAP.yaml))
— только факты, каждый проверен либо чтением исходников `@tanstack/solid-query`/`solid-js` в
`node_modules`, либо прямым прогоном.

---

## Solid-адаптер

### Почему опции `createQuery` обязаны быть функцией, если тип называется `UndefinedInitialDataOptions`, а не `Accessor<...>`?

**Коротко: имя типа прячет это — сам тип объявлен как `Accessor<...>` под другим именем, и ошибка компилятора на голом объекте не подсказывает причину прямо.**

`UndefinedInitialDataOptions`/`DefinedInitialDataOptions` (`@tanstack/solid-query/src/queryOptions.ts`)
объявлены буквально как `Accessor<QueryOptions<...> & {...}>` — тип из `solid-js`, то есть
функция без аргументов. `useQuery` (`src/useQuery.ts`) сразу вызывает `options()` внутри
`createMemo(() => options())`. Голый объект на месте параметра либо не пройдёт тайпчек (он не
вызываем), либо, если TS всё же пропустит благодаря структурной типизации подходящей формы,
`options()` в рантайме упадёт как вызов не-функции — что в обоих случаях не объясняет причину
человеку, потому что имя типа не содержит слова `Accessor`.

Проверено чтением `@tanstack/solid-query@5.102.8/src/queryOptions.ts` и `src/useQuery.ts`
(2026-09-04).

---

### Почему результат `createQuery` нельзя деструктурировать (`const { data } = query`)?

**Коротко: результат — `Proxy` над Solid-стором (`createStore`), а не обычный объект; доступ по
свойству — единственный путь, которым Solid отслеживает изменение.**

`useBaseQuery` (`src/useBaseQuery.ts`) хранит состояние в `createStore` (`solid-js/store`) и
возвращает `new Proxy(state, handler)`, где `handler.get` дополнительно перехватывает `data` —
для него значение читается не из стора напрямую, а из `createResource` (`queryResource`), под
которым лежит асинхронная загрузка. Деструктуризация (`const { data } = query`) читает оба поля
ОДИН раз в момент вызова, не оборачивает чтение в реактивный geттер — Solid не видит, что `data`
вообще было прочитано, и не пересчитывает потребителя при следующем обновлении.

Проверено чтением `src/useBaseQuery.ts`, функция `createDeepSignal`/`handler.get` (2026-09-04).

---

### Почему `create*` (`createQuery`, `createMutation`, …) — не просто типовые алиасы, а буквально та же функция, что и `use*`?

**Коротко: `export const createQuery = useQuery` — присваивание переменной, не отдельная
реализация и не только тип; в рантайме это один и тот же объект функции.**

`@tanstack/solid-query/src/index.ts` объявляет каждый `create*` через `export const createX = useX`
рядом с реэкспортом самого `useX`. Разницы в поведении нет по построению, не только по контракту
типов — `createQuery === useQuery` (`===`, не просто совместимые сигнатуры).

Проверено чтением `src/index.ts` (2026-09-04).

## Структура пакета

### Почему корневой `src/index.ts` не несёт логику сам, а только реэкспортирует `engine/`?

**Коротко: по образцу `packages/store`/`packages/assembly` — «поверхность пакета» отдельно от
реализации.**

`src/index.ts` — один `export * from "./engine/index.js"` с комментарием сверху. Вся логика (сам
реэкспорт `@tanstack/solid-query` вместе с объяснением, почему он полный) — в
`src/engine/index.ts`. `dist/index.d.ts` после сборки — тоже один реэкспорт, все типы протянуты
насквозь.

---

### Почему `./devtools` и `./persist` — отдельные папки (`src/devtools/index.ts`,
`src/persist/index.ts`), а не файлы прямо в `src/`, как было раньше?

**Коротко: по образцу `@web-core/store`'s `./machine` — самостоятельный подпуть без внутренней
семьи получает свою папку; в отличие от store'вских `./persist`/`./undo`/`./reset`/`./validate`,
у которых общий смысл «аддон `.with()`» оправдывает один `addons/`-каталог на четверых, у query
`devtools` и `persist` не связаны друг с другом ничем, кроме общего вендора TanStack — разной
природы подпути, разные папки.**

Смена коснулась только `package.json` `exports` (пути `dist/devtools.js` →
`dist/devtools/index.js`, аналогично `persist`) — публичные имена подпутей (`./devtools`,
`./persist`) не менялись, содержимое файлов тоже.

---

### Почему `@tanstack/solid-query` объявлен зависимостью (`dependencies`), а не `peerDependencies`, хотя `solid-js` — peer?

**Коротко: приложение никогда не импортирует `@tanstack/solid-query` напрямую (в отличие от
`solid-js`, который держит и приложение, и этот пакет, и другие пакеты web-core одновременно) —
версия вендора целиком наша забота, прятать её от потребителя безопасно.**

`solid-js` обязан быть ровно ОДНИМ экземпляром на всё приложение (реактивность держится на общем
модуле) — поэтому он peer, версию выбирает приложение. `@tanstack/solid-query` достаётся
исключительно через `@web-core/query`, второй копии взяться неоткуда — значит колебание его
версии между релизами этого пакета не бьёт по потребителю, и держать его обычной зависимостью
безопасно.

## Devtools

### Vendor уже прячет `SolidQueryDevtools` в проде сам (`isDev`) — зачем README всё равно просит оборачивать импорт в `import.meta.env.DEV`?

**Коротко: самозащита есть, но она не про размер бандла — `import.meta.env.DEV` на стороне
приложения нужен, чтобы Vite вообще не включал код девтулов (и его чанк) в прод-сборку, а не
только чтобы компонент не отрисовался.**

`@tanstack/solid-query-devtools/src/index.tsx`: `SolidQueryDevtools = isDev ? clientOnly(() => import('./devtools')) : function() { return null }`. `isDev` берётся из `solid-js/web` —
константа, буквально `true`/`false`, выбранная package.json`exports`'ом самого `solid-js/web` по
условию `development` (`dist/dev.js` → `isDev = true`, дефолтная ветка `dist/web.js` → `isDev = false`, сверено 2026-09-04). Vite подставляет условие `development` только в дев-сервере — в
проде резолвится `web.js`, и компонент правда становится no-op сам по себе, без участия этого
пакета.

Но это не отменяет совет: `isDev` решает только что ОТРИСУЕТСЯ, а не что ПОПАДЁТ В БАНДЛ — сам
модуль `./devtools` (и код `clientOnly`) остаётся частью графа импортов, пока приложение его
статически импортирует, вне зависимости от значения `isDev`. `import.meta.env.DEV` на стороне
приложения — единственный способ, которым Vite может исключить сам импорт целиком (dead code
elimination на уровне statically known constant, не на уровне значения экспортированной
переменной).

## GraphQL

### Почему основной способ — `createGraphQLClient`, а не сразу `graphqlRequest`?

**Коротко: первая версия `./graphql` экспортировала только `graphqlRequest(url, document,
variables?, headers?)` — url/headers на КАЖДЫЙ вызов. Замечание user: "получается что сейчас он
строит механики у себя... получается у тебя набор утилит, а не движок" — и это было в точку.
Копия `./persist`'s `storage` сюда не годилась: `storage` передаётся ОДИН раз при вызове
`persistQueryClient()` на старте, а не на каждый запрос, как было бы с `graphqlRequest`.**

Раз url/headers нужны на каждый вызов, а голый `graphqlRequest` их не хранит — вызывающий код либо
копирует их в каждый `queryFn`, либо сам собирает вокруг пакета свой клиент. Второе и есть «юзер
химичит у себя» — движок должен давать одну готовую механику, а не заготовку под самостоятельную
сборку. `createGraphQLClient({ url, headers? })` конфигурируется один раз при старте (рядом с
`new QueryClient()`), дальше `.request(document, variables?)` используется как есть.
`graphqlRequest`/`gql`/`ClientError` оставлены (по просьбе user — «могут пригодиться, плюс их уже
юзают») как ОСОЗНАННЫЙ побег из движка, не альтернативная витрина API — см. README, раздел
"Анатомия".

---

### Почему `graphql-request`, а не `urql`/Apollo Client — оба тоже умеют GraphQL?

**Коротко: у обоих свой нормализованный кэш поверх данных, а кэш в приложении уже есть —
`@tanstack/solid-query`, смонтированный через `QueryClientProvider`. Второй кэш поверх первого не
даёт выгоды, только источник рассинхрона (какая копия свежая после мутации).**

`graphql-request` сам себя позиционирует как "minimal GraphQL client" — синглтон `fetch` с телом
`{query, variables}`, без стора и без кэша. Это ровно то, что нужно на роль
`queryFn`/`mutationFn`: вся механика загрузки/повторов/протухания остаётся на TanStack Query,
GraphQL-клиент — только транспорт до байт ответа. Функция `request` реэкспортирована под именем
`graphqlRequest` (вендорское имя слишком общее для верхнего уровня пакета, где уже есть чужой
`fetch`); класс `GraphQLClient` того же вендора — БЕЗ переименования, но и без прямого экспорта —
питает `createGraphQLClient` изнутри (он тоже не держит кэша, только url+headers, так что
рассуждение "не тащим второй кэш" его не касается).

---

### Почему `graphql` — `peerDependencies`, а не только `devDependencies` для типов?

**Коротко: это не только типы — `graphql-request` реально дёргает `parse`/`print`/`Kind` из
`graphql` в рантайме (разбор строки документа при отправке запроса), значит без пакета `graphql`
рядом в `node_modules` приложения будет ошибка резолва модуля в проде, а не ошибка типов в
редакторе.**

Диапазон версий (`"14 - 16"`) — тот же, что объявляет сам `graphql-request@7.4.0` в своих
`peerDependencies` (`graphql@17` не входит в диапазон, поэтому в `devDependencies` этого пакета —
`^16.14.2`, не последняя мажорная). `gql`-тег того же вендора рантайм-зависимости от `graphql` не
несёт — это чистый passthrough по строке для подсветки синтаксиса в редакторах/prettier, без
парсинга в AST.

Проверено чтением `graphql-request@7.4.0/build/legacy/helpers/analyzeDocument.js` (`import { parse, print } from 'graphql'`) и `graphql-request@7.4.0/package.json` (2026-09-09).

## REST

### Почему основной способ — `createRestClient`, а не сразу `restRequest`?

**Коротко: та же история, что в GraphQL-секции — `restRequest(url, init?)` брал url параметром на
каждый вызов, скопировано с `./persist`'s `storage`, но там конфиг передаётся один раз на старте,
а не на каждый запрос. `createRestClient({ baseUrl, headers? })` конфигурируется один раз, дальше
`.request(path, init?)` — только путь. per-call `headers` в `init` перекрывают клиентские по
имени (нужно для разовых заголовков вроде `idempotency-key`, не для смены авторизации на каждый
вызов).**

`restRequest`/`HTTPError` оставлены (по просьбе user) как ОСОЗНАННЫЙ побег из движка — см. README,
раздел "Анатомия", и симметричный вопрос в секции GraphQL.

---

### Почему у REST нет вендора вроде `ky`/`ofetch`, а у GraphQL — есть (`graphql-request`)?

**Коротко: GraphQL-запрос — это протокол (POST с телом `{query, variables}`, разбор ошибок из
`errors`-поля ответа), для него есть смысл не изобретать велосипед. REST — просто `fetch` + JSON,
протокола сверх HTTP нет, а всё, что дают `ky`/`ofetch` сверх голого `fetch` (ретраи, таймауты,
хуки, свой кэш ответов) — либо уже делает TanStack Query, либо не нужно вообще. Зависимость ради
15 строк кода не окупается.**

`restRequest`/`HTTPError` — свой код (`src/rest/index.ts`), не реэкспорт. Держит ровно то, что не
умеет голый `fetch` сам: `json`-шорткат (сериализация + `content-type` без ручной возни) и бросок
типизированной ошибки на не-2xx (`fetch` сам по себе не считает 404/500 ошибкой — `response.ok`
надо проверять руками на каждом вызове, что и заворачивает `restRequest` один раз). `createRestClient`
использует их же изнутри — второй реализации HTTP-логики в пакете нет.

---

### Почему `restRequest` не бросает на 2xx с нечитаемым телом, а тихо отдаёт `undefined`/текст?

**Коротко: `204 No Content` (обычный ответ на `DELETE`/некоторые `PUT`) и пустое тело — не
ошибка, а часть контракта HTTP; заставлять `restRequest` кидаться на этот случай значило бы
принуждать каждый вызывающий код к try/catch там, где он должен быть необязательным.**

Разбор тела смотрит на `content-length: 0`/`status: 204` → `undefined`, иначе на `content-type`:
содержит `json` → `response.json()`, иначе — `response.text()` (бэки, отдающие голый текст/HTML
вместо JSON на ошибке — частый случай, `.json()` на таком теле сам бросил бы менее полезную
ошибку парсинга вместо `HTTPError` с исходным текстом в `data`).

## Поставка наружу

### Почему заголовки клиентов описаны своим `RequestHeaders`, а не `HeadersInit`?

**Коротко: `HeadersInit` — глобал библиотеки `DOM`, а транспорт зовут и из серверных пакетов,
которые типизируются без неё; своя карта «имя → значение» не зависит от среды и принимается
`fetch`/`GraphQLClient` как есть.**

Поймано первой реальной публикацией пакетов в реестр: `pnpm --filter @web-core/mcp build` падал
на `../query/src/graphql/index.ts(9,70): error TS2304: Cannot find name 'HeadersInit'`, и
`@web-core/mcp` единственный не уехал в реестр. `packages/mcp` стоит на
`@web-core/build/tsconfig-node` (`lib: ["ESNext"]`, `types: ["node"]`, без `DOM`) и импортирует
`@web-core/query/graphql`.

Проверено чтением `@types/node@24.13.3/web-globals/fetch.d.ts` (2026-09-22): под node-типизацией
глобально объявлены `fetch`, `Headers`, `Response`, `Request`, `RequestInit` — а `HeadersInit`
нет. Значит ломалось ровно одно имя, и лечится оно сужением, а не переездом транспорта на другие
типы: остальной код обоих подпутей под `lib: ["ESNext"]` проходит.

Добавить `DOM` в `@web-core/build/tsconfig-node` — не решение: серверному пакету нельзя выдавать
браузерные глобалы ради одной подписи типа, это прячет ошибку, а не убирает её. Так же не годится
и «починить только `./graphql`, раз падает он»: то же имя стояло в `createRestClient`, и
следующий серверный потребитель упёрся бы в ту же стену.

Два следствия, которые стоит знать:

- **Поверхность сузилась.** Раньше формально можно было передать `Headers`-объект или массив пар,
  теперь — только карту. В репозитории `headers` в `createGraphQLClient`/`createRestClient` не
  передавал ни один потребитель, так что правка никого не сломала, но выпуск всё равно минорный.
- **Реэкспорты вендора типизирует вендор.** `graphqlRequest` и его `requestHeaders` приходят из
  `graphql-request` и по-прежнему объявлены через `HeadersInit` в его собственных `.d.ts` — это
  не ломает серверного потребителя, потому что `skipLibCheck` не проверяет чужие декларации. Свой
  тип мы обещаем за свои сигнатуры, не за вендорские.

Чтобы регресс не вернулся молча, `pnpm typecheck` пакета гоняет второй проект —
`tsconfig.node.json` (только `src/graphql`+`src/rest`, база `@web-core/build/tsconfig-node`).
Проверено на месте: возврат `HeadersInit` в сигнатуру снова даёт `TS2304`, не дожидаясь сборки
чужого пакета.

## defineQuery (эксперимент)

### Почему `defineQuery` принимает `queryKey` и `queryFn` двумя отдельными параметрами, а не одним объектом `{queryKey, queryFn}` — как `createQuery`?

**Коротко: два отдельных `(arg: TArg) => ...`-параметра — потому что при попытке через один
callback, возвращающий `{queryKey, queryFn: () => Promise<TData>}`, TypeScript не выводит
`TData` (падает в `{}`) одновременно с выводом `TArg` из того же callback — независимо от того,
завёрнут ли фетчер в лямбду или передан как есть. Подтверждено изолированным прогоном `tsc` на
трёх вариантах сигнатуры при реализации (2026-09-15).**

С двумя отдельными типизированными параметрами (`queryKey: (arg) => QueryKey`,
`queryFn: (arg) => Promise<TData>`) вывод обоих `TArg`/`TData` работает надёжно — при условии,
что оба параметра реально типизированы (см. следующий вопрос про `vi.fn`).

---

### Почему в тестах `vi.fn().mockResolvedValue(x)` не подходит для `queryFn`, переданного в `defineQuery`?

**Коротко: возвращаемый тип `vi.fn().mockResolvedValue(x)`, при передаче в generic-функцию с
непустым `TArg`, не несёт достаточной информации для вывода `TData` — падает в `{}` независимо
от формы `defineQuery`. С обычной типизированной функцией (`async function fetchX(arg): Promise<T>`
или `vi.fn(async (arg) => x)`) проблема не воспроизводится.**

Проверено изолированными прогонами `tsc` при реализации `test/define.test.tsx` (2026-09-15):
`vi.fn().mockResolvedValue(...)` работает нормально, когда мок передаётся НЕПОСРЕДСТВЕННО в
`createQuery`/`createMutation` (как в `test/query.test.tsx`) — там `TArg` для generic-вывода не
участвует вообще. Проблема проявляется только когда мок проходит через ДОПОЛНИТЕЛЬНЫЙ слой
generic-вывода (как у `defineQuery`, где одновременно выводятся `TData` и `TArg`). Вывод для
всех тестов пакета: если фетчер параметризован и передаётся через собственный generic-хелпер —
типизировать мок реализацией (`vi.fn(async (arg) => x)`), не `.mockResolvedValue`.

---

### Почему опции вендора пробрасываются двумя разными наборами — часть при определении, часть вторым аргументом `.use`, а не одним списком?

**Коротко: у двух путей разные типы опций у самого вендора. `queryClient.query(...)` принимает
`QueryExecuteOptions` — там нет ни `enabled`, ни `placeholderData`, ни `select`: это опции
наблюдателя, а императивный вызов наблюдателя не заводит. Один общий список пришлось бы
приводить типом на входе в `queryClient.query`, то есть прятать факт, что половина опций там не
работает.**

Проверено чтением `@tanstack/query-core@5.102.8/build/modern/hydration-*.d.ts` (2026-09-23):
`QueryClient.query(options: QueryExecuteOptions<…>)`, а `QueryExecuteOptions` расширяет
`QueryOptions` ядра (`staleTime`/`gcTime`/`retry`/`networkMode`/`meta`), не
`QueryObserverOptions`. Отсюда и раскладка: `config` при определении — пересечение, понятное
обоим путям; второй аргумент `.use` — то, что имеет смысл только в реактивном.

Заодно это отвечает на вопрос «почему `enabled` нельзя назвать один раз при определении»: у
императивного пути его нет, а у реактивного он ещё и меняется во времени — см. следующий вопрос.

---

### Почему второй аргумент `.use` — функция, а не объект опций?

**Коротко: `createQuery` вызывает переданный `Accessor` на каждый такт, и реактивная опция обязана
читаться ВНУТРИ него. Объект, собранный на месте вызова `.use`, прочитает сигналы один раз и
замёрзнет — `enabled` навсегда останется тем, чем был в момент монтирования.**

Тот же факт, что уже описан выше про сам `createQuery` (опции — `Accessor` под именем
`UndefinedInitialDataOptions`). Доказано тестом с реальным рендером: сигнал `enabled` `false →
true` отпускает запрос, `queryFn` вызывается ровно один раз (`test/define.test.tsx`).

---

### Почему `initialData` — единственная опция, которая НЕ пробрасывается?

**Коротко: перегрузки `useQuery` делят мир надвое по этому полю — `initialData?: undefined` в
одной и `initialData: TQueryFnData | (() => TQueryFnData)` в другой. Объект, собранный из двух
необязательных источников (`config` + опции `.use`), не принадлежит ни одной: его `initialData`
имеет тип `TData | InitialDataFunction<TData> | undefined`, и компилятор отбивает вызов с
`TS2769: No overload matches this call`.**

Проверено на месте при реализации (2026-09-23): с `initialData` в наборе опций тайпчек пакета
падает именно так; исключение поля из обоих наборов — единственное, что держит остальной проброс
целым без приведения типов. Чем заменить: `placeholderData` (если нужно показать что-то до
резолва) или `queryClient.setQueryData(...)` до вызова (если нужно именно засеять кэш).

---

### Почему `defineQuery` — эксперимент, а не сразу канон, как `createGraphQLClient`/`createRestClient`?

**Коротко: слова user — "я пока делаю апп скин буду юзать это если все полетит то введем
официально". Решает конкретное повторение (несколько запросов вида `presetsClient.list(kind,
filter)` в `apps/skin`), но пока не проверено на реальном разнообразии запросов (`select`,
условный `enabled`, отличный от `staleTime` конфиг) — если разнообразие потребует протаскивать
через `defineQuery` всё больше опций вендора, это сигнал, что механика не годится, и её нужно
откатить, а не разрастить. Первый реальный потребитель — `apps/skin`; статус пересматривается
после того, как он покажет, держится ли форма.**

Пересмотр состоялся 2026-09-23, когда витрина попросила `enabled`/`placeholderData`. Механика
оставлена, статус — по-прежнему эксперимент, и вот на чём это стоит: критерий отката написан про
РАСТУЩИЙ СПИСОК, то есть про перечисление опций по одной, от которого сигнатура пухнет с каждой
заявкой. Опции пробрасываются целиком, типами вендора (`QueryExecuteOptions` и `QueryOptions`
минус ключи запроса) — седьмая опция не добавит ни строки, значит списку расти негде и критерий
к этому случаю не относится. Новый критерий отката уже: если следующая заявка потребует менять
САМУ сигнатуру, а не просто назвать опцию внутри уже пробрасываемого типа. Разбор раскладки
опций — в трёх вопросах выше.
