# 🧪 Примеры — как работать с `@web-core/solid`

Рабочий код, который можно скопировать и сразу погонять. Устройство и решения —
[`README.md`](./README.md) / [`FAQ.md`](./FAQ.md), план — [`ROADMAP.yaml`](./ROADMAP.yaml).

Всё, что ниже, прогнано на коде пакета 2026-09-19.

**Главное деление, из-за которого стоит прочитать словарь первым.** В пакете лежат две разные
вещи, и путать их дорого:

- **Движок** — сам Solid, доехавший сюда без изменений, плюс одно наше добавление (`mountApp`).
  Берёшь его потому, что зонам кита запрещено импортировать `solid-js` напрямую;
- **Примитивы** — механики, которых у Solid нет, взятые готовыми у комьюнити. Сегодня подключён
  ровно один (`./keyed`). Это НЕ «всё, что бывает»: обзор рынка лежит в
  [`PRIMITIVES.md`](./PRIMITIVES.md), и он про то, что **можно** вытянуть, а не про то, что уже
  есть.

<h2 id="словарь">0. Четыре подпути и что за каждым</h2>

Подпуть называет **происхождение** кода — по спецификатору импорта видно, чья это вещь и кто её
чинит.

| Подпуть | Род | Что внутри | Кто сопровождает |
| --- | --- | --- | --- |
| `@web-core/solid` | движок | весь `solid-js` как есть | команда Solid |
| `@web-core/solid/web` | движок | весь `solid-js/web` как есть | команда Solid |
| `@web-core/solid/mount` | наше | `mountApp(root)` — точки входа у Solid нет вовсе | этот пакет |
| `@web-core/solid/keyed` | примитив | весь `@solid-primitives/keyed` | `solidjs-community` |

Правило одной строкой: **зона кита импортирует отсюда, а не из `solid-js`**. Тогда во всех файлах
резолвится один и тот же физический модуль, а версию решают в одном месте, а не в двадцати
`package.json`. Почему так — [`FAQ.md`](./FAQ.md).

<h2 id="кейс-1">1. Точка входа приложения: `mountApp()`</h2>

Единственное место, где это вообще зовётся, — `main.tsx` приложения. Один раз за жизнь проекта.

```tsx
// src/main.tsx
import { mountApp } from "@web-core/solid/mount";

import { App } from "./app";

mountApp(() => <App />);
```

```html
<!-- index.html -->
<div id="root"></div>
```

Три вещи, которые обычно спрашивают:

- **точку монтирования функция ищет сама** — идентификатор не аргумент, поэтому разметку страницы
  можно двигать, не трогая `main.tsx`;
- **наружу не возвращается ничего** (`void`). Ручку уничтожения корня функция держит у себя, по
  узлу-хозяину — отдавать её некому и незачем;
- **нет `#root` — летит `Error` с текстом, что добавить**, а не тихий пустой экран.

Реальный корень приложения обычно обёрнут провайдерами — они монтируются тут же:

```tsx
import { mountApp } from "@web-core/solid/mount";
import { QueryClient, QueryClientProvider } from "@web-core/query";
import { RouterProvider } from "@web-core/router";

import { router } from "./router";

const queryClient = new QueryClient();

mountApp(() => (
  <QueryClientProvider client={queryClient}>
    <RouterProvider router={router} />
  </QueryClientProvider>
));
```

<h2 id="кейс-2">2. Реактивное ядро через фасад</h2>

Импорт один в один с `solid-js`, меняется только спецификатор. Ничего заворачивать не надо —
`createSignal` здесь это тот самый `createSignal`.

```tsx
import { createEffect, createMemo, createSignal, onCleanup, onMount } from "@web-core/solid";

export function Ticker() {
  const [ticks, setTicks] = createSignal(0);
  const label = createMemo(() => (ticks() % 2 === 0 ? "чёт" : "нечет"));

  onMount(() => {
    const id = setInterval(() => setTicks((n) => n + 1), 1000);
    onCleanup(() => clearInterval(id));
  });

  createEffect(() => console.log("тик", ticks(), label()));

  return <span>{ticks()} — {label()}</span>;
}
```

Что отсюда доступно: всё, что есть у `solid-js`, — `createResource`, `createContext`/`useContext`,
`batch`, `untrack`, `For`, `Index`, `Show`, `Switch`/`Match`, `ErrorBoundary`, `Suspense`,
`createUniqueId`, JSX-типы. Реэкспорт полный намеренно: отбор по имени значил бы забыть прокинуть
новое при очередном выпуске Solid.

<h2 id="кейс-3">3. Рендер руками: `render` и `Portal`</h2>

`mountApp()` закрывает обычный случай. Голый `render` нужен, когда корней несколько или хозяина
выбираешь не ты: виджет на чужой странице, стенд, проба в тесте.

```tsx
import { render } from "@web-core/solid/web";

const host = document.querySelector("#widget-slot")!;
const dispose = render(() => <Widget />, host);

// Корень обязан быть уничтожен явно, иначе его вычисления живут дальше.
window.addEventListener("beforeunload", dispose);
```

`Portal` — когда узел обязан оказаться вне своего родителя по DOM, а по реактивности остаться
внутри (модалка, тултип, дроп поверх `overflow: hidden`):

```tsx
import { Show, type JSX } from "@web-core/solid";
import { Portal } from "@web-core/solid/web";

export function Modal(props: { open: boolean; children: JSX.Element }) {
  return (
    <Show when={props.open}>
      <Portal mount={document.body}>
        <div class="backdrop">{props.children}</div>
      </Portal>
    </Show>
  );
}
```

<h2 id="кейс-4">4. Второй `mountApp()` на том же `#root` — HMR и рестарт</h2>

Повторный вызов на том же элементе — это не ошибка и не «второе приложение». Прежний корень
**гасится до** нового рендера:

```tsx
mountApp(() => <span>первый</span>);   // #root: «первый»
mountApp(() => <span>второй</span>);   // #root: «второй», первый корень уничтожен
```

Проверено прогоном: содержимое `#root` заменяется целиком, а компонент первого корня заново не
вызывается — он снят, а не спрятан.

Инвариант простой: **один документ — одно приложение**. Если бы корни складывались стопкой, старые
эффекты продолжали бы реагировать на изменения, до которых новый UI уже не имеет отношения, —
именно так выглядит «после хот-релоада всё стало тормозить и дублировать запросы».

<h2 id="кейс-5">5. `<Key>` вместо `<For>`: узел живёт за ключом</h2>

Список приехал с сервера заново. Объекты в нём **новые**, а `id` те же. Для `<For>` это другие
элементы — он сносит узлы и строит заново, теряя фокус в поле, выделение, открытое состояние
строки. `<Key>` сопоставляет старое и новое по названному ключу:

```tsx
import { Key } from "@web-core/solid/keyed";

<Key each={props.items} by={props.itemKey}>
  {(item) => <Node value={props.itemKey(item())} />}
</Key>;
```

Ключевое про тело: **`item` — сигнал, а не значение**. Узел за ключом остаётся тем же объектом
DOM, а внутрь него приезжает новое значение — поэтому вызывать надо `item()`, и поэтому
деструктурировать аргумент нельзя (реактивность потеряется).

Второй аргумент — тоже сигнал, это индекс:

```tsx
<Key each={rows()} by="id" fallback={<p>Пусто</p>}>
  {(row, index) => (
    <tr data-index={index()}>
      <td>{row().title}</td>
    </tr>
  )}
</Key>
```

Что проверено прогоном (`test/keyed.test.tsx`): после подмены массива новыми объектами с теми же
ключами `querySelector` возвращает **тот же самый** узел, а текст в нём обновлён. На `<For>` этот
же тест падает — в этом вся разница.

Пустой список: `each` принимает `null` и `false`, не только массив, — удобно для `each={ready() &&
rows()}`. На пустом рисуется `fallback`, если он задан, иначе ничего.

<h2 id="кейс-6">6. `by` строкой и `by` функцией</h2>

`by` — это ответ на вопрос «по чему считать, что это тот же элемент».

```tsx
// Ключ лежит полем объекта — короткая форма.
<Key each={users()} by="id">{(user) => <UserCard user={user()} />}</Key>

// Ключ составной или вычисляемый — функция.
<Key each={cells()} by={(cell) => `${cell.row}:${cell.col}`}>
  {(cell) => <Cell value={cell().value} />}
</Key>

// Ключ приходит снаружи — функция пропсом, как в примере из кейса 5.
<Key each={props.items} by={props.itemKey}>{(item) => <Node value={item()} />}</Key>
```

Выбор ключа — решение, а не формальность: **поменялось значение ключа = это другой элемент**, узел
будет снесён и построен заново. Поэтому индекс в массиве ключом не годится (сортировка порвёт всё),
а поле, которое юзер может отредактировать, — годится только если ты правда хочешь пересоздание
строки на такую правку.

<h2 id="кейс-7">7. `keyArray` — то же самое без JSX</h2>

Под `<Key>` лежит обычный реактивный примитив. Он нужен, когда сопоставление по ключу требуется не
для разметки: производные модели, кэш по строке, предвычисленные объекты.

```ts
import { createSignal } from "@web-core/solid";
import { keyArray } from "@web-core/solid/keyed";

type Row = { id: string; title: string };

const [rows, setRows] = createSignal<Row[]>([{ id: "a", title: "первый" }]);

const views = keyArray(
  rows,                                  // Accessor списка
  (row) => row.id,                       // чем опознаём элемент
  (row) => ({                            // row — СИГНАЛ; тело зовётся один раз на ключ
    id: row().id,
    shout: () => row().title.toUpperCase(),
  }),
);

views()[0]!.shout();                     // "ПЕРВЫЙ"
setRows([{ id: "a", title: "первый, но другой объект" }]);
views()[0]!.shout();                     // "ПЕРВЫЙ, НО ДРУГОЙ ОБЪЕКТ" — объект view тот же
```

Проверено прогоном: при подмене объекта с тем же ключом функция сопоставления **не зовётся
второй раз** — переиспользуется уже созданное, меняется только значение внутри сигнала. Ровно это
свойство и даёт `<Key>` его смысл.

Зовётся внутри реактивного владельца (компонент или `createRoot`) — как любой примитив Solid.

<h2 id="кейс-8">8. Обход объекта, `Map` и `Set`</h2>

Три компонента того же пакета для случаев, когда источник не массив. Сигнатура тела у каждого
своя — стоит свериться, а не гадать:

```tsx
import { Entries, MapEntries, SetValues } from "@web-core/solid/keyed";

// Объект: ключ — ОБЫЧНАЯ строка, значение — сигнал.
<Entries of={settings()} fallback={<p>Настроек нет</p>}>
  {(key, value) => <Row label={key} value={value()} />}
</Entries>

// Map: ключ обычный (любого типа), значение — сигнал.
<MapEntries of={cache()}>
  {(key, value, index) => <Row index={index()} label={String(key)} value={value()} />}
</MapEntries>

// Set: значение обычное, сигнал только индекс — у множества менять значение негде.
<SetValues of={tags()}>{(tag) => <Tag name={tag} />}</SetValues>
```

Запомнить проще так: **сигналом приходит то, что может измениться, не меняя тождества элемента.**
У объекта и `Map` это значение под ключом; у `Set` значение и есть ключ, поэтому оно обычное.

Все три принимают `undefined`/`null`/`false` в `of` и рисуют на них `fallback`.

<h2 id="кейс-9">9. `<Rerun>` — перестроить кусок по триггеру</h2>

Обратная задача: не «сохрани узлы», а «снеси и построй заново, когда изменилось вот это». Нужно
для некооперативных вещей — сторонний виджет, `<canvas>`, компонент с неуправляемым внутренним
состоянием, который проще пересоздать, чем синхронизировать.

```tsx
import { createSignal } from "@web-core/solid";
import { Rerun } from "@web-core/solid/keyed";

const [theme, setTheme] = createSignal("dark");

<Rerun on={theme}>
  {(now, was) => {
    console.log("перестроились", was, "→", now);
    return <ThirdPartyChart theme={now} />;
  }}
</Rerun>;
```

Тело получает **новое значение и предыдущее** (`undefined` на первом проходе) — проверено прогоном.
`on` принимает аксессор, массив аксессоров (`on={[theme, locale]}`) или просто значение. Телом
может быть и не функция, а сразу JSX, если предыдущее значение не нужно.

<h2 id="кейс-10">10. `<For>` / `<Index>` / `<Key>` — что когда</h2>

| Берём | Элемент опознаётся | Сигналом приходит | Когда это правильный выбор |
| --- | --- | --- | --- |
| `<For>` | по **ссылке** на объект | индекс | список живёт в сторе и мутируется на месте; объекты стабильны |
| `<Index>` | по **позиции** | значение | позиция и есть смысл: нумерованные слоты, фиксированная сетка, список примитивов |
| `<Key>` | по **названному ключу** | значение и индекс | список перестраивается новыми объектами: ответ сервера, `JSON.parse`, пересборка из другого источника |

Практический признак, что нужен именно `<Key>`: **после обновления списка пропадает фокус, слетает
выделение или схлопывается раскрытая строка**, хотя данные почти те же. Это `<For>` не узнал
элементы, потому что объекты новые.

Обратный признак — `<Key>` не нужен: список приходит из стора, где элементы правят на месте. Тогда
`<For>` дешевле, а ключа просто нет.

`<For>` и `<Index>` берутся из барели движка (`@web-core/solid`), `<Key>` — из `./keyed`. Разные
подпути, потому что разное происхождение, а не потому что разное назначение.

<h2 id="кейс-11">11. «Реактивность не работает» — почти всегда условия резолва</h2>

Симптом: в тесте или в ноде компонент рендерится один раз и больше не обновляется, сигналы вроде бы
меняются, а DOM стоит. Причина не в коде — `solid-js/web` отдаёт **серверную** сборку, если условия
резолва не названы: там рендер разовый по определению.

Лечится в конфиге прогона, а не в компоненте:

```ts
// vitest.config.ts
import solid from "vite-plugin-solid";
import { defineConfig } from "vitest/config";

export default defineConfig({
  test: {
    projects: [
      {
        plugins: [solid()],
        resolve: { conditions: ["development", "browser"] },
        test: {
          environment: "jsdom",
          include: ["test/*.test.tsx"],
        },
      },
    ],
  },
});
```

Ровно этот конфиг лежит в пакете — с него можно списывать. Вторая частая причина того же симптома —
**деструктуризация**: `{(item) => …}` отдаёт сигнал, и `const { title } = item()` читает значение
один раз, навсегда. Читать надо в том месте, где значение используется.

<h2 id="кейс-12">12. Чего здесь нет и где это искать</h2>

- **`Key` нет в барели `@web-core/solid`** — и не будет: барель дословно зеркалит `solid-js`, а
  `Key` не оттуда. Импорт из `./keyed`, всегда.
- **Прямой `import … from "solid-js"` в зоне кита — не «тоже вариант», а то, ради отмены чего
  пакет существует.** Сегодня часть зон так ещё импортирует; это известный долг
  (`ROADMAP.yaml`, `id: migrate-direct-solid-imports`), а не образец.
- **Остальные примитивы комьюнити НЕ подключены.** [`PRIMITIVES.md`](./PRIMITIVES.md) — это обзор
  рынка: что существует и что можно было бы вытянуть. Из всего списка у нас живёт один `keyed`.
  Нужен ещё один — это заявка архитектору, а не `pnpm add` в своей зоне: зависимость в поставку
  решает он.
- **Роутинг, запросы, стор, стили** — отдельные пакеты кита (`@web-core/router`, `@web-core/query`,
  `@web-core/store`, `@web-core/style`). Здесь только сам Solid и то, что достроено вокруг него.
