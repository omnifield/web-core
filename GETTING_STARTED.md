<h2 id="быстрый-старт">⚡ Быстрый старт</h2>

Репозиторий рассчитан на **Dev Containers** (`.devcontainer/devcontainer.json`) — стандартный
образ `mcr.microsoft.com/devcontainers/typescript-node:24`, без самописных скриптов поверх.
Открыть в VS Code / Claude Code с поддержкой Dev Containers — окружение поднимется само
(включая `corepack`, который фиксирует версию `pnpm` ровно по пину репозитория).

Без контейнера — вручную:

```bash
corepack enable          # версия pnpm — из package.json/packageManager
pnpm install             # пакеты берут друг друга через workspace:*, не npm-реестром
```

Node 24, `pnpm 11` (см. `package.json`).

<h2 id="приложения">🖥️ Как запускать приложения</h2>

| приложение  | назначение                                                                    | dev-команда                                       |
| ----------- | ------------------------------------------------------------------------------ | -------------------------------------------------- |
| `studio`    | 🎨 витрина компонентов кита и скинов — эталон `genus: app`                     | `pnpm --filter @web-core/studio dev` → `:5174`     |
| `reference` | 🚨 эталонное приложение — гейт сборки цепочки зон, падает при поломанном шве   | `pnpm --filter @web-core/reference dev`            |

Общие команды по всему монорепо (гоняют цель по всем `@web-core/*` через Nx):

```bash
pnpm dev         # dev-таргет всех пакетов/приложений параллельно
pnpm build       # сборка
pnpm test        # vitest
pnpm lint        # eslint + typecheck
pnpm typecheck   # только tsc
pnpm graph       # граф зависимостей Nx в браузере
```

Один пакет/приложение — через `--filter`: `pnpm --filter @web-core/studio test`.

<h2 id="синк">🔁 Синк во внешние репозитории</h2>

`scripts/sync-repo.sh` — squash-синк текущей ветки в конфигурируемый внешний репозиторий
(например, при выносе продукта из монорепо). Цели — в `sync-targets.yaml` (`url`/`branch`/`source`
на каждую).

```bash
./scripts/sync-repo.sh --list                       # показать цели из sync-targets.yaml
./scripts/sync-repo.sh <target> [--message "текст"] [--force]
```

- Работает в изолированном temp-`worktree` — сеть/прерывание не может застрять в основном
  checkout.
- Если ветки `branch` на цели ещё нет — создаёт её (orphan-ветка от `source`).
- `--force` — перезаписать содержимое ветки цели содержимым `source` целиком: без
  `merge --squash`, без конфликтов (удалённая история отбрасывается).

<h2 id="агенты">🤖 Как работать с агентами</h2>

Репозиторий работает на **agent-harness** (Claude Code): роль сессии задаётся переменной
`WEBCORE_SCOPE` при старте, конфиг ролей и границ — `.claude/harness.yaml`, тексты ролей —
`.claude/agents/*.md`.

**Правила работы агент читает сам — из [`CLAUDE.md`](./CLAUDE.md)**: этот файл (и его короткие
копии в корне каждого скоупа) харнесс кладёт в контекст автоматически, в отличие от остальной
доки, которую сессия открывает только по своему решению. Поэтому всё, что агент обязан знать
до первого действия, живёт там, а не здесь.

Кто ты в открытой сессии — видно **в строке состояния внизу экрана** (`🏛 architect` /
`🔧 owner-<zone>` + зона, ветка, модель): при нескольких открытых сессиях это единственный
способ не перепутать, с кем говоришь, не листая переписку.

**Роли:**

| роль | что делает | файлы | git |
| --- | --- | --- | --- |
| `architect` (`main`) | триаж, контракты/ADR, ставит ТЗ владельцам зон задачами в трекере, ревьюит, **владеет доставкой** | всё, что не отдано зоне | заводит ветку → PR → **вливает только он** |
| `owner-<zone>` | полный lifecycle своей зоны: код + тесты + трейсы + доки | только свои `paths[]` из `harness.yaml` | commit-only, в ветку, которую завёл architect |
| `layer` | один типовой артефакт по узкому промпту | по промпту | не трогает git |
| `research` / `routine` | помощники внутри роль-сессии (read-only / правки в границах родителя) — не отдельные роли | границы родителя | как у родителя |

**Ключевые правила** (полностью — `.claude/agents/shared-policy.md`):

- **Границу зон держит машина**, не договорённость: `governance.mjs` физически блокирует
  `Edit`/`Write` вне `paths[]` зоны — обход (симлинк, относительный путь) бесполезен.
- **architect не пишет код зон** — ставит задачу владельцу зоны; владелец не заводит свою
  ветку и не пушит/вливает сам.
- **Роль-сессии друг друга не вызывают.** Маршрутизатор между architect и owner — человек
  (user): architect говорит user'у, кого поднять и с каким ТЗ.
- **Истина — в трекере продукта**, не в файлах репозитория. Какой это трекер — решает
  продукт; `briefs/`-файлов в репозитории не заводим — вторая копия ТЗ молча расходится с
  первой.
- **Коммит ограничен зоной так же, как правка.** `git-gate` считает, что реально попадёт в
  коммит (индекс, `-a`, явный pathspec), и отбивает чужие файлы: в общем working tree
  `git add .` иначе уносит незакоммиченную работу соседей в чужой коммит.
- Модели закреплены за ролями алиасами в `harness.yaml` (`models:`): `architect` →
  `claude-opus-5`, `owner` → `claude-opus-5`, `layer` → `claude-haiku-4-5`.

**MCP-серверы, доступные агенту в этом репозитории** (`.mcp.json`):

- **Windshift** — self-hosted трекер работы (роадмапы, задачи, страницы дока) как тул агента.
  Боевой адрес — `https://150.251.145.87:9443/mcp` (он же `WINDSHIFT_URL` в `.env`); сервер
  `windshift-local` — тот же продукт на `localhost:7777` для разработки самого
  `products/windshift`, к работе по задачам отношения не имеет.
- **Ark UI** — доки/примеры/пропсы компонентов Ark UI прямо в сессии.
- **Chrome DevTools** — управление браузером для живой проверки UI.
- **skin** — MCP зоны `skin` (`apps/studio/.mcp`), работа со скинами кита.
