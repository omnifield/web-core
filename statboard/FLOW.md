<h2 id="паспорт">🪪 Паспорт проекта</h2>

Род проекта, метки и список целей читаются одной командой — не глазами по конфигам:

```bash
pnpm exec nx show project statboard --json
```

Что оттуда брать:

| Поле | Значение | Что означает |
|---|---|---|
| `projectType` | `application` | это приложение: его разворачивают, а не публикуют в реестр |
| `tags` | `type:app`, `deploy:static`, `npm:private` | статика; в реестр не уезжает |
| `metadata.js.packageVersion` | версия | метка выкатки, ею и различают сборки |
| `targets` | цели | что можно запустить |
| `targets.build.outputs` | `dist` | откуда забирать собранное |

📌 Имена целей — часть контракта: `lint`, `typecheck`, `test`, `build`. Они не переименовываются,
на них можно ссылаться из своих сценариев.

<h2 id="нужно">🔑 Что нужно подготовить</h2>

| | |
|---|---|
| Node | версия объявлена в `package.json` (`engines`) |
| pnpm | версия объявлена там же (`packageManager`); `corepack enable` берёт её оттуда |
| Сеть | доступ к реестру пакетов `@web-core/*` — адрес лежит в `.npmrc` |
| Токен | **не нужен**: пакеты отдаются на чтение анонимно |

Установка:

```bash
corepack enable
pnpm install --frozen-lockfile
```

⚠️ Менеджер пакетов держит карантин на свежие публикации: версия моложе суток по умолчанию не
резолвится. При установке по зафиксированному состоянию (`--frozen-lockfile`) это не мешает —
версии уже выбраны. А вот обновление зависимостей сразу после публикации новой версии пакета
выглядит как «версии нет»: подождите сутки либо добавьте её в `minimumReleaseAgeExclude`.

<h2 id="команды">🚀 Команды</h2>

Любую цель можно звать через граф задач (с кэшем) или напрямую скриптом — результат один:

```bash
pnpm exec nx run statboard:build    # с кэшем
pnpm build                          # без кэша
```

| Цель | Что делает | Код возврата | Что оставляет |
|---|---|---|---|
| `lint` | проверка правил | `0` — чисто, `1` — есть замечания | ничего |
| `typecheck` | проверка типов | `0` — чисто, иначе отказ | ничего |
| `test` | прогон тестов | `0` — все прошли, иначе отказ | ничего |
| `build` | сборка приложения | `0` — собрано | `dist/` |
| `dev` | сервер разработки на порту `5175` | — | ничего |
| `preview` | отдача уже собранного `dist/` на том же порту | — | ничего |

Все четыре проверки одним прогоном:

```bash
pnpm exec nx run-many -t lint typecheck test build
```

♻️ Результат целей кэшируется: повторный прогон без изменений не считает заново. Кэш локальный, в
`.nx/`, и в репозиторий не едет. Нужен честный прогон — ключ `--skip-nx-cache`.

⚠️ Порт `5175` занят — сервер **падает**, а не занимает соседний. Это сделано нарочно: иначе
проверка идёт не на том приложении.

<h2 id="артефакт">📦 Артефакт</h2>

`build` кладёт собранную статику в `dist/`: обычный набор файлов для статического хостинга, ничего
кроме отдачи файлов ему не нужно. Что с ним делать дальше — контейнер, машина, домены, кэширующий
слой — решается на вашей стороне, репозиторий об этом ничего не знает и знать не должен.

Проверить, что собралось, не разворачивая никуда: `pnpm preview`.

<h2 id="выпуск">🏷️ Выпуск</h2>

Версию поднимает граф задач, считая её по истории коммитов (`feat` → минорная, `fix` → патч):

```bash
pnpm exec nx release --dry-run   # посчитать и ничего не записать
pnpm exec nx release             # версия, CHANGELOG.md, коммит, тег
git push --follow-tags
```

Публикации в реестр нет — приложение туда не едет, **результат выпуска это тег**. Отдельного ключа
для пропуска публикации не нужно: команда сама её не делает.

🔎 Если с прошлого тега не было ни одного значимого коммита, выпуск честно отвечает, что менять
нечего, и ничего не пишет.

<h2 id="нет">🚪 Чего здесь нет</h2>

- **Файлов сборочного конвейера.** Сценарий пишется под конкретную платформу и живёт на вашей
  стороне — мы даём команды, а не готовые пайплайны.
- **Образа контейнера и раскладки.** См. «Артефакт».
- **Не хватило команды?** Это не повод обходить её через правку исходников — скажите, какая
  нужна, и она появится здесь же, рядом с остальными.
