# `entities` — структурная модель движка (слой FSD, адаптированный)

## Место в иерархии

Порядок слоёв сверху вниз в этом пакете: `widgets → features → entities`.
`entities` — самый нижний из заведённых слоёв: выше него `features`, `widgets`; ниже —
только внешние пакеты (`shared` в этом пакете пока не заведён, см. [`../DBP.md`](../DBP.md)).

## Чем это отличается от `entities` в бизнес-приложении

В каноне FSD `entities` — бизнес-сущность (`user`, `order`). Здесь — НЕ бизнес-сущность:
`entities` даёт структурную модель самого движка, то, ЧЕМ мод оперирует технически. Примеры из
этого пакета:

- `entities/tree` — модель узла дерева (`FieldBinding`, `useTree`): как читать/писать значение
  по пути внутри произвольной зод-схемы, без знания, ЧТО это за схема с точки зрения бизнеса.
- `entities/openapi` — структура распознанного Swagger 2.0 (`OpenapiEndpoint`) и схема A
  (`EndpointDescriptor` под ручной ввод ручки без документа-источника) — форма API-ручки, не
  бизнес-домен, к которому эта ручка относится.
- `entities/mapping` — `describeVariant`/`applyMapping`, тонкая обёртка над `@web-core/io`:
  форма "варианта" (сырые данные или зод-схема) для сведения полей, а не сами сведённые данные.

Проверка "моё ли это" та же, что и в бизнес-приложении, просто с другим словарём: сущность даёт
чистые прозрачные методы (распознать, достать, сопоставить, простая трансформация) — «россыпь»
примитивов формы данных мода, а не готовый сценарий работы с ними. Внутри себя сущность НИЧЕГО
не строит: ни композиций UI, ни цепочек из нескольких своих же методов, ни выбора, что показать
пользователю — это работа `features`/`widgets`, не её. Сущность не знает, в каком моде и рядом с
чем её используют — это забота слоёв выше.

`ui/`-сегмент сущности (пример — `entities/openapi/ui/endpoint.tsx`) — тот же принцип, только
для разметки: один базовый, самостоятельный кусок отображения БЕЗ сборки нескольких таких кусков
в поток с логикой. Как только кусок начинает решать, в каком порядке вызвать несколько методов
сущности или что показать вместо чего — он вырос из `entities` и переезжает в `features`/
`widgets`.

## Правило импортов

- `entities` импортирует только внешние пакеты (`@web-core/*`, `zod`, `solid-js` и т.д.) —
  `shared` в этом пакете пока не заведён (см. [`../DBP.md`](../DBP.md)).
- НЕ импортирует `features`/`widgets` — оба лежат выше. Если сущности "хочется" знать про
  конкретный мод или конкретный UI-компонент, который её показывает — это инверсия
  зависимости, сигнал, что код лежит не на том слое.

## Слайсы — вертикальный разрез по моду, не по типу файла

Один слайс = один мод наполнения (`tree`, `openapi`, `mapping`). Внутри слайса — сегменты по
ТЕХНИЧЕСКОЙ роли:
- `ui/` (или `models/ui`) — компоненты базового отображения структуры мода.
- `models/`/файлы верхнего уровня слайса — структура, типы, чистая логика распознавания/
  сведения (без разметки).

Правило "один слайс = один мод" даёт **cohesion**: слайс меняется по ОДНОЙ причине. Если слайс
параллельно знает детали структуры ДВУХ разных модов, он начинает меняться по причинам, не
относящимся к его прямой задаче — это и есть потеря связности, ради недопущения которой
методология и разделяет слайсы.

## Слайсы одного слоя не видят друг друга напрямую

Ключевое свойство FSD, ради которого всё затевалось: изоляция слайсов на одном уровне даёт
стабильность при рефакторинге — переписал структуру одного мода, соседний физически не мог
залезть в его внутренности и не сломался. Если двум модам регулярно нужны детали структуры друг
друга — это повод пересмотреть границу (может, общая часть на самом деле принадлежит будущему
`shared`), а не заводить cross-import как способ "быстро заработало".

## Public API

Наружу слайса — только `index.ts`. Всё остальное (`models/*.ts` напрямую, `ui/*.tsx` без
реэкспорта из корневого `index.ts`) — внутренности, снаружи трогать нельзя. Прямой импорт во
внутренности: (а) ломает гарантию "остальной пакет не знает о структуре слайса" — рефакторинг
ВНУТРИ одного слайса не должен требовать правок по всему дереву; (б) плодит циклические
зависимости; (в) тащит наружу вес, который не предполагался публичным.

Это правило действует и ВНУТРИ одного слайса, если он расширяется несколькими близкими
поддоменами (пример — `entities/openapi/models` с подпапкой `swagger/` под парсинг конкретно
Swagger 2.0): каждый поддомен получает свою папку с тонким `index.ts`, сосед вызывает функцию
соседнего поддомена через его `index.ts`, а не напрямую через внутренний файл.
