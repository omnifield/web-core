# `widgets` — сборка мода целиком (слой FSD, адаптированный)

## Место в иерархии

Порядок слоёв сверху вниз в этом пакете: `widgets → features → entities`.
`widgets` — самый верхний из заведённых слоёв: выше него ничего (пакет не собирает "приложение"
из виджетов, см. [`../DBP.md`](../DBP.md)); ниже — `features` и `entities`.

## Что кладётся сюда

Виджет — публичный компонент одного МОДА наполнения целиком: `Tree` (мод 1), `OpenapiEditor`/
`OpenapiList` (мод 2), `Mapping` (мод 4). Он собирает `entities` (структуру) и `features`
(действия интерфейса) в готовый, полностью контролируемый снаружи компонент — это и есть та
"сборка", ради которой существует отдельный слой, а не просто россыпь примитивов.

Три вещи, которые здесь происходят одновременно, — не взаимоисключающие роли, а слои одной
задачи:
- **Обход структуры.** `widgets/tree` рекурсивно обходит `FieldDescriptor[]` из
  `entities/tree`/`@web-core/generators/fields`, рендеря `Node`/`Leaf` на каждый уровень
  вложенности.
- **Монтаж действий.** На каждый лист/карточку монтируется соответствующая фича —
  `Button`/`*Input` из `features/edit-value` на скаляр дерева, `invokeEndpoint` из
  `features/invoke-endpoint` на кнопку вызова карточки ручки.
- **Локальное состояние сборки, не самого значения.** `OpenapiEditor` держит форму "добавить
  группу" (имя+вид, до нажатия кнопки), `EndpointCard` — локальный `value`/`status` вызова.
  Значение и структура (то, ЧТО показывается) остаются полностью контролируемыми снаружи —
  `schema`/`value`/`onChange`, `groups`/`onGroupsChange` — см. `README.md`, разделы "Настройки"/
  "Состояния".

## Чем правило импортов ОТЛИЧАЕТСЯ от канона FSD-приложения — и почему

В бизнес-приложении (см. `apps/studio/src/widgets/DBP.md`) виджет НЕ импортирует `entities`:
ему не положено знать форму бизнес-данных, только нейтральные типы через пропсы — иначе виджет
незаметно срастается с конкретной бизнес-сущностью и теряет переиспользуемость.

Здесь это правило снято осознанно (решение зафиксировано в `ROADMAP.yaml`,
`fsd-layers-adapted`, 2026-09-14) — по той же причине, по которой `entities` в этом пакете не
бизнес-сущность (см. [`../entities/DBP.md`](../entities/DBP.md)): виджет мода И ЕСТЬ механизм,
который умеет рендерить и редактировать конкретно ЭТУ структуру (`FieldBinding`,
`OpenapiEndpoint`, вариант сведения). Спрятать эту зависимость за нейтральным пропом было бы не
изоляцией, а фиктивной абстракцией поверх единственного реального случая использования — виджет
"дерево" без знания формы узла дерева не может обойти узел дерева.

- `widgets` импортирует из `features`, `entities` и внешних пакетов.
- НЕ импортирует другой слайс `widgets` напрямую в обход `entities`/`features` (см. "Слайсы"
  ниже) и не импортирует ничего, что физически не существует в этом пакете (`app`/`pages`/
  `shared` — см. [`../DBP.md`](../DBP.md)).

Если в будущем в `entities` появится код, который ДЕЙСТВИТЕЛЬНО является нейтральной нижней
инфраструктурой без знания о конкретной структуре мода — по определению `entities` из
[`../entities/DBP.md`](../entities/DBP.md) ему место в `shared`, не в `entities`, и уже тогда
вопрос "виджет знает форму `shared`" не встанет — `shared` по определению не несёт формы,
специфичной ни одному моду.

## Слайсы и переиспользование частей между ними

Один слайс `widgets` — один мод наполнения. В отличие от строгой изоляции слайсов на нижних
слоях, `widgets`-слайсы в этом пакете переиспользуют части друг друга напрямую, когда один мод
физически построен НАД структурой другого — пример: `widgets/openapi` (мод 2) переиспользует
`Node`/`Leaf`/`Box` из `widgets/tree` (мод 1) для конфигурации параметров одной ручки и для
редактирования дескрипторов группы-юзера (`Tree` рендерит `manualGroupSchema` — зод-схему
дескриптора ручки, это тот же общий движок дерева, не копия). Это не нарушение изоляции —
аналог "виджета-надстройки" из канона FSD-приложения (см. `apps/studio/src/widgets/DBP.md`,
раздел "Виджеты друг друга не импортируют"): если убрать импорт `widgets/tree` из
`widgets/openapi`, перестаёт существовать сам способ показать и отредактировать параметры ручки
— значит это законная зависимость по роли, а не утечка.

Если двум модам нужен общий код БЕЗ такой прямой зависимости по роли — он относится либо к
`entities` (общая структура), либо к будущему `shared` (техническая утилита), а не расшаривается
произвольным cross-import между виджетами.

## Public API

Наружу слайса — только `index.ts`/`index.tsx`, как и на любом другом слое (см.
[`../DBP.md`](../DBP.md)). Один слайс может расширяться несколькими техническими сегментами
(пример — `widgets/openapi/groups/` под виды групп редактора), между которыми делить код можно
свободнее, чем между разными слайсами — но публичный вход у слайса всё равно один.
