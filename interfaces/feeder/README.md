<h2 id="главное">🏠 Главное</h2>

⚡ Первая сущность корня `interfaces/` — слоя между `packages/` (кирпичи) и `apps/` (поверхности):
сущность здесь сводит функционал нескольких пакетов фреймворка и накладывает на него UI, а
пользуется результатом больше чем одно приложение. `interfaces/chat` — второй ожидаемый кейс этого
же слоя, ещё не заведён.

🍽️ Feeder отвечает на один вопрос целиком: **откуда компонент берёт данные и как чужой ответ
становится его формой**. Обе половины пути собраны:

1. **принять описание API** — загрузить документ Swagger 2.0 или завести ручки руками, получить
   именованный пресет;
2. **показать и поправить состав** — группы, ручки, параметры;
3. **дёрнуть ручку** — форма параметров по схеме, живой HTTP-вызов, ответ наружу диспатчем;
4. **свести поля** — мастер сведения: слева слоты формы потребителя, справа поля живого ответа,
   связь ставится переносом;
5. **накормить потребителя** — найти адаптер пары «поставщик + потребитель», прогнать ответ и
   отдать готовый объект нужной формы.

🧪 Живьём в браузере проверен мастер сведения (перенос, состояния слота, цвета типов); остальное —
vitest+jsdom.

<h2 id="анатомия">🧩 Анатомия</h2>

🗺️ Один вход, без подпутей: `@web-core/feeder`.

| Часть | Экспортирует | Про что |
| --- | --- | --- |
| Загрузка | `ExternalSchemaLoader` | принять документ файлом или вставкой, разобрать, положить пресетом |
| Каталог | `ApiCatalog`, `ApiProbe`, `Endpoints` | состав API: группы → ручки → параметры; `ApiCatalog` правит состав, `ApiProbe` показывает только связанное с потребителем и кормит его |
| Вызов | `Endpoint`, `Call`, `useInvoke`, `invokeEndpoint`, `serve` | форма параметров, один HTTP-вызов, ответ; `serve` вдобавок кормит потребителя |
| Склад | `presetsStore`, `Presets`, `PresetInfo`, `recordsOf` | именованные пользовательские записи, отбор по виду, выдача записей приведёнными |
| Модель API | `API_KIND`, `parseSchema`, `asSchemaDocument`, `endpointOf`, `groupEndpoints`, `schemaNodeToZod` | наш формат документа и работа с ним |
| Конфиг узла | `ENDPOINT_CONFIG`, `GROUP_CONFIG`, `PRESET_CONFIG`, `endpointConfigOf`, `groupConfigOf`, `presetConfigOf` | зод-схема и значение формы для узла: ручки, группы, записи склада |
| Форма | `TreeForm` | дерево по произвольной зод-схеме |
| Сведение | `AdapterMastering` | мастер: слоты выхода принимают поля входа переносом |
| Адаптер | `ADAPTER_KIND`, `asAdapter`, `applyAdapter`, `feed`, `isFed`, `noFeed` | запись шва и работа с ней |
| Пользователи адаптера | `API_USER`, `defineUserKind`, `userKinds`, `userKindOf`, `usedBy`, `usersOf`, `adapterFor`, `partnersOf`, `savedAdapters` | кто кормит и кого кормят: объявление вида, адреса, поиск, готовый список записей |
| Типы | `Preset`, `PresetsState`, `PresetConfig`, `SchemaDocument`, `SchemaNode`, `EndpointDescriptor`, `EndpointParam`, `EndpointConfig`, `Group`, `GroupConfig`, `EndpointGroup`, `ConfigTarget`, `HttpMethod`, `ParamIn`, `OpenapiEndpoint`, `InvokeResult`, `Invocation`, `ApiCatalogResult`, `ApiProbeResult`, `Serving`, `Users`, `Record`, `Adapter`, `AdapterRule`, `UserTree`, `UserKind`, `UserPath`, `FeedResult` | |

📦 Внутри — адаптированный FSD, переосмысленный под движок (правила слоёв — [`src/DBP.md`](./src/DBP.md)):

- `entities/preset` — склад: `Preset { id, kind, name, content }`, стор и механика показа записей
  своего вида. Про содержимое `content` не знает ничего, а `kind` сравнивает, но не толкует;
- `entities/openapi` — наш формат API: `SchemaDocument { endpoints, groups, defs }`, распознавание
  Swagger 2.0 (`swagger2Template` поверх `@web-core/generators/mapping`), простановка айди ручкам
  и сборка групп из тегов документа (`identify`), JSON Schema → zod (`schemaNodeToZod`),
  компоновка ручек по группам, правки состава, примитивы вызова;
- `entities/form` — движок дерева по зод-схеме (`Tree`, `useTree`, `itemBinding`, kit инпутов);
- `entities/adapter` — шов «поставщик → потребитель»: запись `Adapter`, её страж, правки над
  черновиком, совместимость типов (`fitOf`), сборка ответа в форму потребителя (`feed`), реестр
  видов участника и блоки мастера (`OutputSlots`, `InputFields`);
- `features/external-schema` — экран загрузки документа;
- `features/api-manager` — каталог пресетов-схем (`ApiCatalog`), его смотровой вариант (`ApiProbe`),
  узел ручки (`Endpoint` = форма настройки `Config` + вызов `Call`), вызов с кормлением (`serve`) и
  объявление вида участника `api` (`API_USER`);
- `features/adapter-manager` — мастер сведения: `Mastering` (контролируемый, про склад не знает) и
  `AdapterMastering` (находит запись пары и правит её);
- `features/tree-form` — `TreeForm`, интерфейсная обёртка над `entities/form`;
- `shared/ui` — обвязка без знания о предмете: `Box` (аккордеон-узел со своими действиями) и
  `RawLoader` (файл или вставка → сырой текст);
- `shared/dnd` — перенос на `@atlaskit/pragmatic-drag-and-drop`: `dragSource`, `dropTarget`,
  `useDragging`. Про адаптер не знает, наружу пакета не отдаётся.

Почему склад не знает про ручки, а `entities/openapi` — про склад: это два независимых предмета,
и сводит их фича. Разбор — `FAQ.md`, «Пресет как склад».

<h2 id="использование">🚀 Использование</h2>

✅ Экран настройки API — два компонента:

```tsx
import { ApiCatalog, ExternalSchemaLoader } from "@web-core/feeder";

<>
  <ExternalSchemaLoader />
  <ApiCatalog onResult={(event) => setProbe(event)} />
</>;
```

✅ Мастер сведения — слева форма потребителя, справа поля живого ответа:

```tsx
import { AdapterMastering, API_USER, defineUserKind } from "@web-core/feeder";
import { describeSample, describeSchema } from "@web-core/io";

const COMPONENT_USER = defineUserKind("component", (name: string) => [name]);

<AdapterMastering
  provider={API_USER.path(presetId, endpointId)}
  consumer={COMPONENT_USER.path("user-card")}
  output={describeSchema(consumerSchema)}
  input={describeSample(response)}
/>;
```

Связи хранит запись адаптера на складе: мастер сам находит её по паре адресов, а при первой связи
заводит. Пока ничего не перетащили — записи нет.

✅ Витрина потребителя — только связанные с ним ручки, и сразу с едой:

```tsx
import { ApiProbe } from "@web-core/feeder";

<ApiProbe
  consumer={COMPONENT_USER.path("user-card")}
  onServing={(event) => board.put(event.serving.data)}
/>;
```

Каталог сам спрашивает `partnersOf`, кто связан с этим потребителем, и показывает только эти
схемы и ручки. Вызов идёт через `serve`, поэтому наружу едет не сырой ответ, а конверт: оригинал,
собранные данные и отчёт.

✅ Дёрнуть ручку и сразу получить еду для потребителя:

```ts
import { serve } from "@web-core/feeder";

const shot = await serve(endpoint, { limit: 10 }, { provider, consumer });

shot.result; // оригинал ответа целиком: status, ok, headers, body
shot.data;   // объект формы потребителя — undefined, если адаптера пары нет
shot.report; // что сошлось, что нет
```

✅ Кто с кем связан:

```ts
import { partnersOf, savedAdapters } from "@web-core/feeder";

const adapters = savedAdapters().map((one) => one.content);

partnersOf(adapters, "consumers", COMPONENT_USER.path("user-card")); // какие ручки кормят карточку
partnersOf(adapters, "providers", API_USER.path(presetId, endpointId)); // кого кормит ручка
```

Доставать записи со склада руками не нужно: `savedAdapters()` отдаёт их уже приведёнными стражем,
вместе с пресетом, в котором они лежат.

✅ Форма по любой зод-схеме:

```tsx
import { TreeForm } from "@web-core/feeder";

<TreeForm schema={schema} value={value()} onChange={setValue} />;
```

Все сценарии по шагам — [`EXAMPLES.md`](./EXAMPLES.md).

<h2 id="настройки">🎚️ Настройки</h2>

🔧 `ExternalSchemaLoader` — **без пропов**: работает с общим стором пресетов. `ApiCatalog` оттуда же
берёт состав и принимает один необязательный проп — `onResult`
(`ApiCatalogResult { presetId, endpoint, result }`). `ApiProbe` устроен иначе: он принимает
`consumer` (адрес потребителя) и необязательный `onServing`, состав не правит вовсе (ни
«Добавить», ни «Убрать», ни «Настроить») и показывает только то, что связано с этим потребителем —
схемы без связанных ручек не рисуются, а когда связей нет вовсе, он говорит это словами.

Состав `ApiCatalog` правит сам, через склад: «+» на схеме заводит пустую группу, «+» на группе —
пустую ручку под ней, корзина убирает схему, группу (со всеми её ручками) или одну ручку. У самой
ручки «+» нет — глубже заводить нечего. Правка самого узла — диалогом «Настроить».

`Endpoints` — `document: SchemaDocument`, необязательный `label` и набор колбэков: `onAddGroup`,
`onRemove`, `onAddEndpoint(group)`, `onRemoveGroup(group)`, `onRemoveEndpoint(endpoint)` и
`onConfig(target)`. Кнопки появляются **от самого колбэка** — не передали, кнопки нет.

`AdapterMastering` — `provider`, `consumer` (адреса участников), `output`, `input`
(`PathType[]` из `@web-core/io`) и необязательное `name` для новой записи (по умолчанию имя
собирается из адресов: `user-card ← endpoint-3`).

`Presets` — механика склада: `kind`, `as` (страж содержимого), необязательные `empty`/`broken` и
обязательный `children`.

`Endpoint` — `endpoint: EndpointDescriptor`, `defs`, необязательные `users`, `onResult` и
`onServing`. `Call` — то же плюс `value`. Передали `users` — вызов идёт через `serve` и наружу
едет конверт `Serving`; не передали — как раньше, сырой `InvokeResult`. `PresetInfo` — `name` / `onName`.
`TreeForm` — `schema: z.ZodType`, `value`, `onChange`.

Чего у движка **нет**: форматов кроме Swagger 2.0; заголовков и авторизации у вызова; хранения
между сессиями; пагинации (её параметры приезжают обычными параметрами ручки); выбора корня записей
на экране — `root` у адаптера пока всегда пустой.

<h2 id="состояния">🎛️ Состояния</h2>

🚦 Пакет держит одно живое состояние в сторе, остальное контролируется снаружи.

- `presetsStore` — `{ presets: Preset[] }`, модульный синглтон (`createActionStore`
  из `@web-core/store`). Действия: `add(kind, name, content) → id`, `remove(id)`,
  `rename(id, name)`, `replace(id, content)`, `edit<T>(id, recipe)` (immer-черновик содержимого),
  `hydrate(presets)`. Селекторы `presetBy(id)` и `presetsOf(kind)` — оба реактивные. Айди — uuid
  при создании, и он не зависит ни от имени, ни от вида, ни от содержимого;
- реестр видов участника — модульная карта: `defineUserKind` объявляет вид и отдаёт построитель
  пути, повторное объявление возвращает прежний.

Состояния мастера видны на самих узлах и адресуются скином: слот несёт `data-filled`, пока в нём
есть источник, `data-over` — пока над ним тащат, `data-fit` (`exact`/`safe`/`risky`) — чем
обернётся бросок того, что несут; поле входа несёт `data-dragging`, пока его тащат. Тип поля
помечен `data-type` на строке и `data-mark` на бейдже.

Локальное состояние сборок: `Endpoint` держит значение параметров, `Call` — результат и отказ
своего вызова, `ExternalSchemaLoader` — имя будущего пресета и текст ошибки разбора, диалог
настройки — пойманный узел и незаписанную правку его полей.

<h2 id="io">🔌 IO</h2>

↔️ **Загрузка.** Вход — сырой текст документа. `parseSchema(raw)` прогоняет его через шаблоны
(сегодня один, Swagger 2.0, совпадение жёсткое), выдаёт айди ручкам, превращает теги документа в
группы и отдаёт `SchemaDocument`. Нераспознанный документ — исключение.

↔️ **Документ.** `SchemaDocument { endpoints, groups, defs }`; ручка —
`{ id, method, url, groupId, params }`, группа — `{ id, name }`, где `params[].schema` — JSON
Schema, а `defs` держит общие типы. Чистый JSON: сериализуется и уезжает на склад как есть.

↔️ **Склад.** `Preset { id, kind, name, content }`, `content` непрозрачен. `kind` — ярлык вида,
который ставит дверь при заведении записи: `api` у документа схемы, `adapter` у шва.

↔️ **Вызов.** `invokeEndpoint(endpoint, value)` → `InvokeResult { status, ok, headers, body }`.
Имя, встреченное в `{плейсхолдере}` url, уходит в путь; ключ `body` — в JSON-тело; остальное — в
query. **Не-2xx — валидный результат**, а сорванный транспорт — исключение.

↔️ **Адаптер.** `Adapter { root, rules, extra?, providers, consumers }`. `root` — где в ответе
лежат записи; `rules` — связи `{ id, target, from, … }` (это `FieldRule` из `@web-core/io` плюс
выданный айди); `providers`/`consumers` — деревья проверенных участников, где первый ключ это вид,
а дальше ветку строит сам вид. Лист — пустой объект: это карта присутствия, не список.

↔️ **Адрес участника.** `defineUserKind(kind, address)` отдаёт построитель: `API_USER.path(presetId,
endpointId)` → `["api", presetId, endpointId]`. Вид ставит сам построитель — руками путь не
собирают. `userKinds()` перечисляет объявленное, `userKindOf(path)` говорит, чей путь; незнакомый
вид — `undefined`, а не догадка.

↔️ **Кормление.** `feed(response, adapter)` → `FeedResult { value, report, error }`. Правила
делятся по позиции цели: с индексом (`/items/0/label`) работают на каждой записи набора, без
индекса (`/title`) дают одно значение и читают источник от корня ответа.

Где лежит сам набор, говорит источник связи: `/data/0/login` — это «в `data`, их много, брать
`login`». Поэтому `root` записи спрашивать не нужно — человек уже показал его, перетащив поле.
Задан `root` явно — берётся он, а пути источников считаются относительными записи. Связь,
тянущая записи из другого набора, в сборку не идёт и называется в отчёте. Коллекций в форме
потребителя может быть несколько — каждая собирается своими правилами из тех же записей.

↔️ **Вызов с кормлением.** `serve(endpoint, value, { provider, consumer })` → `Serving`: `result`
приезжает всегда, `data`/`report`/`error` — только если нашёлся адаптер этой пары. Тот же конверт
отдают `Endpoint`/`Call` событием `onServing` и `ApiProbe` — событием `ApiProbeResult`, где рядом
лежит происхождение (`presetId` + ручка).

↔️ **Записи склада наружу.** `recordsOf(kind, as)` отдаёт записи своего вида уже приведёнными
стражем — `{ preset, content }`. `savedAdapters()` — то же для адаптеров, без аргументов.

<h2 id="сборки">🏗️ Сборки</h2>

🧪 Vitest + jsdom. **228 тестов, все зелёные:**

- `entities/openapi` — конфиг узла, распознавание petstore, айди при разборе, JSON Schema → zod,
  компоновка по группам, правки состава, живучесть узлов при правке;
- `entities/preset` — стор и механика показа записей своего вида в настоящем DOM;
- `entities/form` — `itemBinding`/`useTree` чистой логикой и `Tree` смонтированным;
- `entities/adapter` — страж записи, правки над черновиком (связь, замена источника с сохранением
  айди, деревья участников), совместимость типов, сборка ответа в форму потребителя (включая две
  коллекции и промах корня), реестр видов, поиск по паре и перечисление партнёров, блоки мастера в
  DOM (лунка, чип, метки типов, снятие связи);
- `features/api-manager` — вызов на моке `fetch`, `useInvoke`, каталог схем и правка состава,
  настройка узла диалогом, `ApiProbe` (отбор по потребителю, пустая витрина словами, отсутствие
  кнопок правки — с контрольной проверкой, что в каталоге они есть), `serve` с адаптером и без,
  узел ручки с потребителем и без него;
- `features/adapter-manager` — перенос поля в слот, ответ слотов на совместимость во время
  переноса, заведение записи при первой связи, подхват готовой записи пары;
- `features/external-schema` — сквозной путь «вставили документ → в сторе лежит разобранный пресет»;
- `shared` — `Box`, `RawLoader`, примитивы переноса (регистрация, данные источника у цели, снятие
  регистрации при размонтаже).

`lint` и `typecheck` зелёные.

Ark-UI/Zag/Kobalte внутри `@web-core/ui` отдают сырой `.jsx` по `solid`-condition — vitest грузит
его напрямую через Node и падает; лечится `test.server.deps.inline` в `vitest.config.ts`.

<h2 id="рецепт">🎨 Рецепт</h2>

🧩 Приёмы, которые стоит понять, чтобы не спорить с движком:

**Чужой формат разбирается один раз, на входе.** После импорта нет ни Swagger 2.0, ни любого
другого — есть наш документ. Поэтому сырьё не хранится, а правка ручки не упирается в сериализацию
чужой спеки.

**Склад не знает, что на нём лежит, но знает, чего оно вида.** `Preset` — имя плюс непрозрачное
содержимое плюс ярлык вида, который склад сравнивает строкой и не толкует. Потребителей двое:
документ API и адаптер, и каждый находит свои записи, не заглядывая в чужие.

**Тождество узла — по выданному айди, а не по ссылке и не по содержимому.** Так у ручки, у группы и
у связи адаптера: всё, что человек правит на экране, опознаётся айди, а не полями, которые он и
меняет.

**Шов не принадлежит ни ручке, ни компоненту.** Адаптер держит форму перекладки и два дерева
проверенных участников — «на этих работает». Поэтому один адаптер обслуживает много поставщиков и
много потребителей, а найти его можно с любой стороны (`partnersOf`).

**Вид участника объявляется, а не перечисляется.** Feeder знает только своё — `api`; компонент,
утилита, что угодно ещё объявляются снаружи через `defineUserKind`. Закрытый список видов означал
бы, что мы знаем всех потребителей заранее.

**Позиция цели решает, чем является правило.** Индекс в пути (`/items/0/label`) говорит «это поле
каждой записи», его отсутствие — «это одно значение на весь объект». Поэтому одна и та же форма
собирается и из набора записей, и из корня ответа, без отдельного переключателя.

**Набор записей называет источник связи, а не отдельный вопрос человеку.** `0` в пути — это не
«первый элемент», а «каждый»: путь пришёл из описания формы, где массив показан одним образцом.
Слева от индекса стоит сам набор, и его достаточно прочитать.

Вся механика описания форм и применения правил — в `@web-core/io`. Feeder не пишет своего движка
сведения: он даёт интерфейс и решает, что и в каком порядке спросить у человека.
