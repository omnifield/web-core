<h2 id="главное">🏠 Главное</h2>

🎛️ Этаж между базой (`../web-core/`) и поверхностями (`../apps/`, `../products/`). Сущность здесь
сводит функционал **нескольких** пакетов фреймворка под общий UI и отдаёт уже собранный
результат, которым пользуется больше чем одно приложение — не кирпич и не поверхность, а готовый
межпродуктовый механизм.

🧬 `genus` у всех — `engine`, в том же смысле, что у [`store`](../web-core/store/README.md) и
[`assembly`](../web-core/assembly/README.md): потребитель настраивает готовый механизм штатными
средствами, а не собирает его заново из россыпи. `группа` — `interfaces`, общая на весь каталог.

<h2 id="критерий">🚪 Критерий включения</h2>

✅ **Сюда кладут** механизм, у которого есть все три признака:

1. **Сводит несколько пакетов** — не одна механика, а их связка под общей задачей пользователя
   (`feeder` — [`generators`](../web-core/generators/README.md) плюс [`io`](../web-core/io/README.md));
2. **Несёт свой UI** — отдаёт готовые виджеты, а не только функции: тем и отличается от базы;
3. **Потребителей больше одного** — иначе это часть того единственного приложения, которое его
   просит, и место ему там.

🚫 **Сюда НЕ кладут:**

- **одну механику без UI** — это `../web-core/`;
- **поверхность с адресом** — это `../apps/`: у интерфейса нет маршрутов, его вход — экспорты
  пакета;
- **UI под один конкретный продукт** — он живёт в самом продукте, пока не появится второй
  потребитель. Второй потребитель — и есть признак, что механика общая.

<h2 id="правила">📏 Общие правила группы</h2>

- 📐 **Внутри — адаптированный FSD, переосмысленный под движок**, тем же приёмом, что в
  [`apps/studio`](../apps/studio/README.md), но без `app`/`pages`: сущность не приложение, вход
  наружу — экспорты пакета, а не маршрут.
  - `entities` — структурная модель самого движка (узел дерева), не бизнес-сущность;
  - `features` — фичи интерфейса (отредактировать значение), не бизнес-операция;
  - `widgets` — сборка entities+features в готовый UI одного режима.
- 🧾 **Расклад слоёв описывается ВНУТРИ раздела «Анатомия»** своего README, не отдельным
  разделом: фиксированный порядок разделов шаблона под этим каталогом не меняется.
- 🔗 **Пакеты берут НОМЕРОМ ВЕРСИИ** (`"@web-core/ui": "^0.4.0"`), а не протоколом `workspace:*`:
  интерфейс живёт своим репозиторием и обязан собираться без базы рядом. Когда база рядом есть,
  та же строка даёт живую папку — подстановку по диапазону включает `linkWorkspacePackages`
  (`../pnpm-workspace.yaml`).
- 🚚 **Выпуск у группы СВОЙ**, не общий с базой: интерфейсы не входят в `versioning.fixed` и
  поднимаются своим номером. Цена названа заранее — номера расходятся с базой, и за
  совместимостью следит сама группа.
- 🚫 **О приложениях не знают.** Интерфейс не импортирует `../apps/`/`../products/` и не
  упоминает их в доке: он межпродуктовый по определению, и знание о конкретном потребителе
  делает его частным случаем.
- 🧪 **Проверки зелёные перед коммитом**: `pnpm --filter @web-core/<интерфейс> lint typecheck test`.

<h2 id="новый">➕ Как завести новый интерфейс</h2>

1. Проверить по [критерию включения](#критерий) главное: потребителей правда больше одного? Если
   один — рано, место такому UI в самом потребителе.
2. Завести пакет со скоупом `@web-core/*` и оснасткой из [`build`](../web-core/build/README.md).
3. Разложить исходники по FSD без `app`/`pages`; публичный вход — `index.ts` пакета.
4. Включить в выпуск ЭТОЙ группы, а не в `versioning.fixed` базы: у интерфейсов своя поставка и
   свой номер.
5. Завести зону владельца в `../.claude/harness.yaml`.
6. Написать тройку доков по шаблону `genus: engine` и добавить строку в [состав](#состав).
