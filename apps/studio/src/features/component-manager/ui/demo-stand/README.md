# Demo stand: оси, ячейки, layout

Демо-стенд показывает один компонент во всех его вариантах/сборках сразу — сеткой (`grid`) или
матрицей (`matrix`). Обе раскладки рисуют одно и то же пересечение двух осей, отличается только
то, как это пересечение подаётся глазу.

## Граница: что про компонент, а что про стенд

Разрез простой и держится на одном вопросе — **зависит ли это от того, кто смотрит**.

| | где живёт | что это |
| --- | --- | --- |
| срез редактора, io-схема, варианты, пресеты данных | `entities/component` | «что это за компонент» — один и тот же ответ для стенда, редактора скина и песочницы |
| `layoutMode`, `axisMode`, `filterMode`, `viewMode`, `feedData`, `secondaryIndex` | `model/store.ts` этой фичи | «как ИМЕННО ЭТОТ стенд показывает» — у соседней фичи будут свои |

Данные компонента приезжают из `useComponent()` (`entities/component`), где асинхронную часть
ведёт кэш запросов (`defineQuery` → TanStack). Копии в сторе стенда нет намеренно: она была
третьей по счёту и единственной, которая не умела ни показать загрузку, ни рассказать об ошибке,
ни обновиться. Загрузку раньше звали висящим промисом без `.catch` — упавший запрос оставлял
пустой экран без единого слова.

Из-за этого разреза стор больше не может сам разрешить «ячейка → показанный элемент»: для этого
нужны оба списка, а он их не держит. Разрешение — чистые функции в `lib/axes.ts`; состояние
стенда и данные компонента сводит `model/stand.ts` (`useStand`), единственное место, где они
встречаются. Побочная выгода: арифметика осей тестируется без стора и без сети вовсе.

## Две оси, всегда primary/secondary

У компонента ровно два измерения, по которым он умножается: варианты (`variant`) и сборки
(`assembly`). Одно из них всегда primary, второе — secondary; какое из двух primary, выбирает
`axisMode` в сторе (`model/store.ts`) — **строго глобально**, на одном уровне с `layoutMode`. У
axisMode нет и не может быть «локального» варианта: ячейка не выбирает, какая ось primary — она
уже родилась внутри уже выбранной primary-оси, ей нечего тут решать.

## `Cell` — примитив, не веха. `primary` фиксирован, `group` — принадлежность, `secondary` — не его

```ts
interface Cell {
  readonly primary: number; // позиция по primary-оси, уникальна ВНУТРИ группы, зашита при создании
  readonly group: string;   // ключ группы (порции primary-оси), "" — без группировки
}
```

Ячейка — что грид-клетка, что слайд карусели matrix — устроена одинаково: `primary` фиксирован раз
и навсегда в момент, когда ячейка строится (`containers/distributor.tsx`, `groups()`). `secondary`
сознательно НЕ поле `Cell` — это не часть ячейки, а динамическое состояние снаружи, в сторе, которое
всегда стартует с `0` и меняется пользователем. Ячейка про него ничего не знает и не хранит.

**Отдельного `id` у ячейки нет — и это не упущение.** Адрес выводится из самой пары полей
(`cellKeyOf` в `model/store.ts`, `` `${group}/${primary}` ``). Хранимое поле пришлось бы держать
уникальным вручную на стороне производителя ячеек, а тот про соседние группы не знает: один вариант
с двумя тегами рождается в двух группах, и «уникальный» `id: String(index)` выходил у них общий.
Следствие было тихим — переключаешь secondary в секции «primary», меняется и в секции «danger»,
которой на экране может быть не видно вовсе. Позиция уникальна только ВНУТРИ группы, поэтому
адресует ячейку именно пара, а не одно число.

## Секondary живёт в сторе, а не в ячейке — и у него есть *scope*

Где именно хранится текущий выбор secondary, решает `state.layoutMode` (само решение — центральное,
в сторе; ни ячейка, ни контролы этой логики не знают):

```ts
function secondaryScopeOf(state, cell) {
  return state.layoutMode === "matrix"
    ? `${state.axisMode}/group/${cell.group}`
    : `${state.axisMode}/cell/${cellKeyOf(cell)}`;
}
```

- **Grid** — scope = ячейка (`cellKeyOf`). Каждая клетка независима, переключение secondary
  «точечное» — у соседних клеток может быть выбран разный элемент.
- **Matrix** — scope = группа (`cell.group`), т.е. вся matrix-обёртка разом. Причина не
  произвольная: в matrix ячейка — это слайд одной и той же карусели, а не самостоятельный блок.
  Если бы каждый слайд листал secondary независимо (как в grid), при горизонтальном свайпе по
  primary слайды «прыгали» бы по secondary вразнобой (по диагонали). Поэтому все слайды одной
  matrix-обёртки обязаны листать один и тот же secondary синхронно — «прямая» ось, не зигзаг.

Обратите внимание: `layoutMode` решает, что слушает **ячейка при рендере**, — это её вопрос, она
про свою раскладку не знает. У записи вопроса нет: контрол с самого начала знает, кто он, и зовёт
своё действие напрямую — grid-шный точечный `setSecondaryIndexOfCell(index, cell)`, matrix-овый на
всю обёртку `setSecondaryIndexOfGroup(index, group)`.

Раньше действие было одно и принимало `cell`, а scope стор выводил из `layoutMode`. Матрице ячейка
при этом была не нужна — ей нужна группа, — и она подсовывала «любую из группы» (`items[0]`), чтобы
стор достал из неё `group`. Тип обещал `Cell`, значение могло быть `undefined` (пустая группа), а
смысл «ячейка» был подложным: адресовали-то группу. Записывающая сторона не должна угадывать то,
что и так знает про себя, — и тем более выдумывать аргумент, чтобы это сообщить.

Сам контрол (`controls/secondary-picker`) после этого ничего не адресует вовсе: показывает список,
отдаёт выбранную позицию, а куда её деть — дело контейнера.

### Ключ описывает, ЧЕМ является число, а не только где его выбрали

В ключ входит не один scope, а ещё и `axisMode` с признаком самого scope (`group`/`cell`), потому
что голого адреса ячейки или группы не хватает — и оба промаха тихие:

- **Смена `axisMode` меняет список, а не только его роль.** Выбрал седьмую сборку, переключил ось —
  secondary теперь варианты, и число `7` указывает уже в чужой список. Ось в ключе разводит эти два
  выбора: обратное переключение возвращает прежний, а не подставляет соседний.
- **Адрес группы и адрес ячейки — разные пространства имён, слитые в одно.** Тег вполне может
  называться `"0"` — ровно так же, как позиция первой ячейки. Признак scope в ключе их разделяет.

### Границу списка держит стор

`secondaryIndexAt` отдаёт наружу только индекс, по которому что-то есть: `Math.min(stored, len-1)`,
и `0` на пустом списке. Списки приезжают асинхронно и умеют становиться короче уже сделанного
выбора; индекс вне границ — это не исключение, а `undefined` из `variantAt`/`assemblyAt`, на котором
`Show` не рисует ничего: ячейка молча пустая, без ошибки и без объяснения. Проверяется в
`test/component-manager-secondary.test.ts`.

## Фильтр режет primary ось на группы — общий механизм для grid и matrix

`filterMode` (например, группировка по тегам) режет primary ось на порции — `Group<Cell>[]`
(`lib/group.ts`, `noGroup`/`groupByTags`), один и тот же для обеих раскладок. Без фильтра группа
одна (`label: ""`, все элементы внутри) — это не отдельный случай, а естественное вырождение той же
механики: раз группа одна, «общий secondary на группу» в matrix автоматически становится «общий на
весь matrix».

- **Grid** — одна секция на группу, внутри плоская сетка независимых ячеек.
- **Matrix** — одна matrix-обёртка на группу. Обёртки полностью независимы друг от друга:
  переключение secondary в группе А не трогает группу Б — то же самое правило независимости, что у
  ячеек grid, просто на уровень выше (обёртка сама себе «большая ячейка»).

### Применимость фильтра зависит от primary-оси

Не всякий фильтр осмыслен на всякой оси: теги есть только у вариантов (`VariantSummary.tags`), у
сборок такого поля нет и не предвидится — это другая сущность, а не недоделка скина. Поэтому каждый
режим в `FILTER_MODES` (`model/modes.ts`) объявляет `axes` — оси, на которых он работает, а
`filterAppliesTo(filterMode, axisMode)` отвечает на вопрос в одном месте для всех, кому он нужен:

- **Контрол** (`controls/filter-modes`) гасит неприменимый режим, а не прячет: исчезающая кнопка
  дёргает раскладку и не объясняет, куда делась, — выключенная говорит «режим есть, но не на этой
  оси».
- **Стор** (`setAxisMode`) сбрасывает на `DEFAULT_FILTER_MODE`, если после смены оси текущий режим
  стал неприменим. Без сброса состояние разъезжается с экраном: контрол такой режим уже не
  показывает, а раскладка продолжает по нему резать.

До этого контрол оставался активным на оси сборок: нажатие честно меняло `filterMode`, раскладка
честно шла группировать, все элементы попадали в один безымянный бакет — и не менялось ничего.
Кнопка, которая гарантированно ничего не делает, хуже отсутствующей. Проверяется в
`test/component-manager-grouping.test.ts`.

## Matrix — плоскость привязки, а не карусель в карусели

Matrix свайпается по обеим осям: горизонталь — primary, вертикаль — secondary. Это ОДИН
scroll-контейнер с `scroll-snap-type: both mandatory` (`containers/matrix/plane.tsx`), внутри —
грид N×M рамок размером во вьюпорт, по краям — две линейки (`ruler.tsx`), каждая вдоль своей оси:
горизонтальная сверху, вертикальная слева.

### Два правила, на которых это держится

**Рамка есть — рендер не обязателен.** Рамок N×M, и это дёшево: пустой div ничего не стоит.
Дорог рендер компонента через движок сборки. Живыми держим окно ±1 вокруг текущей позиции
(`lib/plane.ts`, `withinWindow`) — не больше девяти штук, сколько бы ни было осей. Именно
слипание этих двух понятий («слайд существует» = «компонент отрисован») и роняло браузер в
прошлых заходах.

**Позиция считается, а не хранится.** Где мы на плоскости — арифметика от `scrollLeft`/`scrollTop`
(`snapIndexAt`), а не отдельное состояние. Пока позиций было две (по одной на карусель), их
приходилось синхронизировать; считаемой позиции синхронизировать не с чем.

Одна засада, на которую стоит смотреть при правках: координаты записываются **одной** транзакцией
(`batch` в `index.tsx`). Порознь между ними успевает пройти отрисовка с позицией «столбец уже
новый, строка ещё старая», плоскость понимает её как «позицию сменили снаружи» и уезжает по
вертикали обратно. Вскрывается только диагональным жестом.

Содержимое рамки обрезается, а не скроллится: свой скролл внутри рамки — это вложенный скроллер
поперёк плоскости, то есть ровно та мешанина жестов, от которой уходили. Не влезает — вопрос к
`footprint` компонента.

### Сверка с рынком · 2026-09-18

**Что смотрел:** карусельные библиотеки (Swiper, Splide, Embla, react-elastic), Ark/zag carousel,
CSS Scroll Snap, CSS-карусели (`::scroll-marker-group`), TanStack Virtual.

**Что нашёл:**

- Двухосевого свайпа как «карусели» нет ни у кого: `direction`/`orientation` везде ОДНА из
  horizontal/vertical. Штатный обходной путь — вложенность (вертикальная карусель внутри
  горизонтальной).
- Вложенные скроллеры поперёк друг друга — известно хрупкий паттерн: жест, начатый в зоне
  внутреннего, глушит внешнюю ось; на Android внутренний то не активируется, то перебивается.
  Лечится `overscroll-behavior` и не всегда. Наши пять неудачных заходов — не случайность.
- `scroll-snap-type: both mandatory` в базовой поддержке с Chrome 69 / Firefox 68 / Safari 11.
  Известная ловушка `mandatory` (утаскивание назад) касается snap-детей БОЛЬШЕ вьюпорта — у нас
  рамка ровно во вьюпорт.
- Браузеры сами защёлкивают почти-вертикальный и почти-горизонтальный жест на одну ось (axis
  locking) — в одном контейнере «свайп = шаг по одной оси» получается даром. В CSSWG обсуждают,
  как этим управлять (`css-overflow-5`, issue #13207).
- CSS-карусели не подходят: маркер-группа одна на контейнер, две линейки по осям из неё не
  собрать, Firefox ещё не умеет.
- 2D-виртуализация решена в TanStack Virtual (два виртуалайзера, есть solid-адаптер).

**Почему берём это:** одна плоскость вместо вложенности получает разведение осей от браузера
даром и снимает синхронизацию позиций. TanStack Virtual пока НЕ берём — окно ±1 это двадцать
строк, а зависимость в поставку решает architect; заводить заявку, если упрёмся в размеры осей.

**Кандидат в кит:** «2D snap-плоскость с двумя линейками» — примитива такого в библиотеках нет, а
переиспользуем он очевидно. Обкатывается здесь; выносить в `@web-core/ui` — заявка owner-ui через
architect, когда докажет себя.

## Статус

Grid — рабочий. Matrix — плоскость выше; самый первый заход рендерил полный кросс-продукт primary ×
secondary живыми ячейками и ронял браузер, второй отменил кросс-продукт, но отдал secondary
селекту вместо свайпа.
