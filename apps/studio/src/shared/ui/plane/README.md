# 🧭 Plane

Двумерная плоскость привязки: свайп по **обеим** осям сразу, с линейками вдоль каждой.

Заготовка под компонент кита. Обкатывается здесь, в `apps/studio`, на живых данных; когда
докажет себя — уезжает в `@web-core/ui` заявкой к architect. Разложена так, чтобы переезд был
механическим: чистая арифметика отдельно от вида, **ноль зависимостей от приложения** (только
`@web-core/skin` и `@web-core/ui`).

## 🧩 Анатомия

| часть | что делает | рисуется |
| --- | --- | --- |
| `Plane` | скролл-вьюпорт с привязкой по обеим осям, внутри грид N×M рамок размером во вьюпорт | `plane.tsx` |
| `PlaneRuler` | линейка одной оси: деление на элемент, текущее отмечено, клик — переход | `ruler.tsx` |
| `snapIndexAt` · `withinWindow` | арифметика позиции и окна, без DOM и без реактивности | `lib/position.ts` |

Линейки — отдельные части, а не потроха плоскости: они кладутся **вдоль своей оси**
(горизонтальная сверху, вертикальная слева), и раскладку выбирает тот, кто собирает. Плоскость
про них не знает.

## 🚀 Использование

```tsx
const [position, setPosition] = createSignal<PlanePosition>({ column: 0, row: 0 });

<PlaneRuler
  orientation="horizontal"
  items={columns}
  index={position().column}
  onSelect={(column) => setPosition((prev) => ({ ...prev, column }))}
/>
<Plane
  columns={columns}
  rows={rows}
  position={position()}
  onMove={setPosition}
  style={{ height: "24rem" }}
>
  {(cell) => <Show...>{/* что показывать в клетке (cell.column, cell.row) */}</Show>}
</Plane>
```

## 🧠 Почему так, а не иначе

**Один контейнер, а не карусель в карусели.** Вложенные скроллеры поперёк друг друга делят один
жест: внутренний то перехватывает чужую ось, то не активируется вовсе (особенно на тач-
устройствах). Это известное свойство паттерна, а не невезение — до этой версии двухосевую
матрицу пробовали собрать вложенностью пять раз и не собрали ни разу. В одном контейнере оси
разводит сам браузер (axis locking), и делать нам нечего.

**Рамка есть — рендер не обязателен.** Рамок N×M, и это дёшево: пустой div ничего не стоит. Дорог
рендер содержимого. Живым держится окно ±1 вокруг текущей позиции (`withinWindow`) — не больше
девяти клеток, сколько бы ни было осей. Замер на витрине (7 вариантов × 3 сборки): 21 рамка,
живых 4 в углу и 9 в центре. Слипание «клетка существует» = «содержимое отрисовано» — ровно то,
что роняло браузер в первом заходе.

**Позиция считается, а не хранится.** Где мы на плоскости — арифметика от
`scrollLeft`/`scrollTop` (`snapIndexAt`), а не отдельное состояние. Пока позиций было две (по
одной на карусель), их приходилось синхронизировать; считаемой синхронизировать не с чем.

**Позиция докладывается по остановке**, а не на каждом событии скролла: иначе плавный доезд по
клику линейки проходит через промежуточные округления, каждое уезжает наружу и возвращается
новым `position` — плоскость начинает спорить сама с собой. `scrollend` решил бы это красивее,
но он ещё не везде.

### ⚠️ Засада для того, кто подключает

Координаты обязаны записываться **одной** транзакцией. Порознь между ними успевает пройти
отрисовка с позицией «столбец уже новый, строка ещё старая» — плоскость понимает её как
«позицию сменили снаружи» и честно уезжает по второй оси обратно. Вскрывается только
диагональным жестом: по одной оси второй координате меняться не с чего.

### Содержимое клетки обрезается, а не скроллится

Свой скролл внутри рамки — это вложенный скроллер поперёк плоскости, то есть ровно та мешанина
жестов, от которой уходили. Не влезает — вопрос к размеру, который задаёт вызывающий через
`style`. Компонент внутри рамки стоит по центру своим размером (`place-content: center`), а не
растягивается: рамка во всю ширину вьюпорта, и растяжка врала бы о том, как содержимое выглядит.

## 📋 Сверка с рынком · 2026-09-18

**Что смотрел:** карусельные библиотеки (Swiper, Splide, Embla, react-elastic), Ark/zag carousel,
CSS Scroll Snap, CSS-карусели (`::scroll-marker-group`), TanStack Virtual.

**Что нашёл:**

- Двухосевого свайпа как «карусели» нет ни у кого: `direction`/`orientation` везде ОДНА из
  horizontal/vertical. Штатный обходной путь — вложенность.
- Вложенные скроллеры поперёк друг друга — известно хрупкий паттерн (см. выше).
- `scroll-snap-type: both mandatory` в базовой поддержке с Chrome 69 / Firefox 68 / Safari 11.
  Известная ловушка `mandatory` (утаскивание назад) касается snap-детей БОЛЬШЕ вьюпорта — здесь
  рамка ровно во вьюпорт.
- Браузеры сами защёлкивают почти-вертикальный и почти-горизонтальный жест на одну ось (axis
  locking). В CSSWG обсуждают, как этим управлять (`css-overflow-5`, issue #13207).
- CSS-карусели не подходят: маркер-группа одна на контейнер, две линейки по осям из неё не
  собрать, Firefox ещё не умеет.
- 2D-виртуализация решена в TanStack Virtual (два виртуалайзера, есть solid-адаптер).

**Почему берём это:** одна плоскость вместо вложенности получает разведение осей от браузера
даром и снимает синхронизацию позиций. TanStack Virtual пока НЕ берём — окно ±1 это двадцать
строк, а зависимость в поставку решает architect; заводить заявку, если упрёмся в размеры осей.

## 🚧 Чего не хватает для кита

Список сознательный — это не «доделки», а то, что осмысленно решать на переезде, а не сейчас:

- **Только управляемый режим.** `position`/`onMove` обязательны; неуправляемого
  (`defaultPosition`) нет. У компонентов кита обычно есть оба.
- **Радиус окна зашит в 1.** Тяжёлому содержимому подошёл бы 0, лёгкому 2 — просится в проп,
  когда появится второй потребитель с другой ценой рендера.
- **Нет паспорта, io-схемы и рецепта** — то есть в ките он пока не «компонент», а просто код.
- **Линейка собрана на `SegmentGroup`.** Для кита это, возможно, своя часть с ролью, а не
  переиспользование чужого контрола.
- **Не проверено на клавиатуре и на тач-устройстве живьём** — только мышью/скриптом в Chrome.
