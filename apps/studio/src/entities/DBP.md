# `entities` — бизнес-сущности (слой FSD)

## Место в иерархии

Порядок слоёв сверху вниз: `app → pages → widgets → features → entities → shared`.
`entities` — второй снизу: выше него `widgets`, `features`, `pages`, `app`; ниже — только
`shared`.

## Что кладётся сюда

Данные и МЕХАНИКА ОДНОЙ бизнес-сущности — существительное предметной области приложения (в
абстрактном примере FSD: `user`, `product`, `order`). Сущность даёт чистые прозрачные методы
(достать, записать, посчитать, простая трансформация) — «россыпь» примитивов, а не готовый
сценарий. Внутри себя сущность НИЧЕГО не строит: ни композиций UI, ни цепочек из нескольких
своих же методов, ни жёсткой бизнес-логики — это работа `features`, не её. Сущность НЕ знает,
на какой странице и рядом с чем её используют — это забота слоёв выше.

`ui/`-сегмент сущности — тот же принцип, только для разметки: один базовый, самостоятельный
кусок (спиннер, одна контрольная панель) БЕЗ сборки нескольких таких кусков в поток с логикой.
Как только кусок начинает решать, В КАКОМ ПОРЯДКЕ вызвать несколько методов сущности или что
показать вместо чего — он вырос из `entities` и переезжает в `features`.

Отличие от `shared`: если модуль без проблем описывается без бизнес-понятий приложения — он
не сюда, а в `shared`. Если в описании модуля неизбежно всплывает бизнес-понятие — это `entities`.
Отличие от `features`: `entities` — чистые методы и базовое отображение одной сущности, без
сборки; `features` — то место, где из этих методов (одного домена или нескольких сразу)
собирается реальный сценарий, см. [`../features/DBP.md`](../features/DBP.md).

## Правило импортов

- `entities` импортирует только из `shared`.
- НЕ импортирует `features`/`widgets`/`pages`/`app` — все они лежат выше. Если сущности
  "хочется" знать про действие, виджет или страницу, которые её показывают — это инверсия
  зависимости, сигнал, что код лежит не на том слое.

## Слайсы — вертикальный разрез по домену, не по типу файла

Один слайс = один бизнес-объект. Внутри слайса — сегменты по ТЕХНИЧЕСКОЙ роли:
- `ui/` — компоненты отображения сущности.
- `model/` — стор, типы, бизнес-логика (без разметки).
- `api/` — запросы, относящиеся именно к этой сущности (в этом приложении обычно уносятся в
  `shared/api` как транспорт, а здесь остаётся только сама сущность).
- `lib/` — вспомогательные чистые функции слайса.

Правило "один слайс = один бизнес-объект" даёт **cohesion**: слайс меняется по ОДНОЙ причине.
Если слайс параллельно знает детали ДВУХ разных сущностей, он начинает меняться по причинам,
не относящимся к его прямой задаче — это и есть потеря связности, ради недопущения которой
методология и разделяет слайсы.

## Слайсы одного слоя не видят друг друга напрямую

Ключевое свойство FSD, ради которого всё затевалось: изоляция слайсов на одном уровне даёт
стабильность при рефакторинге — переписал один слайс, соседние не сломались, потому что они
физически не могли залезть в его внутренности. Если двум сущностям регулярно нужны детали друг
друга — это повод пересмотреть границу домена (может, это на самом деле один слайс, а не два),
а не заводить cross-import как способ "быстро заработало".

## Public API

Наружу слайса — только `index.ts`. Всё остальное (`model/*.ts` напрямую, `ui/*/index.tsx` без
реэкспорта из корневого `index.ts`) — внутренности, снаружи трогать нельзя. Прямой импорт во
внутренности: (а) ломает гарантию "остальное приложение не знает о структуре слайса" —
рефакторинг ВНУТРИ одного слайса не должен требовать правок по всему дереву; (б) плодит
циклические зависимости; (в) тащит наружу вес, который не предполагался публичным.

Это правило действует и ВНУТРИ одного слайса, если он расширяется несколькими близкими
поддоменами: каждый поддомен получает свою папку с тонким `index.ts`, сосед вызывает функцию
соседнего поддомена через его `index.ts`, а не напрямую через внутренний файл.
