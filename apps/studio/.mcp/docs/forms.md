# Форма (рецепт компонента)

Разведка перед `save_preset(kind:"form")`. Полный разбор терминов — README.md, раздел «Словарь».

## Прежде чем писать с нуля — найдите пример

В службе уже лежат настоящие, рабочие формы (`omnifield-*`). `list_components` даёт `group`/
`footprint` каждого компонента — у компонента с ТЕМ ЖЕ `group`/`footprint` почти наверняка уже
есть форма-эталон. `get_preset({kind:"form", name:"omnifield-<похожий>"})` — копируйте СТРУКТУРУ
(какие части/состояния тронуты, как устроены переходы), не значения.

## `check_form` — два прохода

1. **Ссылки** — та же проверка, что и у наряда: роль/переменная в рецепте реально существует у
   палитры.
2. **Адрес** — часть/состояние/настройка реально существуют в паспорте компонента (`get_passport`).

Опечатка в любом из двух — флав с адресом, не тихое неприменение. Нужна палитра для сверки ролей —
не назвали `paletteName`, берётся первая из службы (для настоящей проверки называйте явно).

## Теги варианта (`variantTags`)

Значение `recipe.variants` можно тегировать — например `error`/`success`/`warning` тегируются
`"status"`, а `primary`/`secondary`/`tertiary` — нет. Каждый тег сверяется со словарём
(`kind:"tag"`); значение без тега получает `["default"]`. При `ok:true` `check_form` отдаёт
`tagGroups` — тег → варианты, готовая раскладка для свайперов/переключателей на витрине.

## Если `ok:false`

`css` пропадает из ответа вместе с флавом — сигнал не противоречив: невалидный рецепт не должен
выглядеть частично рабочим.

## ОБЯЗАТЕЛЬНО — иначе форма выглядит «сломанной», а флава не будет

Два пункта ниже НЕ ловит ни `check_form`, ни `check_outfit`, ни `save_preset` — оба прохода
структурно валидны, флав не сработает. Симптом в обоих случаях один: «стили как будто не
применились» — легко списать на баг движка, хотя дело в данных. Проверено дважды живьём
(2026-09-10) на реальной службе, оба раза одной и той же ошибкой внешнего агента.

### 1. Форма мертва, пока её нет в `forms` НУЖНОГО наряда

`save_preset(kind:"form")` кладёт форму в службу — это ЕЩЁ НЕ значит, что её кто-то носит.
CSS компонента генерируется только для форм, перечисленных в `Outfit.forms[]` конкретного наряда
(`check_outfit`/`assemble_preview`/сборка витрины резолвят строго по этому списку). Форма, которую
забыли туда добавить — для витрины как будто не существует: ни одного CSS-правила на компонент не
генерируется, браузер красит его дефолтными UA-стилями (обычно это читается как «всё серое/чёрное,
без бренда»), а не «форма нашлась, но что-то не так».

**Правило:** сохранили новую форму (или добавили её компоненту, у которого раньше формы не было) —
сразу проверьте `get_preset({kind:"outfit", name:"<каждый актуальный наряд>"})`'s `forms[]` и, если
имени там нет, добавьте (`check_outfit` → `save_preset(kind:"outfit")`). НА КАЖДЫЙ активный наряд
отдельно — двух почти одинаковых (`omnifield`/`amethyst`) уже нашлось по 9 форм, вписанных в один
и пропущенных в другом.

Живой случай: `omnifield-diagram` и ещё 8 форм (`drawer`/`slider`/`splitter`/`timer`/`toggle`/
`icon`/`tabs`/`table`) существовали в службе, проходили `check_form` с `ok:true`, но не входили в
`forms[]` НИ ОДНОГО из двух реальных нарядов — витрина рисовала эти компоненты вообще без скина.

### 2. Анимация в `recipe` без своего `keyframes` — молчаливый труп, не флав

Состояние, зовущее анимацию по имени (`props.animation: "moving-part var(--motion-normal) …"`),
ОБЯЗАНО иметь этот `keyframes`-ключ в `Form.keyframes` (см. канон-рецепт компонента в
`web-core/ui/src/<component>/playground/recipe.ts` — если там есть `keyframes`, форма должна нести
то же самое или явно тот же смысл, а не только `recipe`). Браузер молча игнорирует `animation` с
несуществующим именем — состояние переключается (`data-state` меняется), а визуального перехода
нет: открытие сразу даёт конечный результат, закрытие замирает на прежнем.

Живой случай: `omnifield-tree-view` и `omnifield-accordion` — `recipe` звал `grow-block-size`/
`shrink-block-size` по имени, `keyframes` был `null`. Сайдбар-дерево и аккордеон визуально не
закрывались/дёргались — не баг движка сборки (три шага `form.keyframes → skin.keyframes →
@keyframes` в CSS целы и проверены), баг данных ОДНОЙ конкретной формы.

### Почему не поймано инструментом

`check_form`/`check_outfit` проверяют ссылочную и структурную целостность (роль есть у палитры,
часть есть у паспорта) — оба случая выше проходят эту проверку честно: `keyframes:null` не ссылка
на несуществующее, а `forms[]` наряда — отдельная, независимо валидная сущность, не обязанная
перечислять ВСЕ существующие формы. Автоматической проверки «все формы компонента внутри одного
наряда» или «recipe без висячих animation-имён» сегодня нет — см. `ROADMAP.yaml`,
`form-animation-and-outfit-coverage-checks`, если решите заводить.
