## ✅ Что сделано в этой сессии

Три больших блока подряд, каждый закрывал реальную живую заявку внешнего агента:

1. **API — пересмотр формы ответа.** `get_passport` разбит на три честных тула (`get_passport` —
   только паспорт, `get_assemblies`, `get_io_schema` — отдельно, по запросу). CSS `assemble_preview`
   едет `resource_link` (`skin-css://<uuid>`), не инлайном. `skinGaps` группирует по тексту `means`.
   `check_palette` несёт структурный `missing: string[]` (все нехватающие роли), не только текст.
   Файл `tools/index.ts` (500+ строк) разбит на `tools/{kit,presets,feedback,content,browser,
   shared}.ts`. Все описания тулов короткие (1-2 предложения), глубокая документация — в
   `docs/*.md`, читается по требованию через `list_docs`/`get_doc` (НЕ грузится агенту заранее).
2. **Личность — `X-User-Login`, не аргумент.** `web-core/mcp`'s `registerTool` теперь пробрасывает
   `ToolContext` (`{headers, sessionId}`) в каждый хендлер — заголовок настоящего HTTP-запроса, не
   выдумка агента. `resolveAuthor(context, argumentAuthor)` в `tools/shared.ts`: заголовок побеждает
   безусловно, аргумент — только резерв для stdio (без заголовков вовсе). Проверено живьём: попытка
   назваться чужим именем аргументом при настоящем заголовке — заголовок побеждает, не аргумент.
3. **`paginate()`'s `DEFAULT_LIMIT` 50 → 20.** Найдено ДВАЖДЫ живой заявкой: сначала `list_presets()`
   без `kind` отдавал всё (7179 симв/28 форм) — точечно чинили своим `OVERVIEW_LIMIT=10` под пять
   видов сразу. Второй заявкой поймали тот же класс бага в СОСЕДНИХ вызовах того же общего
   `paginate()` — `list_components()` и `list_presets(kind:"form")` тоже отдавали всё целиком без
   `nextCursor`, потому что 50 не был пройден НИ НА ОДНОМ реальном наборе зоны. Починено в движке
   (`web-core/mcp/src/pagination`), одной правкой на все ветки — см. чекпоинт пакета.

Плюс по мелочи: `resolveVariantTags` теперь ловит опечатку в имени варианта (реверс-проверка, раньше
тихо игнорировалась), `report_feedback` получил `sign: "issue"|"praise"`, `list_feedback`/
`get_feedback` разделены на заголовок/тело (как `get_preset`/`get_content`), `limitSchema` — общий
потолок `100` вместо утечки языкового максимума в JSON Schema.

**Session-wide находка, важная на будущее**: измерять вес ответа тула нужно через
`content[0].text.length` (реальный текст на проводе — `ok()` печатает `JSON.stringify(value, null,
2)` с отступом), НЕ через `JSON.stringify(перепарсенное).length` (компактная пересборка занижает
реальный вес на 20-40%). Несколько уже опубликованных чисел в этой сессии были найдены и
пересчитаны именно из-за этой ошибки — если увидите старое число где-то ещё, пересчитывайте.

## 📋 Открытые заявки

Пусто на конец сессии — `list_feedback` возвращает `{items: []}`. Все реальные заявки этого раунда
разобраны и закрыты через `resolve_feedback` с честной запиской (в том числе один случай, где первая
починка оказалась no-op, и это явно признано в записке, не скрыто).

Один пункт НЕ починен намеренно, решение user: одна заявка про `save_preset`'s `author` из аргумента
вместо заголовка оказалась не багом ЭТОЙ зоны — на сервере заголовок побеждает (проверено живьём),
расхождение было на стороне клиента внешнего агента (не проставлял `X-User-Login` в той сессии).
User подтвердил «по заголовкам всё ок» — закрыто как не-баг.

Отдельно: `list_content` НЕ фильтруется по владельцу (все видят все наборы данных всех юзеров) — это
НЕ баг, осознанное решение user: «просмотр доступен всем, защита только на перезапись/удаление
чужого» — тот же симметричный принцип, что и у `list_presets`. Задокументировано в `docs/author.md`.
