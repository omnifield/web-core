# ❓ FAQ

Короткие ответы на конкретные вопросы, которые уже возникали по этому компоненту. Не общая
документация (она в [`README.md`](./README.md)) и не план (он в [`ROADMAP.yaml`](./ROADMAP.yaml))
— только факты, каждый проверен на практике.

---

### Почему `trigger` переименован в `control`, хотя настоящая Zag-анатомия называет его иначе?

**Коротко: тот же общий словарь кита, что у accordion/popover для «кликабельного, что открывает что-то» — одинаковый смысл называется одинаково во всём ките.**

`entity/anatomy.ts` вырезает родное имя Zag (`.omit("trigger", ...)`) и добавляет кит-имя
(`.extendWith("control")`) — тот же приём, что у `popover`
(`popoverAnatomy.omit("trigger", "indicator").extendWith(...parts.controlSet)`). `content` остаётся
родным именем Zag — оно уже совпадает со словарём, переименовывать нечего.

### Почему у диалога нет `controlIndicator`, хотя у accordion/popover control всегда идёт парой с ним?

**Коротко: у диалога нет своей стрелки/шеврона, и нет родной части Zag, которую можно было бы под неё переадресовать.**

`shared/data/anatomy.ts`'s `controlSet` — пара `control`+`controlIndicator`, но она подходит,
только когда есть РЕАЛЬНАЯ часть-поставщик под индикатор (у accordion/popover — их собственный
`itemIndicator`/`indicator`). В ките нет ни одного `controlIndicator`, выдуманного с нуля без
реальной части за ним — плодить первый такой прецедент без нужды не стали.

### Почему `backdrop`/`closeTrigger` — реальные части паспорта, но не экспортируются как компоненты?

**Коротко: они всегда рендерятся вместе с `content` и никогда не составляются потребителем отдельно — отдельный публичный компонент для них был бы абстракцией без единого кейса использования.**

Проверка была прямой: назвать хоть один случай, когда `backdrop` или `closeTrigger` нужны ОТДЕЛЬНО
от `content` — такого случая нет. `DialogContent` рендерит оба напрямую как `Ark`'s `DialogBackdrop`/
`DialogCloseTrigger` (`components/content/index.tsx`), без своих файлов-обёрток кита — карта кита
(`defineKitComponent`) указывает на эти же Ark-компоненты напрямую, не через лишний слой. Они
остаются НАСТОЯЩИМИ частями паспорта (свой `data-scope`/`data-part`, свой рецепт) — скин красит их
адресно, просто состав диалога потребитель не собирает вручную.

### Почему первая версия этой правки заводила отдельные файлы `backdrop.tsx`/`close-trigger.tsx`, а эта — нет?

**Коротко: ранняя версия скопировала форму accordion/popover (отдельный файл на часть) не проверив, есть ли у ЭТОЙ части хоть один независимый кейс использования — здесь его нет.**

У accordion/popover каждая часть — реальный строительный кубик, который потребитель кладёт в разных
местах разных композиций. `backdrop`/`closeTrigger` диалога — не кубики, а фиксированная механика
одного места: они существуют РОВНО там, где `content`, и больше нигде. Файл на часть оправдан,
когда часть — что-то, что реально собирают отдельно; когда нет — это лишняя обёртка, а не следование
конвенции кита.

### Почему живой рендер падал `useDialogContext returned undefined`, хотя юнит-тест был зелёным?

**Коротко: `components/index.ts`'s `defineKitComponent(passport, {...})` не передавал `Dialog` третьим аргументом — юнит-тест этого не ловил, потому что сам подставлял провайдера руками в свой `REGISTRY`, в обход настоящей карты кита.**

Причина не имела отношения к порталу вовсе — она существовала до всей этой правки. `kit-form.ts`'s
`provider` — то, чем `RenderTree` оборачивает корень, когда у компонента нет собственного DOM-узла
(тот же приём, что у `popover`/`menu`). Без третьего аргумента карта кита об этом не знала — живая
витрина падала, юнит-тест — нет, потому что сам обходил проверяемый путь. Найдено только живым
прогоном в реальном браузере (`chrome-devtools`, `/showcase/dialog/basic`) — jsdom-тест эту ошибку
поймать не мог, раз сам её обходил. Исправлено, тест переписан на `provider: dialogKit.provider`.

### Почему `role="alertdialog"` — это не просто смена атрибута для скринридера?

**Коротко: вместе с ролью меняется реальное поведение — фокус по умолчанию и закрытие кликом снаружи.**

Компонент читает `role` не только для `aria-`атрибута на самом узле — при `alertdialog` фокус по
умолчанию уходит на первый фокусируемый элемент внутри содержимого (обычно кнопку закрытия/отмены),
и клик снаружи диалог не закрывает. Оба поведения осмысленны для предупреждения об опасном действии.

### Почему клик по одному из нескольких `DialogControl` помечает именно его как `current`, хотя диалог один на всех?

**Коротко: `value` на каждом control — то же различение, что и у `drawer`/`popover` с несколькими триггерами.**

Машина хранит не «открыт/закрыт» само по себе, а ещё и то, какой конкретно control его открыл
(`triggerValue`) — `current` сравнивает собственный `value` с этим значением.
