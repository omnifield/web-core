# ❓ FAQ

Короткие ответы на конкретные вопросы, которые уже возникали по этому компоненту. Не общая
документация (она в [`README.md`](./README.md)) и не план (он в [`ROADMAP.yaml`](./ROADMAP.yaml))
— только факты, каждый проверен на практике.

---

### Почему у слайдера нет скрытого поля формы само собой, как у чекбокса?

**Коротко: так и задумано — потребитель кладёт его сам внутрь каждого бегунка.**

В отличие от чекбокса и переключателя (где скрытый `<input>` кладёт сам корень), слайдер этого не
делает — потребитель ставит его вручную внутри нужного бегунка. У диапазона (двух бегунков) может
понадобиться два разных поля с разными именами, и решение, сколько их и как назвать, оставлено
тому, кто собирает форму, а не угадано заранее.

### Почему текст значения в сборке не обновляется при перетаскивании?

**Коротко: в сборке это статичный снимок стартового значения, не живая привязка — так задумано.**

Статичное дерево сборки не может выразить «читать внутреннее состояние компонента по ходу
взаимодействия» — тот же класс ограничения, что у некоторых других живых частей кита. Сам слайдер
(дорожка, закраска, перетаскивание бегунка) при этом работает полностью настоящим состоянием —
неживой остаётся только эта одна часть. В реальном использовании текст значения читается
реактивно из контекста слайдера, не через сборку.

### Почему в рецепте почти нечего красить у позиции бегунка/деления/подсказки?

**Коротко: позицию целиком считает и выставляет сам слайдер — рецепту достаётся только вид.**

Расположение бегунка, конец закрашенной дорожки, место деления шкалы — всё это уже посчитано и
выставлено инлайн-стилем до того, как рецепт вообще начинает работать. Рецепт красит только то,
что поверх готовой позиции: цвет, размер, тень. Единственное реальное исключение — собственный
размер бегунка: слайдер его ИЗМЕРЯЕТ, значит рецепт обязан дать бегунку настоящий фиксированный
размер, а не переменную, иначе измерять было бы нечего.
