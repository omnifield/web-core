<h2 id="быстрый-старт">⚡ Быстрый старт</h2>

```bash
pnpm install     # поставит зависимости и соберёт оснастку, без которой не поднимется остальное
pnpm build       # соберёт все пакеты в правильном порядке
pnpm test        # прогонит пробы
```

Нужны **Node 24** и **pnpm 11**. Менеджер пакетов удобнее включать через `corepack enable` —
тогда версия берётся из манифеста, а не из того, что оказалось на машине.

⚠️ Первая команда — обязательно `pnpm install`, и обязательно **из корня**. На установке
собирается оснастка (конфиги сборки, пресет проб, канон линтера): без неё остальные пакеты не
конфигурируются, потому что берут её готовой. Запуск из подпапки возьмёт не тот корень и заведёт
второе дерево зависимостей — в нём окажется вторая копия реактивного движка, и всё, что стоит на
машинах состояний, начнёт падать с невнятными ошибками про недоступный контекст.

<h2 id="команды">🧰 Команды</h2>

Все цели гоняются графом задач: он сам считает порядок и не пересобирает то, что не менялось.

```bash
pnpm build       # сборка всех пакетов
pnpm test        # пробы
pnpm lint        # линтер плюс проверка типов
pnpm typecheck   # только проверка типов
pnpm graph       # граф зависимостей в браузере
```

Один пакет — фильтром по имени:

```bash
pnpm --filter @web-core/ui test
pnpm --filter @web-core/skin build
```

🔍 Граф знает, что одни пакеты нужны другим: проба кита сначала соберёт то, от чего он зависит.
Поэтому `pnpm test` из корня и «зайти в папку пакета и запустить там» — не одно и то же: второй
способ берёт соседей такими, какими они лежат на диске, и легко ловит устаревшую сборку.

<h2 id="дерево">🧱 Как устроено дерево</h2>

В корне — сами пакеты, по папке на каждый, плюс рабочая папка выпуска. Ни приложений, ни
демо-стендов здесь нет: это база, которую ставят себе другие.

| папка | что там |
|---|---|
| `ui` | примитивы интерфейса: 1-to-1 DOM, ноль стилей по умолчанию, паспорт компонента |
| `skin` | модель скина: рецепт, адресация из анатомии, порождение CSS, надевание |
| `style` | токен-контракт, шкалы, построение половин из семени |
| `assembly` | дерево узлов, реестр из паспортов, отрисовка по данным |
| `form` | валидация и жизнь формы поверх дерева сборки |
| `store` · `query` · `router` | состояние, данные из сети, роутинг |
| `io` | универсальный вход/выход данных, граница схем |
| `solid` | единственная точка резолва реактивного движка плюс монтирование приложения |
| `build` · `lint` · `cli` | оснастка: конфиги сборки, каноны проверки, движок командных тулзов |
| `generators` · `mcp` · `trace` · `neurobox` | генерация шаблонов, тулинг MCP-серверов, трейсы, рантайм агента |

У каждой папки своя тройка `README.md` / `FAQ.md` / `ROADMAP.yaml` — устройство, обоснования и
план живут там, а не здесь.

<h2 id="связи">🔗 Как пакеты видят друг друга</h2>

Внутри этого репозитория соседи берутся **протоколом воркспейса** (`workspace:*`), а не номером
версии: правка в одном пакете видна другому сразу, без выпуска. При упаковке протокол сам
подменяется реальной версией, так что публикацию это не ломает.

🧩 Реактивный движок резолвится **только через пакет `solid`** — остальные берут его оттуда, а не
напрямую. Это не стиль: как только в дереве оказывается две копии движка, контекст одной невидим
для другой, и рушится всё, что стоит на машинах состояний. Одна точка резолва делает такую
ситуацию невозможной.

🚚 Вся группа держится на **одной версии**: бампается один пакет — бампаются все. Разойтись по
совместимости между собой они физически не могут, и матрицу версий держать в голове не нужно.

⚠️ Обратная сторона, о которой важно знать заранее: **внутри репозитория поверхность поставки не
проверяется вовсе** — она подменена ссылками на соседние папки. Забытый в поставке файл, неверное
условие резолва, разошедшийся диапазон зависимости — изнутри не видно ничего: сборка зелёная,
пробы зелёные, а у того, кто поставил пакет из реестра, ничего не работает. Единственная
настоящая проверка — установить опубликованный пакет в чистый проект и собрать его там.

<h2 id="выпуск">🚚 Выпуск</h2>

Сценарий живёт рабочей папкой [`.release/`](./.release/README.md) — четыре шага, каждый своей
командой: план → версии → публикация → приёмка. Порядок и условия перехода между шагами описаны
в [`FLOW.md`](./.release/FLOW.md).

Адрес реестра и токен приходят переменными окружения, а не записаны в коде: одни и те же скрипты
работают в любом репозитории, различаются только переменные.
