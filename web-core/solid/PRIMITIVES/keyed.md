# 🔑 `keyed` — поток по названному ключу

Взятый примитив комьюнити. Здесь его полный разбор: что даёт, как звать, где грабли. Короткая
вводка и место среди остального — [`EXAMPLES.md`](../EXAMPLES.md), раздел «Примитивы».

## 🪪 Паспорт

| | |
| --- | --- |
| **Адрес импорта** | `@web-core/solid/keyed` |
| **Вендор** | [`@solid-primitives/keyed`](https://github.com/solidjs-community/solid-primitives/tree/main/packages/keyed) · [доки](https://primitives.solidjs.community/package/keyed/) |
| **Версия на момент взятия** | `1.5.3`, peer `solid-js ^1.6.12`, своих зависимостей нет |
| **Форма подключения** | полный реэкспорт, отдельным подпутём — не в барели `.` |
| **Повод взять** | нужен `<Key each by>` для списков, которые перестраиваются новыми объектами |
| **Когда сверялись с рынком** | 2026-09-19 |
| **Чем подтверждено** | `test/keyed.test.tsx` — рендер в JSDOM, а не смоук на «экспорт есть» |

Почему взяли готовое, почему отдельный подпуть и почему обычная зависимость, а не peer, —
[`FAQ.md`](../FAQ.md), раздел «Поток по ключу».

## 🎯 Зачем он вообще

Список приехал с сервера заново. Объекты в нём **новые**, а `id` те же.

- `<For>` опознаёт элемент **по ссылке** на объект. Объекты новые → для него это другой список: он
  сносит узлы и строит заново. Уходит фокус в поле, выделение, открытая строка, позиция скролла
  внутри строки.
- `<Index>` опознаёт **по позиции**. Переживает подмену объектов, но ломается на сортировке и
  вставке в середину — там позиция и есть то, что изменилось.
- `<Key>` опознаёт **по значению, которое ты сам назвал ключом**. Узел за ключом переживает
  перестройку, а внутрь него приезжает новое значение.

Практический признак, что нужен именно он: **после обновления списка слетает фокус или выделение**,
хотя данные почти те же.

## 📦 Состав подпути

Шесть экспортов, все из вендора один в один.

| Экспорт | Сигнатура | Про что |
| --- | --- | --- |
| `Key` | `(props: { each?, by, fallback?, children }) => JSX.Element` | список по ключу |
| `Entries` | `(props: { of, fallback?, children }) => JSX.Element` | обход объекта |
| `MapEntries` | `(props: { of, fallback?, children }) => JSX.Element` | обход `Map` |
| `SetValues` | `(props: { of, fallback?, children }) => JSX.Element` | обход `Set` |
| `Rerun` | `(props: { on, children }) => JSX.Element` | перестроить кусок по триггеру |
| `keyArray` | `(items, keyFn, mapFn, options?) => Accessor<U[]>` | то же, что `Key`, но без JSX |

## `<Key>`

```tsx
import { Key } from "@web-core/solid/keyed";

<Key each={props.items} by={props.itemKey}>
  {(item) => <Node value={props.itemKey(item())} />}
</Key>;
```

Точная форма пропсов:

| Проп | Тип | Обязателен |
| --- | --- | --- |
| `each` | `readonly T[] \| null \| false` | нет — пусто значит `fallback` |
| `by` | `keyof T \| ((item: T) => unknown)` | **да** |
| `fallback` | `JSX.Element` | нет — без него на пустом не рисуется ничего |
| `children` | `(item: Accessor<T>, index: Accessor<number>) => JSX.Element` | **да** |

**Главное про тело: `item` — сигнал, а не значение.** Узел за ключом остаётся тем же объектом DOM,
а внутрь приезжает новое значение — поэтому `item()`, и поэтому деструктурировать аргумент нельзя.
Индекс — тоже сигнал:

```tsx
<Key each={rows()} by="id" fallback={<p>Пусто</p>}>
  {(row, index) => (
    <tr data-index={index()}>
      <td>{row().title}</td>
    </tr>
  )}
</Key>
```

`each` принимает `null` и `false`, не только массив — удобно для `each={ready() && rows()}`.

## `by` — строкой и функцией

`by` отвечает на вопрос «по чему считать, что это тот же элемент».

```tsx
// Ключ лежит полем объекта — короткая форма.
<Key each={users()} by="id">{(user) => <UserCard user={user()} />}</Key>

// Ключ составной или вычисляемый — функция.
<Key each={cells()} by={(cell) => `${cell.row}:${cell.col}`}>
  {(cell) => <Cell value={cell().value} />}
</Key>

// Ключ приходит снаружи — функция пропсом.
<Key each={props.items} by={props.itemKey}>{(item) => <Node value={item()} />}</Key>
```

Выбор ключа — решение, а не формальность: **поменялось значение ключа = это другой элемент**, узел
снесут и построят заново. Поэтому индекс в массиве ключом не годится (сортировка порвёт всё), а
поле, которое юзер может отредактировать, годится только если пересоздание строки на такую правку
— это правда то, чего ты хочешь.

## `keyArray` — то же без JSX

Под `<Key>` лежит обычный реактивный примитив. Нужен, когда сопоставление по ключу требуется не для
разметки: производные модели, кэш по строке, предвычисленные объекты.

```ts
import { createSignal } from "@web-core/solid";
import { keyArray } from "@web-core/solid/keyed";

type Row = { id: string; title: string };

const [rows, setRows] = createSignal<Row[]>([{ id: "a", title: "первый" }]);

const views = keyArray(
  rows,                                  // Accessor списка
  (row) => row.id,                       // чем опознаём элемент
  (row) => ({                            // row — СИГНАЛ; тело зовётся один раз на ключ
    id: row().id,
    shout: () => row().title.toUpperCase(),
  }),
);

views()[0]!.shout();                     // "ПЕРВЫЙ"
setRows([{ id: "a", title: "первый, но другой объект" }]);
views()[0]!.shout();                     // "ПЕРВЫЙ, НО ДРУГОЙ ОБЪЕКТ" — объект view тот же
```

Проверено прогоном: при подмене объекта с тем же ключом функция сопоставления **не зовётся второй
раз** — переиспользуется уже созданное, меняется только значение внутри сигнала. Ровно это свойство
и даёт `<Key>` его смысл.

Зовётся внутри реактивного владельца (компонент или `createRoot`), как любой примитив Solid.
Четвёртым аргументом принимает `{ fallback }` — аксессор значения для пустого списка.

## `<Entries>` / `<MapEntries>` / `<SetValues>`

Для случаев, когда источник не массив. Сигнатура тела у каждого своя — стоит свериться, а не
гадать:

```tsx
import { Entries, MapEntries, SetValues } from "@web-core/solid/keyed";

// Объект: ключ — ОБЫЧНАЯ строка, значение — сигнал.
<Entries of={settings()} fallback={<p>Настроек нет</p>}>
  {(key, value) => <Row label={key} value={value()} />}
</Entries>

// Map: ключ обычный (любого типа), значение — сигнал.
<MapEntries of={cache()}>
  {(key, value, index) => <Row index={index()} label={String(key)} value={value()} />}
</MapEntries>

// Set: значение обычное, сигнал только индекс — у множества менять значение негде.
<SetValues of={tags()}>{(tag) => <Tag name={tag} />}</SetValues>
```

Запомнить проще так: **сигналом приходит то, что может измениться, не меняя тождества элемента.**
У объекта и `Map` это значение под ключом; у `Set` значение и есть ключ, поэтому оно обычное.

Все три принимают `undefined`/`null`/`false` в `of` и рисуют на них `fallback`.

## `<Rerun>` — перестроить по триггеру

Обратная задача: не «сохрани узлы», а «снеси и построй заново, когда изменилось вот это». Нужно для
некооперативных вещей — сторонний виджет, `<canvas>`, компонент с неуправляемым внутренним
состоянием, который проще пересоздать, чем синхронизировать.

```tsx
import { createSignal } from "@web-core/solid";
import { Rerun } from "@web-core/solid/keyed";

const [theme, setTheme] = createSignal("dark");

<Rerun on={theme}>
  {(now, was) => {
    console.log("перестроились", was, "→", now);
    return <ThirdPartyChart theme={now} />;
  }}
</Rerun>;
```

Тело получает **новое значение и предыдущее** (`undefined` на первом проходе) — проверено прогоном.
`on` принимает аксессор, массив аксессоров (`on={[theme, locale]}`) или просто значение. Телом
может быть и не функция, а сразу JSX, если предыдущее значение не нужно.

## 🧭 Что когда: `<For>` / `<Index>` / `<Key>`

| Берём | Элемент опознаётся | Сигналом приходит | Когда это правильный выбор |
| --- | --- | --- | --- |
| `<For>` | по **ссылке** на объект | индекс | список живёт в сторе и мутируется на месте; объекты стабильны |
| `<Index>` | по **позиции** | значение | позиция и есть смысл: нумерованные слоты, фиксированная сетка, список примитивов |
| `<Key>` | по **названному ключу** | значение и индекс | список перестраивается новыми объектами: ответ сервера, `JSON.parse`, пересборка из другого источника |

`<For>` и `<Index>` берутся из барели движка (`@web-core/solid`), `<Key>` — отсюда. Разные подпути,
потому что разное происхождение, а не потому что разное назначение.

Обратный признак — `<Key>` не нужен: список приходит из стора, где элементы правят на месте. Тогда
`<For>` дешевле, а ключа просто нет.

## 🪤 Грабли

- **Деструктуризация убивает реактивность.** `const { title } = item()` читает значение один раз,
  навсегда. Читать надо там, где значение используется.
- **Ключ поменялся — элемент другой.** Это не оптимизация, которую можно «настроить»: сменившийся
  ключ означает пересоздание узла по определению.
- **Не обновляется вообще ничего** — почти всегда условия резолва, а не этот примитив:
  `solid-js/web` без `development`/`browser` отдаёт серверную сборку с разовым рендером. Разбор —
  [`EXAMPLES.md`](../EXAMPLES.md), кейс 11.
