<h2 id="главное">🏠 Главное</h2>

🔍 Единственный шаг выпуска, которого нет в графе задач: поставить **опубликованные** пакеты в
чистый проект **вне репозитория**, импортировать каждый подпуть из `exports` и проверить типы.

Зачем отдельный шаг. Внутри репозитория поверхность поставки не проверяется вовсе — она подменена
ссылками на соседние папки. Забытый в поставке файл, неверное условие резолва, разошедшийся
диапазон зависимости изнутри невидимы: сборка зелёная, пробы зелёные, а у того, кто поставил
пакет из реестра, ничего не работает. Ответ на вопрос «а у потребителя оно работает» даёт только
установка со стороны.

🔁 Шаг одинаков в любом репозитории, где лежит эта группа: различаются [переменные](#переменные),
а не код.

<h2 id="команда">🚀 Команда</h2>

```bash
pnpm --filter @web-core/release release verify [--json]
```

| Ключ | Что делает |
|---|---|
| `--only <пакет>` | проверить один пакет вместо всей группы |
| `--no-types` | без проверки типов — быстрее |
| `--registry <url>` | откуда ставить; по умолчанию — реестр из окружения |

Коды возврата: `0` — сделано или делать нечего, `1` — отказ, `2` — команду позвали неверно.
`--json` отдаёт ответ одним конвертом: `outcome` (`done` / `nothing` / `failed`), `summary` для
человека и `data` с отчётом по каждому пакету.

⚠️ Отчёт читают глазами, а не принимают за светофор — часть отказов это ограничения самой пробы.
Как отличить настоящий от ложного — [`FLOW.md`](./FLOW.md).

<h2 id="переменные">🎚️ Переменные</h2>

| Переменная | Что задаёт | По умолчанию |
|---|---|---|
| `NPM_CONFIG_REGISTRY` (или `--registry`) | откуда ставить при приёмке | реестр из окружения |
| токен реестра | доступ к приватным пакетам | строка в ПОЛЬЗОВАТЕЛЬСКОМ `~/.npmrc` или шаг пайплайна |

⚠️ Токен нельзя положить в `.npmrc` репозитория даже переменной: pnpm 11 не разворачивает
переменные в учётных данных из project-level файла и отказывает предупреждением — файл
коммитится, и секрет утёк бы в чужой реестр.

<h2 id="устройство">🧩 Устройство</h2>

| Файл | Что держит |
|---|---|
| `src/index.ts` | объявление команды и запуск программы |
| `src/verify.ts` | приёмка: проба поставки по каждому публикуемому пакету |
| `src/workspace.ts` | какие пакеты воркспейса вообще публикуются |
| `src/run.ts` | запуск внешней команды с захватом вывода |
| `src/root.ts` | поиск корня воркспейса — от него работают рекурсивные команды |

<h2 id="нет">🚪 Чего здесь нет</h2>

- **Версий, CHANGELOG и публикации** — это делает граф задач штатно (`nx.json`, секция `release`):
  фиксированная группа, планы версий как источник, подмена ссылок на соседей при публикации.
  Раньше здесь лежали свои шаги поверх менеджера пакетов — они дублировали готовое, а план
  выпуска собирался разбором человеческого текста регуляркой.
- **Тегов, релизов и мержа** — они на стороне репозитория и его пайплайна.
- **Знания о конкретном реестре** — адрес приходит переменной, а не записан в коде.
