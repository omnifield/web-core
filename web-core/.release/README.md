<h2 id="главное">🏠 Главное</h2>

🔍 Приёмка проверяет **опубликованные** пакеты со стороны потребителя: ставит каждый из реестра в
пустой проект во временной папке, импортирует все подпути, которые пакет объявил в `exports`, и
проверяет типы.

Зачем это отдельным шагом, а не очередной проверкой в репозитории. Внутри репозитория пакеты
соединены ссылками на соседние папки, и поверхность поставки не участвует в работе вообще:
`exports`, список файлов в тарболе, условия резолва, диапазоны зависимостей. Ошибка в любом из них
изнутри невидима — сборка и пробы зелёные, а у того, кто поставил пакет из реестра, ничего не
работает. Установка со стороны — единственный способ это увидеть.

<h2 id="команда">🚀 Команда</h2>

```bash
pnpm --filter @web-core/release release verify [--json]
```

| Ключ | Что делает |
|---|---|
| `--registry <url>` | откуда ставить; по умолчанию берётся `NPM_CONFIG_REGISTRY` из окружения |
| `--only <пакет>` | проверить один пакет вместо всей группы |
| `--no-types` | пропустить проверку типов |
| `--json` | отдать отчёт машиночитаемо, одним конвертом |

Коды возврата: `0` — принято либо проверять нечего, `1` — отказ, `2` — команду позвали неверно.

⏱️ Каждому пакету — своя установка в свой чистый проект, поэтому полный прогон идёт около десяти
минут. На отладке берите `--only`.

<h2 id="проверка">🔬 Что именно проверяется</h2>

По каждому пакету проба проходит одни и те же шаги, и каждый виден в отчёте отдельной записью со
своей командой, временем и выводом:

| Шаг | Что делает | Что ловит |
|---|---|---|
| `install` | ставит пакет из реестра в пустой проект | пакета нет в реестре, не тот адрес, нет прав, неразрешимая зависимость |
| `install-peers` | доставляет peer-зависимости, объявленные пакетом | — (подготовка к импорту) |
| `import` | импортирует **каждый** подпуть из `exports` установленного пакета | подпуть ведёт в файл, которого нет в тарболе; импорт папки без входа; забытая зависимость |
| `typecheck` | `tsc --noEmit` на тех же подпутях | типы не поставлены или не разрешаются из `dist` |

Подпути берутся **у установленного пакета**, а не из репозитория: проверяется ровно то, что
получил потребитель.

<h2 id="отчёт">📋 Как читать отчёт</h2>

`--json` отдаёт один конверт: `outcome` (`done` / `nothing` / `failed`), `summary` для человека и
`details` с разбором по каждому пакету.

Ключевое свойство: **проба сама различает дефект поставки и собственный предел** — руками
сортировать отказы не нужно. Итог каждого подпути лежит в его `verdict`:

| Итог | Что это | Красит приёмку? |
|---|---|---|
| `ok` | подпуть встал и импортировался | — |
| `delivery-broken` | подпуть ведёт в никуда: файла нет в тарболе, условие резолва не сработало, импортируется папка без входного файла | 🔴 да |
| `dependency-undeclared` | пакету нужен чужой модуль, которого он не объявил зависимостью | 🔴 да |
| `peer-missing`, обязательный | объявленная обязательной peer-зависимость не встала | 🔴 да |
| `foreign-broken` | отказ случился в файле чужого пакета, а не нашего | 🔴 да |
| `peer-missing`, необязательный | необязательный peer не поставлен — это контракт пакета | 🟡 нет |
| `node-refused` | Node отказался выполнять подпуть | 🟡 нет |

🟡 **Жёлтое — не дефект, а граница пробы.** Импорт идёт голым Node, и часть поставки так не
импортируется по своей природе: браузерный подпуть обращается к DOM, подпуть с файлом стилей или
конфигом вообще не модуль, необязательный peer потребитель ставит сам. Такие подпути собраны в
списке `limited`, причина названа в их `blocker`.

🔴 **Красное** собрано в списке `broken`. Каждая запись несёт `blocker` с кодом отказа, тем, кто
отказал (`culprit`), и тем, через кого до него дошли (`importedBy`), — по ним видно, чей это
дефект.

🔁 Временный проект каждой пробы **остаётся на диске**, путь указан в отчёте (`projectDir`). Там
всё воспроизводится руками — командой из поля `remedy`.

<h2 id="переменные">🎚️ Переменные</h2>

| Переменная | Что задаёт | По умолчанию |
|---|---|---|
| `NPM_CONFIG_REGISTRY` (или `--registry`) | откуда ставить пакеты при проверке | реестр из окружения |
| токен реестра | доступ, если пакеты приватные | строка `//<хост>/:_authToken=…` в пользовательском `~/.npmrc` или шаг пайплайна |

⚠️ Адреса реестра нет ни в одном файле репозитория — ни в манифестах пакетов, ни в конфиге
менеджера. Он приходит переменной: одни и те же скрипты работают в любом окружении.

⚠️ Токен не кладут в `.npmrc` репозитория даже через переменную: pnpm не разворачивает переменные
в учётных данных из файла проекта. Файл коммитится — секрет уехал бы вместе с ним.

<h2 id="устройство">🧩 Устройство</h2>

| Файл | Что держит |
|---|---|
| `src/index.ts` | объявление команды и запуск программы |
| `src/verify.ts` | проход по пакетам группы и сборка общего исхода |
| `src/workspace.ts` | какие пакеты воркспейса публикуются, а какие нет |
| `src/root.ts` | поиск корня воркспейса |
| `src/run.ts` | запуск внешней команды с захватом вывода |

Сама проба живёт не здесь: она механика общего назначения и лежит в
[`@web-core/cli`](../cli/README.md), подпуть `/probe`. Здесь остаётся только знание, специфичное
для этой группы: какие пакеты публикуются и что считать принятой поставкой.

<h2 id="нет">🚪 Чего здесь нет</h2>

- **Версий, CHANGELOG, коммита, тега и публикации** — всё это делает граф задач штатными
  средствами, настройка в `nx.json`, секция `release`. Порядок шагов — [`FLOW.md`](./FLOW.md).
- **Адреса реестра** — приходит переменной, в коде его нет.
