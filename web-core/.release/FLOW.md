# 🧭 Порядок выпуска

Как пакеты `@web-core/*` попадают в реестр: что делает каждый шаг, чем он запускается и что
меняет в репозитории. Тем же порядком устроен пайплайн в `.gitlab-ci.yml`.

- 🧱 [Как устроено](#устройство)
- 🔑 [Что нужно подготовить](#нужно)
- 🚦 [Шаги](#шаги)
- 🧯 [Если что-то пошло не так](#ошибки)

<h2 id="устройство">🧱 Как устроено</h2>

Версии, CHANGELOG, коммит, тег и публикацию делает **граф задач** — настройка в `nx.json`, секция
`release`. Он знает зависимости между пакетами, считает порядок сам и при упаковке подставляет
вместо ссылок на соседей их реальные версии.

Два свойства заданы конфигом, и от них зависит всё остальное:

- 📦 **фиксированная группа** — пакеты выпускаются одной версией. Поднимается один — поднимаются
  все семнадцать, включая те, где правок не было. Взамен между ними не бывает вопроса
  совместимости;
- 📝 **планы версий** — изменение объявляется файлом в ветке, а не угадывается по тексту коммитов.
  Нет ни одного плана — выпускать нечего, и выпуск честно отвечает, что менять ничего не будет.

Последний шаг — [приёмка](./README.md) — единственный, которого в графе нет: это взгляд со стороны
потребителя, а не операция над репозиторием.

<h2 id="нужно">🔑 Что нужно подготовить</h2>

| | |
|---|---|
| Node и pnpm | версии объявлены в корневом `package.json` (`engines`, `packageManager`); `corepack enable` берёт их оттуда |
| Адрес реестра | переменная `NPM_CONFIG_REGISTRY` — в файлах репозитория адреса нет ни одного |
| Токен на запись в реестр | строкой `//<хост>/:_authToken=…` в пользовательском `~/.npmrc` либо шагом пайплайна |
| Токен с правом пуша | шаг подъёма версий отправляет коммит и тег в основную ветку |

⚠️ Токен не кладут в `.npmrc` самого репозитория даже через переменную: pnpm не разворачивает
переменные в учётных данных из файла проекта. Файл коммитится — секрет уехал бы вместе с ним.

Две вещи, без которых шаги ведут себя странно, а не падают:

- команды запускаются **из корня репозитория** — рекурсивные операции и выбор пакетов идут от
  корня воркспейса, из подпапки возьмётся другой набор;
- клон нужен **с полной историей** (`GIT_DEPTH: "0"`, `fetch-depth: 0`): «затронутое» считается
  сравнением с целевой веткой, и мелкому клону не с чем сравнивать.

<h2 id="шаги">🚦 Шаги</h2>

### 1️⃣ Объявить изменение

Делает разработчик в своей ветке, не выпускающий:

```bash
pnpm plan
```

Команда спрашивает, насколько поднять версию и что написать в CHANGELOG, и кладёт файл плана в
`.nx/version-plans/`. Файл едет в ветке рядом с кодом; на выпуске он превращается в записи
CHANGELOG и удаляется.

Наличие плана проверяется отдельно — чтобы выяснить это на merge request, а не на выпуске:

```bash
nx release plan:check
```

Возврат `0`, когда планы на месте или трогать нечего; `1` — и тогда команда перечисляет поимённо
пакеты, которые изменение задело, а плана на них нет.

### 2️⃣ Проверки

В ветке считается **только затронутое**: граф сравнивает её с целевой и берёт пакеты, до которых
изменение дотянулось, вместе с их зависимыми. Достаёт он далеко — правка в пакете, на котором
стоит оснастка, тянет за собой почти всю группу.

```bash
nx affected -t lint typecheck test --base=origin/<целевая> --head=HEAD
```

В основной ветке — **всё целиком**, без выборки: она обязана быть зелёной вся, а не частично.

```bash
nx run-many -t lint typecheck test build
```

### 3️⃣ Сухой прогон

```bash
nx release --dry-run
```

Считает всё и не пишет ничего: ни файлов, ни коммита, ни тега, ни публикации. Печатает, какая
версия получится, из каких планов она собрана и что попадёт в CHANGELOG каждого пакета. Стоит
прогонять перед каждым выпуском.

### 4️⃣ Поднять версии

```bash
nx release --skip-publish
git push --follow-tags
```

Шаг переписывает версию в манифесте каждого пакета группы, дописывает CHANGELOG каждому и общий,
удаляет использованные планы версий, обновляет файл блокировки, делает коммит
`chore(release): publish <версия>` и ставит на него тег `v<версия>`.

Запускается человеком, а не по каждому коммиту: поднять версию — решение, а не событие.
Публикации здесь нет намеренно, **тег и есть сигнал к ней**.

⚠️ Незакоммиченные правки рядом шаг не останавливают и в релизный коммит не забирает — он
добавляет в индекс только то, что изменил сам. Но и предупреждения об этом не будет: следить, что
в дереве лежит, придётся самому.

⚠️ Ключи `--skip-publish` и `-y` взаимоисключающие: вместе команда откажется разбирать аргументы.

### 5️⃣ Опубликовать

Запускается **по тегу**:

```bash
nx run-many -t build
nx release publish
```

🔨 Сборка обязательна. В реестр уезжает содержимое `dist`, и отдельного шага, который соберёт его
перед публикацией, нет: пропустите — уедет то, что лежало с прошлого раза.

На каждый пакет команда печатает строку `Published to <реестр> with tag "latest"` — семнадцать
строк и есть подтверждение, что уехала вся группа. Повторный запуск безопасен: уже опубликованные
версии пропускаются.

### 6️⃣ Принять поставку

```bash
pnpm --filter @web-core/release release verify --registry "$NPM_CONFIG_REGISTRY"
```

Ставит опубликованные пакеты в пустые проекты **вне репозитория** и проверяет, что они там
поднимаются. Единственный шаг, отвечающий на вопрос «а у потребителя оно работает»: внутри
репозитория пакеты подменены ссылками на соседние папки, и поверхность поставки не участвует в
работе вовсе.

⏱️ Идёт около десяти минут на всю группу — каждому пакету своя установка. Отчёт читается глазами,
а не как светофор; как именно — [`README.md`](./README.md).

<h2 id="ошибки">🧯 Если что-то пошло не так</h2>

| Симптом | Что это значит |
|---|---|
| «нет изменений в планах версий» | планов нет — выпускать нечего, это не ошибка |
| `ERR_PNPM_NO_LOCKFILE` на установке | файла блокировки нет: он лежит в репозитории, проверьте, что клон полный |
| установка отказывает на `--frozen-lockfile` | блокировка разошлась с манифестами: `pnpm install --lockfile-only` и закоммитить результат |
| `nx release plan:check` вернул `1` | перечисленные им пакеты изменение задело, а плана на них нет |
| «затронутое» захватывает слишком много | либо клон без полной истории, либо правка и правда в пакете, на котором стоит вся группа |
| публикация отказывает | нет прав или реестр недоступен; повторить безопасно |
| приёмка ставит пакеты не из того реестра | адрес не задан: `NPM_CONFIG_REGISTRY` или ключ `--registry` |
| приёмка отказывает | смотреть отчёт: бывает и дефект поставки, и граница самой пробы |
