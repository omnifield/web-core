# 🧭 Флоу выпуска — что делает девопс

Порядок, которым выпускаются пакеты `@web-core/*`. Готовый пайплайн — `.gitlab-ci.yml` в корне;
здесь то же самое словами, плюс то, обо что реально спотыкаются.

## 📦 Чем это сделано

Версии, CHANGELOG и публикацию делает **граф задач** штатными средствами: он знает зависимости
между пакетами, считает порядок сам и умеет подменять ссылки на соседей реальными версиями при
публикации. Настройка — `nx.json`, секция `release`.

Своим остался **один шаг — приёмка** (`.release/`): поставить опубликованное в чистый проект вне
репозитория и убедиться, что оно там работает. Такой проверки в графе нет, а изнутри репозитория
она невозможна в принципе — там пакеты подменены ссылками на соседние папки.

Два свойства выпуска, заданные конфигом:

- **фиксированная группа** — все пакеты поднимаются одной версией; бампается один, бампаются все;
- **планы версий** — изменение объявляется файлом, а не угадывается по тексту коммитов.

## 🔑 Что нужно до первого запуска

|                        |                                                                |
| ---------------------- | -------------------------------------------------------------- |
| Адрес реестра          | `NPM_CONFIG_REGISTRY` (или `--registry` у приёмки)             |
| Токен на запись        | строка в **пользовательском** `~/.npmrc` либо шаг пайплайна    |
| Токен с правом пуша    | для шага выпуска: он пушит коммит версий и тег в основную ветку |

> [!IMPORTANT]
> **Токен нельзя класть в `.npmrc` репозитория даже через переменную.** pnpm 11 не разворачивает
> переменные в учётных данных из project-level файла и отказывает предупреждением: файл
> коммитится, и секрет утёк бы в чужой реестр.

> [!IMPORTANT]
> **Все команды запускаются из КОРНЯ репозитория**, и истории нужен полный клон: «затронутое»
> считается сравнением с целевой веткой, а мелкий клон не даёт от чего отмерять.

## 🚦 Порядок

### 1. Объявить изменение — это делает разработчик, не девопс

```bash
pnpm plan          # спросит пакеты и вид подъёма, создаст файл плана версии
```

Файл ложится в `.nx/version-plans/` и едет в ветке вместе с кодом. Нет плана — нечего выпускать,
и пайплайн честно заканчивается, а не падает. На merge request это проверяется отдельным шагом.

### 2. Проверки

На ветке считается **только затронутое** — граф сравнивает её с целевой и берёт пакеты, до
которых изменение реально дотянулось, вместе с зависимыми:

```bash
nx affected -t lint typecheck test --base=origin/<целевая> --head=HEAD
```

На основной ветке — **всё целиком**: она обязана быть зелёной вся, а не в затронутой части.

```bash
nx run-many -t lint typecheck test build
```

### 3. Посмотреть, что выпустится

```bash
nx release --dry-run
```

Считает всё и **не пишет ничего**: ни файлов, ни коммитов, ни тегов, ни публикации. Печатает,
какая версия получится и из каких планов. Перед настоящим выпуском стоит прогонять всегда.

### 4. Поднять версии — решение человека, а не событие

```bash
nx release --skip-publish
git push --follow-tags
```

Шаг меняет манифесты, пишет CHANGELOG, делает коммит и тег. Публикации здесь нет намеренно:
**тег и есть сигнал** к ней. Требует чистого рабочего дерева — в пайплайне после checkout оно
чистое, руками своё коммитят до выпуска.

### 5. Опубликовать — по тегу

```bash
nx run-many -t build     # публикуется dist, и никто не соберёт его за вас
nx release publish
```

Сборка обязательна и её легко забыть: пропустили — в реестр уедет прошлая версия содержимого,
а то и пустота. Повторный запуск, когда всё уже опубликовано, безопасен.

### 6. Принять поставку

```bash
pnpm --filter @web-core/release release verify --json
release verify --only @web-core/io    # один пакет
release verify --no-types             # без проверки типов, быстрее
```

Единственный шаг, отвечающий на вопрос «а у потребителя оно вообще работает».

⚠️ **Читайте отчёт глазами, светофором этот шаг пока не считайте.** Проба строже, чем нужно:
часть отказов — её собственные ограничения, а не поломка поставки. Браузерный пакет голым `node`
импортировать нельзя по природе; подпуть, отдающий файл (стили, конфиг), модулем не является;
опциональная зависимость честно требует, чтобы её поставил потребитель, а проба этого не делает.

Отличить одно от другого несложно: отчёт несёт шаги и путь к временному проекту, где всё
воспроизводится руками. Отказ, который повторяется в обычном потребительском сценарии, —
настоящий; отказ, исчезающий при сборке бандлером или после установки недостающей зависимости, —
ограничение пробы.

## 🧯 Если что-то пошло не так

| Симптом | Что значит |
|---|---|
| «нет изменений в планах версий» | планов нет — выпускать нечего, это не ошибка |
| отказ на подъёме версий, «дерево не чистое» | в дереве незакоммиченные правки |
| отказ на публикации | нет прав (токен) или реестр недоступен — повторить безопасно |
| отказ на приёмке | возможна поломка поставки, но бывает и ограничение пробы — смотреть шаги и повторять руками |
| «затронутое» считает слишком много | клон мелкий, нет общего предка с целевой веткой — нужна полная история |
