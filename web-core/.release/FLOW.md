# 🧭 Порядок выпуска

Как пакеты `@web-core/*` попадают в реестр. Готовый пайплайн лежит в корне
(`.gitlab-ci.yml`) — здесь то же самое словами, с пояснениями, зачем каждый шаг.

- 🧱 [Как устроено](#устройство)
- 🔑 [Что нужно до первого выпуска](#нужно)
- 🚦 [Шаги](#шаги)
- 🧯 [Если что-то пошло не так](#ошибки)

<h2 id="устройство">🧱 Как устроено</h2>

Версии, CHANGELOG и публикацию делает **граф задач** (настройка — `nx.json`, секция `release`).
Он знает зависимости между пакетами, считает порядок сам и при публикации подставляет вместо
ссылок на соседей их реальные версии.

Два свойства, заданные конфигом и важные для понимания остального:

- 📦 **фиксированная группа** — все пакеты выпускаются одной версией. Поднимается один — значит
  поднимаются все, включая те, где правок не было. Взамен между ними не бывает вопроса
  совместимости;
- 📝 **планы версий** — изменение объявляется файлом в ветке, а не угадывается по тексту
  коммитов. Пока плана нет, выпускать нечего.

Отдельно от графа стоит последний шаг — [приёмка](./README.md): проверка опубликованного со
стороны потребителя.

<h2 id="нужно">🔑 Что нужно до первого выпуска</h2>

| | |
|---|---|
| Адрес реестра | переменная `NPM_CONFIG_REGISTRY` |
| Токен на запись в реестр | в пользовательском `~/.npmrc` или шагом пайплайна, не в файле репозитория |
| Токен с правом пуша | шаг выпуска отправляет коммит версий и тег в основную ветку |

Две вещи, без которых шаги ведут себя странно, а не падают:

- ⚠️ команды запускаются **из корня репозитория** — рекурсивные операции и их сводки работают
  от корня воркспейса;
- ⚠️ клон нужен **с полной историей** — «затронутое» считается сравнением с целевой веткой, и
  мелкому клону не от чего отмерять.

<h2 id="шаги">🚦 Шаги</h2>

### 1. Объявить изменение

Делает разработчик в своей ветке, не девопс:

```bash
pnpm plan
```

Команда спросит, какие пакеты и насколько поднять, и создаст файл плана в `.nx/version-plans/`.
Файл едет в ветке рядом с кодом и попадает в CHANGELOG при выпуске.

На merge request наличие плана проверяется отдельно — чтобы не выяснять это на выпуске.

### 2. Проверки

В ветке считается **только затронутое**: граф сравнивает её с целевой и берёт пакеты, до которых
изменение дотянулось, вместе с зависимыми.

```bash
nx affected -t lint typecheck test --base=origin/<целевая> --head=HEAD
```

В основной ветке — **всё целиком**, без выборки:

```bash
nx run-many -t lint typecheck test build
```

### 3. Посмотреть, что выпустится

```bash
nx release --dry-run
```

Считает всё и не пишет ничего: ни файлов, ни коммитов, ни тегов, ни публикации. Показывает, какая
версия получится и из каких планов она собрана. Стоит прогонять перед каждым выпуском.

### 4. Поднять версии

```bash
nx release --skip-publish
git push --follow-tags
```

Шаг меняет манифесты, пишет CHANGELOG, делает коммит и тег. Публикации здесь нет намеренно: тег
и есть сигнал к ней. Требуется чистое рабочее дерево.

### 5. Опубликовать

Запускается по тегу:

```bash
nx run-many -t build
nx release publish
```

🔨 Сборка обязательна. В реестр уезжает содержимое `dist`, и отдельного шага, который соберёт его
перед публикацией, нет: пропустите — уедет то, что лежало раньше.

Повторный запуск безопасен: уже опубликованные версии пропускаются.

### 6. Принять поставку

```bash
pnpm --filter @web-core/release release verify --json
```

Ставит опубликованные пакеты в пустой проект вне репозитория и проверяет, что они там работают.
Как читать отчёт и почему не всякий отказ означает сломанный пакет — [`README.md`](./README.md).

<h2 id="ошибки">🧯 Если что-то пошло не так</h2>

| Симптом | Что это значит |
|---|---|
| «изменений в планах версий нет» | планов нет — выпускать нечего, это не ошибка |
| отказ на подъёме версий: дерево не чистое | есть незакоммиченные правки |
| отказ на публикации | нет прав или реестр недоступен; повторить безопасно |
| отказ на приёмке | смотреть отчёт: бывает и дефект поставки, и граница самой пробы |
| «затронутое» захватывает слишком много | клон без полной истории, не с чем сравнивать |
